# Tuning for long sequence length guide

Reaching a long sequence length is a memory problem. Every knob in this guide trades GPU memory for something else -- recompute, compute sharding, host RAM, etc. -- so first use the knobs that impact performance the least until the target fits. Once a fitting configuration exists, [refine performance at that target](#refine-a-fitting-target-configuration) using its measured history rather than restarting the capacity search.

This guide covers the knobs `dss-platform` exposes, what each one costs, and the order to turn them on. The techniques behind the three biggest ones -- token-tiled MLP, activation CPU offload, and sequence parallelism -- are [Arctic Long Sequence Training](https://arxiv.org/abs/2506.13996); the per-subsystem docs linked below give the implementation detail this guide summarizes.

## Set Up Each Experiment Correctly

**Execute an immutable launcher snapshot and leave active runtime sources unchanged.** Copy a launcher into its unique trial-owner directory before invoking Bash, record that copy, and do not modify it while the process is running. Bash can read later portions of a script after earlier commands complete; inserting lines into an executing file can break its remaining parsing even when the edited file passes a fresh syntax check. Prepare the next candidate in a separate file or wait for the existing launcher to exit. If training already wrote a valid result and only subsequent bookkeeping failed, retain the raw result and failed launcher log, acquire fresh before/after runtime comparison and whole-assigned-node release evidence, and record the recovery separately without rewriting the result or rerunning measured updates.

**Schedule renewal five minutes before the earliest node deadline.** Use the earliest qualified per-node check plus 20 minutes as the receipt expiry, and schedule renewal by that check plus 15 minutes. Before any wait, setup phase or handoff, compare its expected duration with the renewal time; renew first if it would cross that time. Persist the receipt directory, exact renewal owner and both times so another session can verify the same attempt. Submission alone does not advance either time: require fresh qualified receipts, and promptly alert the operator if renewal fails.

**Qualify keepalive on every node before provisioning or staging, and throughout active work.** Run the existing GPU keepalive with a CUDA-capable interpreter on each allocated host, including sampling hosts and idle nodes awaiting their next role. Require successful touches on every eligible idle GPU; a live daemon, fresh agent heartbeat or updated `last_touch` file alone is insufficient. The shared helper can update that file even when every CUDA touch failed. AP's [keepalive receipt validator](../tuning/keepalive_receipt.py) checks actual successful GPU indices and records one receipt per host without changing the shared helper. Refresh and recheck at least every 20 minutes while working or waiting for long jobs, and at trial boundaries; keep touches outside scored training intervals. Explicitly use agent-gated mode, never add an unattended refresh loop. If any node's receipt is absent, stale or failed, do not launch another expensive phase: diagnose the interpreter, CUDA library path and daemon errors, then require a fresh successful check. Recent measured training activity can explain skipped touches, but neither GPU memory occupancy nor historical utilization proves current progress or future node lifetime.

**Persist the next keepalive deadline before a long wait or handoff.** Record the latest successful check for each node and the earliest next deadline in the durable session state; return to the per-node check within 20 minutes rather than treating the training or setup process as keepalive evidence. Bound each observation wait to end before that deadline, leaving time for the per-node checks. An observer timeout ends observation, not the remote experiment: recheck the exact owner instead of restarting it. The idle-allocation setup gate validates receipt age, distinct actual hosts, hostfile addresses and successful touches on all eight GPUs before provisioning. A failed check blocks new phases, not an automatic cancellation of an existing experiment. Report failures that cannot be promptly recovered; do not claim protection from independent scheduler or infrastructure termination.

**Validate the GPU selection used by the touch helper, not an earlier utilization sample.** GPU eligibility can change between samples during initialization or training. AP's receipt wrapper records the unchanged shared helper's actual selection before its CUDA touch, then requires a successful touch on every selected GPU; missing selection, partial success or CUDA errors remain failures. Raw selection and touch output are retained even when validation fails. During an exact owned live job, `qualify_allocation(..., require_idle=False)` validates fresh per-node receipts and permits explicitly recorded busy-GPU skips; inspect current job activity separately and do not describe skipped GPUs as touched. Default `qualify_allocation(...)` remains the idle setup gate and requires all eight GPUs per node. Active-job receipts do not authorize idle provisioning, prove training progress, or guarantee future allocation lifetime.

**The full-recipe launcher requires keepalive receipts in every mode.** Set `TUNING_KEEPALIVE_RECEIPTS` to fresh successful idle receipts whose staged hostfile exactly matches the experiment allocation. The launcher rejects missing receipts before setup and validates freshness, every host's CUDA success and the hostfile before starting a workload, including ordinary capacity searches. A failed gate does not cancel an already running experiment; diagnose it, renew all nodes and alert the operator before resuming new launches.

**Use an owned local gateway on the requested GPU allocation, never onprem.** Run through the allocation's remote runner and shared hostfile, not the agent's CPU environment, an onprem service or a managed Snowflake endpoint. Complete the provided `setup.sh` on every node; do not build a separate stack. Verify imported AP and `dss-platform-main` paths and dependency versions on every node. Stage the actual checkpoint on each node that may receive a zone, verify the pinned files and loader lookup, and confirm the allocation can place every requested sub-job, including sampling when present. Do not drop a sampling sub-job to make a recipe fit.

**Provision one identical GPU environment on every allocated node.** The provided `setup.sh` uses Torch 2.13.0+cu130, torchvision 0.28.0+cu130 and vLLM 0.31.0 for both training and sampling in the existing `dss` conda environment. Training-only overrides are rejected: assigning a sampling or training role must not change the environment build. Provision all nodes from the same setup-script snapshot, preserve GPU-family-specific wheel selection, and compare full package manifests, interpreter paths and imported sources after installation. AP's [five-node setup launcher](../tuning/one_node_setup.sh) takes fresh all-node idle keepalive receipts and refuses qualification if any node differs. A Torch-only match does not establish environment equality; retain the actual per-node inventories. Never create additional virtualenvs or node-role environments.

**Collect inventories inside each allocation before comparing separate jobs.** SSH connectivity within a job does not imply connectivity between jobs. Use each allocation's live runner and its own qualified hostfile to collect package and import records, then compare the complete records through shared artifacts. A cross-job SSH timeout is a collection failure, not an environment mismatch or a reason to reinstall packages. Require the exact expected host sets; partial inventories cannot qualify the combined allocation.

**The gateway does not own an allocation-wide Ray cluster.** The [local gateway](../../dss-platform-main/dss/ray_dss/gateway_server.py) reads a hostfile with one `<host> slots=<n>` line per node and starts a separate zone on free GPUs for each sub-job. Let this placement path manage the zones; do not pre-start an unrelated shared Ray cluster or attach the experiment to another job's workers. Stage the node-local `/job/hostfile` into the trial's shared artifact directory, verify its node and slot counts, and use that exact copy for launch and cleanup.

**Derive host roles and interpreter paths again when an allocation changes.** Match actual hostnames to the current hostfile addresses using per-node receipts, preserve the recipe's sampling GPU count and record the training and sampling roles in preparation metadata. Read each setup-provided interpreter path from that metadata; an old allocation's host prefix or node-local environment does not identify the new runtime. Require per-role package/import checks, fresh checkpoint lookup and actual training-loss qualification before transferring capacity bounds. Reuse the existing search and qualification helpers; an allocation change needs new evidence, not a separate search algorithm.

**Keep a requested smaller-node maximum separate from the larger-node result.** Preserve the qualified larger-node config and export. Reuse its controls as planning evidence, adjust the active world and legal SP/EP, and establish fresh buffered capacity bounds after current-allocation qualification. Neither a larger-node maximum nor an older smaller-node OOM supplies a bound for the changed topology or runtime. When only part of a reservation is occupied, stage the exact active hostfile and unmodified fresh receipts for those hosts, while still qualifying keepalive on every reserved node. Export under the active GPU count, not the reservation size.

**Recompute placement roles when switching recipes, not dependency versions.** A two-node sampler becoming a one-node sampler frees a host for training. Reuse the qualified common `dss` environment, update the role metadata and independently qualify the new workload's imports, checkpoint and actual loss. Do not modify an environment used by an active experiment. Historical role-specific setup scripts do not authorize restoring different package stacks; checkpoint staging and full-loss qualification remain separate required gates.

**Reuse compatible onboarding history when replacing recipes, including same-GPU-count work.** Keep setup and checkpoint qualifications, topology exclusions, diagnostics and successful memory-knob choices wherever their prerequisites still apply. Derive every preserved sub-job's GPU count from the replacement JSON rather than a historical one-node launcher. A different checkpoint, LoRA trainable-parameter set, precision or loss can change both memory and speed even at an identical GPU count: use prior evidence to narrow local refinement, but transfer measured outcomes only when their full configuration, workload, reserve and runtime match. Keep a requested fixed-length task at that length; replacing recipes does not authorize maximum-length search. Name final deployment JSONs with the model/variant, recipe kind, total active recipe GPU count and sequence length, for example `glm53-flash-lora-sft-8gpus-256k.json`. Count every preserved sampling sub-job too: eight training plus eight sampling GPUs use `glm53-flash-lora-rl-16gpus-256k.json`. Report training and sampling counts separately; do not include idle reservation GPUs in the filename.

**Do not block a ready recipe on another checkpoint's staging.** Independently qualify the selected recipe's pinned offline checkpoint on every assigned training and sampling host, plus its common setup and fresh keepalive receipts. A cached LoRA variant can then begin original validation while a separate BF16 checkpoint downloads. Preserve the unfinished staging owner's artifacts and require full qualification before using its remaining assignments. Run concurrent recipes only on disjoint role placements; record a changed placement rather than editing an active experiment's hostfile or silently rerunning its original.

**Keep the original preparation reference when chaining GLM RL refinements.** A capacity or chunk-refinement result directory is not necessarily a preparation directory. Set `TUNING_RUNTIME_PREPARATION` to the qualified directory containing `preparation.json`, `original-source-config.json` and the allocation hostfile when the selected history lacks those files. The existing capacity launcher resolves this directory to an absolute path before remote use; workers launched through SSH need not share the head process's working directory. The launcher validates the directory against the seed's hostfile, actual host roles, interpreter and model, records the reference, then independently compares freshly imported runtime evidence on every node with the completed seed. Missing metadata or empty receipts is a setup failure, not an OOM bound; preserve the failed launch and correct its reference without weakening runtime equality or rerunning a qualified seed.

**Stage GLM against the actual allocation and prepared interpreter.** The reusable [GLM allocation staging script](../tuning/glm_sft_allocation_stage.sh) takes the node count, a fresh keepalive-receipt directory and an optional completed role-setup directory. Its [receipt checks](../tuning/stage_glm_model.py) bind actual hostnames to allocation addresses, preserve the selected recipe hash and require every node's pinned model/revision, config/index hashes, shard count, weight bytes and successful offline loader lookup. Historical job 7 hostnames are not allocation evidence. The checkpoint pin can be reused for another recipe selecting that model, but the new recipe's hash is recorded separately. On the GPU head node through the remote runner, after preceding experiments have released the allocation and GLM role setup has qualified:

```bash
TUNING_GLM_STAGING_SOURCE=/path/to/cortex-training/recipes/rl/configs/glm53_flash.json \
  bash tuning/glm_sft_allocation_stage.sh \
  5 /path/to/fresh-keepalive-receipts /path/to/completed-glm-role-setup
```

The third argument selects that setup's interpreter path; the source, host/address mapping and setup metadata must agree. Staging remains a separate gate from full-recipe training qualification.

**Write a fresh receipt when requalifying completed staging.** Preserve the original checkpoint receipts and recheck the source hashes, every assigned host, pinned revision and offline-loader evidence. The replacement-recipe staging CLI accepts `qualify-staging --root /path/to/completed-staging --variant bf16 --output /path/to/new-owner/qualified-staging.json`; the new output path must not already exist. An exclusive-write collision in the old qualification receipt is bookkeeping failure, not evidence that checkpoint staging or the prepared runtime failed. Resume from those independently qualified artifacts instead of repeating setup, model copies or completed training.

**Give each experiment a unique log directory and an available gateway port.** This example uses port 8003; choose another free port if it is occupied, and use the same port in the client. Run with the setup-provided training environment on the GPU head node:

```bash
AP_CHECKOUT=/path/to/arctic-platform
DSS_CHECKOUT=/path/to/dss-platform-main
TRIAL_ROOT=/path/to/unique-trial-artifacts
HOSTFILE="$TRIAL_ROOT/hostfile"
mkdir -p "$TRIAL_ROOT"
cp -n /job/hostfile "$HOSTFILE"
export PYTHONPATH="$AP_CHECKOUT:$DSS_CHECKOUT${PYTHONPATH:+:$PYTHONPATH}"
export RAYDSS_LOG_DIR="$TRIAL_ROOT/zones"
export DSS_ZONE_HEALTH_TIMEOUT_S=300
python -m dss.ray_dss.gateway_server \
  --host 0.0.0.0 \
  --port 8003 \
  --backend gpu \
  --placement local \
  --hostfile "$HOSTFILE"
```

`DSS_ZONE_HEALTH_TIMEOUT_S` defaults to 60 seconds; select and record a larger bound when required by model loading. `RAYDSS_LOG_DIR` holds per-zone logs. `PYTHONPATH` is forwarded to zone processes: explicitly select the intended checkouts, then verify the actual imports on every node. `GET /health` must return `{"status":"OK"}` before submission. A healthy gateway proves only that the process is up, not that a recipe or training update works.

**Resolve model paths before creating zones.** An absolute path or a path beginning with `./` or `../` is used as supplied. An `<org>/<model>` identifier normally maps to `$DSS_BAKED_MODEL_ROOT/<org>/<model>`; the default root is `/mnt/neutrino/base-models`. Set `DSS_ALLOW_REMOTE_MODELS=1` when the identifier must remain unchanged for the Hugging Face loader. This also permits a pre-staged, pinned offline Hugging Face cache; it does not prove a download is needed or the cache is complete. Record the effective model path, revision and cache environment. The gateway does not copy weights between nodes.

**Pass the experiment environment explicitly to remote preflight commands.** Exporting variables on the coordinator does not forward them through `ds_ssh`. Include the intended cache, offline/model-resolution, source-import, CUDA-library and transport settings in each remote command, using shell quoting and an explicit allowlist rather than copying unrelated environment values. Verify those settings through actual loader lookup and imported-runtime evidence on every node. A staged checkpoint plus a coordinator-only `DSS_ALLOW_REMOTE_MODELS=1` can still produce `ModelCacheNotReady` on a remote check; that failure is infrastructure evidence, not OOM or baseline qualification. Gateway-to-zone forwarding is a separate mechanism and must also be verified.

**Qualify FlashInfer compiler discovery on the actual sampler host and inside its zone.** An installed FlashInfer package and a supported GPU do not by themselves satisfy vLLM's availability check. In the observed FlashInfer0.7.0.post1 runtime, the check also needs discoverable `nvcc` unless predownloaded cubins are enabled. Use the installed CUDA toolkit, not a new build: validate `CUDA_HOME/bin/nvcc`, include its directory in `PATH`, and merge `PATH` and `CUDA_HOME` into the gateway's existing JSON-array `DSS_PROPAGATE_ENV_EXTRA` setting. AP's [launcher environment helper](../tuning/cuda_runtime_environment.py) preserves other forwarding names and validates compiler discovery before gateway startup. Record the launch environment, verify the availability predicate on every assigned role host, and require successful sampler initialization before claiming the forwarding correction worked. A coordinator-only successful import is insufficient; keep package and runtime identity unchanged while correcting propagation.

**Avoid multiline inline Python in fan-out commands.** The observed `ds_ssh` command path flattened newlines inside a quoted `python -c` argument, turning valid Python into a remote syntax error. Prefer a shared helper script with an absolute path, or a short single-line command. Require successful per-node receipts rather than trusting the outer fan-out return code; a collector's syntax failure does not change a training memory bracket.

**Resolve shared artifact paths before remote execution.** Normalize preparation directories, hostfiles, configuration paths and output directories to absolute shared-filesystem paths on the coordinator, then quote them in each remote command. A remote shell need not start in the coordinator's working directory. A missing relative-path artifact is a launcher failure, not model capacity evidence; preserve the failed preflight and retry after correcting the path, without reinstalling an already qualified runtime.

**Require per-node receipts before declaring remote preparation complete.** A fan-out command or outer runner can return success despite a node-level failure. Require exactly one successful receipt from every intended host, matching checkpoint revision, configuration/index hashes and verified loader lookup, before emitting the preparation-complete marker or submitting a dependent recipe. Validate runtime-required files and indexed weight shards against pinned metadata; repository documents and Git metadata are not runtime dependencies unless the actual loader requires them. Preserve a failed staging attempt and retry only staging when its role environments already qualified; recheck runtime identity before training.

**Submit the complete create-job request through the CortexTrainingClient recipe route.** Run the client or CLI on the same GPU head node as the gateway in these examples: `127.0.0.1` refers to that node, not the agent's CPU machine. Verify the imported client checkout and version too. Use the [local client](../../cortex-training/src/cortex_training/client.py) directly, without a Snowflake host, personal access token (PAT) or Authorization header. Do not use the recipes package's `make_client`, which targets Snowflake accounts. Preserve the entire `sub_job_configs` envelope and every sub-job. If AP transport adaptation is required, apply the existing [AP bridge](../arctic_platform/integrations/dss_training_config.py) to training sub-jobs in a copied envelope, preserve all other sub-jobs and training semantics, and save the source and transported bodies separately. Never replace full-recipe submission with direct `/initialize` calls.

```python
import json
from cortex_training.client import CortexTrainingClient

client = CortexTrainingClient(
    base_url="http://127.0.0.1:8003",
    database="dev",
    schema="dev",
    endpoint="cortex-training",
    poll_interval=5.0,
    poll_max_interval=20.0,
    poll_timeout=3600.0,
)
with open("/path/to/recipe.json") as stream:
    body = json.load(stream)
created = client.create_job_from_body(body)
job = client.wait_for_job(created["job_id"])
```

The example submits a recipe that needs no transport adaptation; submit the saved transported body instead when adaptation is required. `poll_max_interval` must be at least `poll_interval`; the default `poll_timeout` is 1800 seconds. Submission POSTs the whole body to `/api/v2/databases/dev/schemas/dev/cortex-training` and returns a parent ID such as `p1` as soon as the parent is recorded. The local gateway ignores the database, schema and endpoint values for placement; those fields form the URL, not a Snowflake connection. Use `base_url` for this HTTP gateway, never a Snowflake hostname plus PAT.

The CLI uses the same client and skips PAT auth when `--base-url` has an HTTP or HTTPS scheme:

```bash
cortex-training submit /path/to/recipe.json \
  --base-url http://127.0.0.1:8003 \
  --database dev --schema dev --poll-timeout 3600 --wait
```

**Parent readiness is not a successful training step.** Sampling is provisioned first when present, and the parent remains pending until all requested zones are running. `wait_for_job` and CLI `--wait` wait for `running`, not for an optimizer update. Inspect `get_job` and stop the readiness wait on `failed`, `done` or `cancelled`; do not treat a returned parent ID, a running sampling zone or a successful model load as a training pass. A launcher's `RUNNING` marker can mean only that the trial driver started, while `INITIALIZED p1` acknowledges submission. Require the exact parent's gateway response or its saved `ready-job.json` to establish parent and child readiness, and complete step artifacts to establish training progress. After readiness, exercise the intended workload through the client's training interface and require at least two complete finite forward/backward and optimizer updates. Preserve original batch settings for onboarding and retain the mandatory 20 GiB reserve in every experiment; afterward use GBS1 for tuning. Never score update 1.

**Qualify the loss from training requests and measured results, not an invented recipe field.** The create-job recipe need not contain `loss_fn` on its training sub-job; SFT or GRPO is selected by each training request's processing contract. When reusing a seed, validate its actual request and recorded result loss, together with the compatible model head, rather than requiring or adding a `loss_fn` field to the recipe. A missing recipe field does not invalidate a qualified GRPO run, and a field containing `"grpo"` does not prove GRPO executed.

**A direct worker probe is diagnostic evidence, not recipe validation.** Calling `/initialize`, `/fwd-bwd` and `/step` directly with a synthetic workload can expose a real allocation failure, but it bypasses the parent recipe, sub-job provisioning and documented client path. Label such evidence explicitly and do not use it to satisfy the original-config gate or certify a full recipe. Record synthetic input shapes separately from configured length limits: a single full-length random row is a chosen workload, not something the recipe alone proves the normal client sends.

**Verify the actual attention implementation before claiming an on/off comparison.** Record both the requested backend and the implementation selected and executed on training workers. An importable FlashMLA wheel or a `sparse_mla` configuration label does not prove a FlashMLA kernel ran. For example, the [GLM-5.3 dispatch](../arctic_platform/model/implementations/glm53/context_parallel.py) previously sent the checkpoint's 512-wide absorbed query to the PyTorch reference path because the FlashMLA kernel requires width 576. The compatibility adapter zero-pads query/KV channels while retaining original scaling and 512 value channels; its actual CUDA outputs, gradients and dispatch must be qualified before training. This path uses FlashMLA forward with reference backward, not a fused FlashMLA backward. A tiny CUDA dispatch test is not full-model training evidence. A failure in the indexer before attention executes cannot establish either backend's attention memory cost. Compare memory only after both actual implementations complete the same workload at a feasible fixed length; report an unavailable comparison if either backend is unsupported or untested.

**Track and release the whole experiment.** Save the source and transported recipe hashes, hostfile, gateway PID and port, parent ID, child job and zone IDs, runtime identity, actual backend, workload and complete-update evidence. Use `client.get_job(job_id)` for status and `client.cancel_job(job_id)` or the corresponding local CLI for cancellation. After completion, failure or cancellation, verify that every owned training and sampling zone has exited and the assigned GPUs are released on every node before another trial. An HTTP success or parent status alone is not release proof. Preserve logs, avoid unrelated jobs and serialize experiments on the allocation.

**Distinguish a live controller from an active training request.** The final `result.json` can remain absent while the controller is handling a failed request, cancelling zones or recovering workers. Before reporting that an update is still running, inspect the exact request's zone events and complete raw failure, not just controller liveness or GPU occupancy. Report a confirmed request failure with cleanup still pending as such. Preserve the raw failure and wait for independent outcome, runtime and release qualification before accepting a memory bound or starting another trial; a missing result alone does not justify restarting the experiment.

**Accepted cancellation can still leave teardown blocked.** Workers may wait in communicator destruction while retaining model memory. Check exact-zone stacks and GPU ownership; if bounded normal teardown fails, use guarded owned-zone recovery and verify release independently. Keep the interrupted candidate classified by its observed failure, not by memory retained during teardown.

**Recover orphaned Ray workers using exact zone ownership, not process titles alone.** Teardown can remove a Ray parent before its actors exit; the surviving actors can be reparented to PID1 and overwrite their command lines with titles such as `ray::_DeepSpeedWorker`. An empty zone command tree is then not evidence of released GPUs. Inspect the GPU-owning PIDs and their open log descriptors for the exact owned `/tmp/ray-<zone-id>/` directory, including descriptors whose targets have been deleted. AP's [scoped recovery helper](../tuning/recover_oom_zone.py) uses that ownership evidence, protects the recovery launcher and its ancestors, and rechecks process start times before signaling to avoid PID-reuse errors. Still require both process-exit acknowledgments and idle GPUs on every node. Preserve the failed trial and its cleanup error; after independent release, reuse its compatible confirmed OOM when resuming the bracket rather than repeating the failed workload.

**Qualify sampling separately from training while using the same environment build.** An importable vLLM attention extension does not establish that a sampling engine works. Use the common setup-provided package/ABI combination on every node and qualify the actual sampling and training workloads separately. The local placement path launches the gateway's interpreter path remotely, so require matching node-local package manifests and imported sources before accepting placement. Do not infer sampling compatibility from a training CUDA kernel check. A different Torch version requires explicit operator approval and a supported common sampling stack, not a role-specific override.

**Inspect apparent stalls before interpreting utilization or changing a memory bound.** Compare elapsed time with compatible cold-update history, then collect exact-zone worker stacks and repeat the observation to check advancement. High GPU utilization can include a stalled communication kernel; a Python frame at a CUDA tensor's `.tolist()` can be waiting for earlier device work rather than identifying the operation that caused the delay. Verify the installed diagnostic signal handler, exact worker ownership and PID identity before requesting stacks. If evidence warrants cancelling a stalled probe, cancel only its owned parent, preserve the infrastructure result, verify whole-allocation release and retry the same candidate with unchanged controls. A delay, cancellation or collective stall is not an OOM endpoint. Exclude diagnostic cold-update time from performance scoring.

**Read the autograd worker's frames as well as the request thread's frames.** During PyTorch backward, the request thread can remain in `_engine_run_backward` while an autograd worker advances through checkpoint recomputation and gradient kernels. Read every dumped thread and compare the computational worker's newest frame across repeated exact-zone snapshots. An unchanged main-thread frame alone does not establish a stall; a changed worker frame establishes stage advancement, not successful completion.

**Separate checkpoint coordination failures from training failures.** Check the last initialization phase and whether any workload input was submitted. Distributed-checkpoint planning uses object collectives before training, so a timeout there does not measure sequence-dependent activation capacity. Compare watchdog sequence numbers and operation types on every rank: peers waiting in a later completion allgather can be consequences of another rank's unfinished metadata scatter. Preserve exact-zone Ray service logs while the session still exists; teardown can remove them. A first isolated failure after compatible successful loads permits one unchanged retry following verified release; a reproduced failure requires an isolated collective or loader diagnostic before another full-model attempt.

**Fail closed before sending diagnostic signals.** On Linux, verify the chosen signal's caught-handler bit in each selected worker's `/proc/<pid>/status` `SigCgt` mask in addition to checking the imported handler implementation. AP's [guarded stack requester](../tuning/current_capacity_stacks.py) requires a caught `SIGUSR1` handler on every selected worker before sending any signal, then rechecks handler presence and exact-zone process identity immediately before each request. A source-level handler declaration is not proof that every live process installed it. An unhandled `SIGUSR1` can terminate a process rather than dump a stack.

**Isolate a reproduced stall before another expensive full-model retry.** If a clean, unchanged retry stalls at the same synchronization point, collect guarded stacks across all ranks to check for divergent progress. Test the suspect preceding CUDA or collective work at the exact tensor shapes, with bounded timeouts, output/gradient reference checks, the 20 GiB reserve and verified cleanup. Derive field shapes and dtypes from the imported implementation, not a related architecture: GLM's decay gate is FP32 `[batch, tokens, heads, head_dim]`, not one scalar per head. Record each field's shape and dtype because they determine packed collective volume and dtype grouping. An isolated pass can narrow the diagnosis but cannot certify full-model capacity or prove that the surrounding runtime is healthy. Change implementation or controls only when supported by the diagnostic evidence, and requalify the resulting runtime.

**After an isolated pass, investigate the surrounding execution rather than assuming the full model is healthy.** A bounded full-recipe diagnostic with `CUDA_LAUNCH_BLOCKING=1` and collective tracing can help localize deferred CUDA work or expose ordering-sensitive behavior. Record those controls and verify their worker propagation; they change execution scheduling. Do not score diagnostic timings or use a synchronized pass to relabel an asynchronous stall as a normal capacity pass. Remove diagnostic controls and requalify the intended runtime after a supported correction.

**Test an existing synchronization control before inventing a communication fix.** If launch blocking allows progress that repeatedly stalled in the ordinary runtime, use a bounded, single-control trial with launch blocking and trace diagnostics removed. For AP's UCCL expert backend, `ARCTIC_UCCLEP_BACKWARD_BARRIER=1` makes each expert-parallel group synchronize after its backward communication event in [`_finish_backward_event`](../arctic_platform/model/implementations/moe/distributed/ucclep.py); it is an optional diagnostic candidate, not a universal tuning requirement or a proven remedy for every stall. Verify the flag on every exact-zone training worker, retain the 20 GiB reserve and workload, and require complete finite updates and whole-allocation release. A scheduling-sensitive diagnostic does not establish a particular race. Give changed execution controls a distinct runtime identity, qualify their capacity bounds afresh, and record any required launcher environment beside the deployment config.

**Use a previous runtime's memory boundary to plan a nearby probe, not to reuse its bound.** After a scheduling or implementation change qualifies a new buffered seed, a nearby historical failing length can be a useful first unmeasured candidate. Test that length under the new runtime and classify its actual outcome before bisection; if it passes, continue expanding to obtain a new OOM endpoint. Avoid automatically doubling a near-wall seed when the history already identifies a more informative nearby point. Record the planning rationale and never insert the old failure into the changed runtime's bracket.

**Pause automatic expansion at a planning checkpoint when the next probe needs new measurements.** Run one history-informed length increase with the required feasibility duration, preserve its raw result and verify whole-allocation release and unchanged runtime. Use two compatible passing lengths' peak counters to estimate memory growth and choose an aligned overshoot; account for implementation-specific nonlinear terms and unknown non-PyTorch demand rather than presenting the estimate as a bound. When memory attribution or the slope is unreliable, select a modest nearby increase from the implementation evidence instead of blindly doubling an expensive long-sequence workload. A deliberately reached trial limit is an incomplete search, not an infrastructure or memory failure. Reuse its qualified result to resume; do not export a maximum or start dependent recipe phases until an actual pass/OOM bracket and final qualification are complete.

**Reuse a completed passing trial even when an interrupted expansion left no OOM endpoint.** Select the original trial result directly, together with its effective payload, exact-zone worker logs and enclosing before/after runtime manifests; do not copy it into a fabricated baseline or rerun the measured length merely to satisfy a directory convention. Require the same configuration hash, workload, loss, reserve, execution controls and all-node release. Plan the next unmeasured length from compatible memory growth or nearby historical evidence, and retain cancellation as non-capacity evidence.

**Treat the required seed duration as a minimum, not an exact update count.** A five-update pass can satisfy a two-update onboarding gate, but every recorded update must retain finite loss/gradient norm and a successful advancing optimizer counter. After a late-update OOM requires five-update probes, explicitly require at least five updates when reusing a seed. An outer runner's EXIT0 or a launch marker is not qualification: independently validate the original result, effective payload, exact-zone reserve logs and before/after runtime and release evidence, including when a post-run bookkeeping check failed. Repair the bookkeeping and reuse qualified measurements instead of repeating expensive training.

**A fresh final stall invalidates the proposed deployment qualification, not a measured memory endpoint.** A synchronization control that passed an initial probe may still fail on a fresh job. Preserve the earlier finite updates and OOM bracket as runtime-specific history, require verified release, and do not export the candidate or start dependent recipe phases until final qualification succeeds. Use watchdog collective sequence numbers, types and element counts alongside repeated exact-zone stacks to identify which earlier GPU work did not finish. When repeating an isolated diagnostic, match the newly failing length and record any separate retained storage used to approximate the loaded-model footprint; do not confuse that storage with the mandatory safety reserve or call an isolated pass full-model qualification.

**Do not promote an unproven exchange-ordering workaround into a deployment requirement.** The experimental SP all-to-all barrier from closed PR247 has been removed from this checkout; the saved implementation and measured overhead remain [historical evidence](../tuning/sp-exchange-barrier-report.md), not an available tuning control. Historical runs that used that barrier retain their original runtime identity and must be requalified before their capacity bounds or deployment configs can be reused without it. Require a controlled stall reproducer and output/gradient parity before proposing another communication-ordering change. The separate UCCL backward synchronization control described above is unaffected.

## Validate the original configuration first

**Check CPU optimizer extension readiness before launching an offloaded baseline.** On each assigned training node, verify the existing `DeepSpeedCPUAdam` extension built by `setup.sh` loads in that node's prescribed `dss` environment. A worker stack blocked in `torch.utils.file_baton.FileBaton.wait` through the CPUAdam extension loader indicates a build-lock wait, not GPU capacity failure. Inspect the exact cache directory, lock identity and modification time, active compiler processes and already-built binary before choosing a recovery. Only archive that lock under a unique preserved name after repeated observations confirm it is unchanged, no compiler remains, the matching binary is newer and loads successfully, and previous owned workers have released their GPUs. Recheck those conditions immediately before the archive; never rename an actively owned lock, delete the cache or rebuild dependencies ad hoc. Record the repair and requalify actual initialization and updates separately: a successful binary import is not a training baseline pass.

**Every configuration onboarding starts with an unchanged-source training baseline on the assigned setup and GPU count, with 20 GiB withheld per GPU.** Complete required provisioning and actual-checkpoint staging, then run the supplied recipe through at least two complete forward/backward and optimizer updates. Keep the original source file unchanged and preserve the original model, precision, loss, sequence limit, parallelism, optimizer/offload, attention and batch settings in a separate experiment copy. Always add `training_config.debug.gpu_mem_preallocate_gib=20` to that copy before transport; the reserve is mandatory during onboarding too. Preserve other source debug controls, record this deliberate experiment-only addition and never remove the reserve to obtain a pass. Do not force global batch size (GBS) to one for onboarding. Transport adaptation must preserve training semantics and be saved separately. Static memory estimates, dependency checks, successful model loading and results from another recipe are not proof that the original configuration works.

**Classify an original-baseline failure before choosing the next action.** Save the source hash, effective config, setup/runtime identity, allocated GPU count, completed-update evidence and raw logs; require finite loss and gradient norm, successful optimizer updates and advancing engine counters for a pass. Never score update 1 as a performance sample. Infrastructure, unsupported kernels and correctness failures require diagnosis and correction before tuning. A confirmed capacity OOM instead permits the [fitting-configuration recovery](#recover-a-capacity-failing-baseline) requested by the operator; it does not require an unchanged impossible baseline to pass. Record an unchanged-source failure separately from the qualification of a modified copy and never treat that failure as a length bound for a different configuration. Verify owned-worker release on every node before another trial.

**A loss-head correction is a modified candidate, not an original-baseline pass.** Disabling fused scalar cross-entropy or enabling a chunked token-logprob head changes the original training configuration, even if parallelism and sequence length are unchanged. Name that attempt `head-corrected`, preserve the original head's separate failure evidence, and qualify the corrected copy using the actual requested loss. A request-contract preflight identifies unsupported settings but does not prove that the original recipe completed training. If no original attempt is recorded for the relevant source and runtime, resolve that onboarding gate before starting the corrected recipe's capacity search; do not silently rename the correction to `original`.

**Use the existing trial runner's explicit original-baseline mode for the unchanged attempt.** Pass `--original-config-baseline --steps 2` and the actual loss to [run_trial.py](../tuning/run_trial.py), using the saved original configuration as `--config`. Do not pass sequence, token-budget, row or request-mode overrides. This mode still materializes the 20 GiB reserve and submits the full recipe, but lets the supplied head reach the actual runtime rather than replacing it or stopping at the tuning-only head preflight. The runtime's real error, completed updates and release evidence determine the outcome. A failed attempt is not a pass, and unsupported synthetic GRPO topology remains rejected. Ordinary tuning keeps its head-contract preflight; never use original-baseline mode to qualify a modified candidate or weaken capacity checks.

**Use the Qwen launcher on the current prepared allocation, with an explicit baseline mode.** The existing [Qwen baseline launcher](../tuning/qwen_rl_current_baseline_stas_dev_7.sh) defaults to `original-baseline`; choose `head-corrected` explicitly for a modified candidate. Set `TUNING_QWEN_SETUP`, `TUNING_QWEN_STAGING` and `TUNING_QWEN_SETUP_LOG` to the current qualified preparation, checkpoint receipts and exact completed setup-owner log, plus `TUNING_KEEPALIVE_RECEIPTS` to fresh successful idle receipts. Despite its historical filename, the launcher reads the interpreter and actual host roles from preparation metadata, verifies the current hostfile and per-node evidence, and does not assume job 7 hostnames. Original mode adds only the reserve, uses two complete updates and sends no length, row or head overrides; an unsupported-head preflight remains diagnostic so the actual unchanged recipe can run and record its failure. Corrected mode retains the supported-head preflight. Qualify the resulting source/effective payload, runtime, all-rank reserves, finite updates or actual failure, and all-node release independently; a launcher's completion marker alone is not a baseline pass.

**Select the unchanged mode in the recipe launcher too.** The [GLM RL launcher](../tuning/glm_rl_current_baseline_stas_dev_7.sh) defaults to `original-baseline`; run that attempt before explicitly selecting `head-corrected`, `resident-ep8` or `offloaded-ep32`. The unchanged candidate adds only the reserve; the selected head-chunk argument does not alter the original recipe. Set `TUNING_KEEPALIVE_RECEIPTS` to the current allocation's fresh receipt directory before each invocation. After role setup and model staging qualify, pass the setup root, its exact autorun log, the preceding Qwen outcome root and its exact log, then the selected mode. The preceding outcome can be a qualified fixed-target export or a completed capacity export with its checked pass/OOM bracket and five-update final verification. Bind the completed owner log to that exact outcome root and derive a capacity handoff's length from the validated final bracket, not an earlier planned candidate, historical filename or unrelated `EXIT 0`. The launcher rechecks the exported content and hash; a short capacity seed or deliberate trial-limit checkpoint is not a completed handoff. Head preflights remain diagnostics, not evidence that the original recipe ran or failed.

**Preserve explicit model-default attention across transport.** For AP MoE recipes, explicit `attn_implementation: null` requests the registered AP loader's default, not the DSS schema's generic backend. The AP [transport bridge](../arctic_platform/integrations/dss_training_config.py) resolves that default through `ModelSpec` before DSS drops null fields during serialization; it does not edit the source recipe or invent a model-specific default. Save source and transport separately, verify the schema round-trip and actual loader selection, and retain any pre-correction failure. An absent attention field and an explicitly selected backend remain unchanged by this normalization.

**Preserve automatic AP loader selection when the source omits a DSS provider.** For EP greater than one, the transport bridge resolves AP's registered loader and maps only supported built-in MoE loaders to DSS's existing `prime_rl` route. The source recipe remains unchanged; explicit providers are never replaced, and an unmapped loader fails closed. Without this normalization, DSS defaults an omitted provider to `huggingface` and rejects expert parallelism before model loading. In addition to schema round-trips, run the actual DSS model-dependent parallelism preflight against the serialized payload and staged checkpoint on every allocated node before launching training.

**Qualify checkpoint staging against the loader's actual offline lookup.** Every indexed weight shard must be complete, but that alone does not qualify configuration/tokenizer files or revision resolution. Exercise the loader's actual `local_files_only=True` lookup for the recipe's revision on every node before training. Stage additional repository files when that lookup requires them; do not infer the requirement solely from the repository's file listing. Preserve downloader-generated cache metadata; do not fabricate completeness markers. A cache-completeness failure is infrastructure evidence, not a sequence-length bound.

**Require a qualified buffered seed before performance ranking or maximum-length search.** After the original baseline passes, or capacity recovery qualifies a fitting modified copy, apply the tuning objective and GBS=1 while retaining the [GPU safety margin](#leave-a-gpu-safety-margin), recording every changed control. Compatible history can satisfy the original attempt or fitting qualification when source, runtime, workload, reserve and allocation match; requalify changed identities and do not repeat an unchanged confirmed OOM. No-buffer evidence never qualifies the buffered seed. A recovered pass does not retrospectively validate the original source.

**Validate recorded length overrides against the exact measured payload.** A probe may keep its source JSON unchanged while explicitly overriding `max_seq_len`, `mb_spec.max_tokens_per_mb` and the provider sequence limit. Verify the original source hash, reconstruct only those recorded overrides in a separate in-memory copy, and require exact equality with the saved effective configuration before accepting the probe as a capacity seed. Do not rewrite the raw result, alter unrelated controls or accept a launch-blocking diagnostic as an ordinary-runtime seed. Preserve any required AP scheduling control in subsequent capacity runs and record that control beside the final deployment JSON; unset it before switching to an unrelated recipe.

### Recover a capacity-failing baseline

**Keep implementation and integration fixes in the operator-designated repository.** In this Arctic Platform workflow, debug controls, transport adaptation and model or collective corrections belong in AP. Treat the paired DSS checkout as a dependency and diagnostic source, not a patch destination, unless the operator explicitly authorizes DSS changes.

**A fixed-target OOM starts a fitting search, not a finished outcome.** Keep the requested length, workload, model, precision, loss and 20 GiB reserve. Establish whether GPU tensors, allocator pressure, non-PyTorch memory or aggregate host state caused the failure, then select a supported change that reduces that term. Apply the [node-count selection](#choose-the-node-count) and [local refinement](#refine-a-fitting-target-configuration) rules, including coupled SP/EP/offload/chunk moves when needed. Reserve all sampling sub-jobs within the authorized total. Qualify the first fitting copy through two complete finite updates before ranking warm performance or searching maximum length.

**Reclassify the failed phase after every recovery.** Bounding an RL logprob head can expose a later routed-expert backward allocation rather than finish the fitting search. Preserve the head correction and address that newly measured transient with a supported expert-dispatch chunk; do not keep shrinking the head to fix an unrelated allocation. Same-site, same-model SFT evidence can identify a useful candidate, but the changed RL configuration still needs its own complete buffered updates, runtime checks and cleanup qualification. The [fixed-256K GLM results](../one-node-256k-tuning-results.md) record this progression without treating a failed request as a timing sample.

**Audit the effective configuration and actual shards after increasing nodes.** Check serialized controls, injected implementations, worker group membership, per-rank shapes and actual input occupancy. More reserved nodes do not help if SP or the active world stayed unchanged. For a sparse indexer that materializes FP32 scores, the temporary can scale as `local_queries * index_heads * global_pooled_keys`, or `sequence_length^2 / SP` at fixed pooling. Doubling SP halves that term at an identical length, but comparing a shorter passing point with a longer failing point is not that experiment. Count simultaneous copies and parameter storage before predicting fit; the guide's generic linear-memory SP rule is not a guarantee for every backend.

**Bound a diagnosed query-scoring temporary without reducing the workload.** When existing controls cannot remove an oversized temporary and the operator authorizes an implementation correction, query-axis chunking can preserve every global key, FP32 score, causal mask, packed boundary and top-k selection. AP's [GLM-5.3 indexer](../arctic_platform/model/implementations/glm53/context_parallel.py) caps each score tile at 512 MiB, except when one query alone exceeds that budget, and applies scale/ReLU in place under `no_grad` before releasing the tile. The budget is not a whole-model memory ceiling. Require selection parity against the original eager expression, output/loss/gradient parity, and an actual CUDA peak-memory check before full-model qualification. Record a new runtime identity and reconsider node-count exclusions caused by the old temporary; do not reuse its OOMs as bounds for the corrected implementation. Keep the original sequence length and 20 GiB reserve, and retain AP ownership for all code changes.

**Do not stop at the first OOM or invent unsupported controls.** Use compatible history to choose the next useful supported configuration, document the changed controls and expected memory effect, and verify cleanup before launching. An analytical exclusion must identify the unavoidable term and the implementations/layouts it covers. If the remaining obstruction requires a backend implementation change rather than an existing knob, state that distinction and obtain agreement when it would undo a user-requested revert or change the requested model semantics. Do not silently remove the reserve, replace a long sequence with short rows, alter attention precision or report an untested winner.

## What sets the wall

A rank runs out of one of two resources, and which one decides everything about what to do next.

**GPU memory** is the usual wall. On an H200 the card exposes ~141 GiB, of which for some models up to ~13 GiB is not PyTorch's to allocate: the CUDA primary context, NCCL buffers, DeepEP/NVSHMEM heaps, and cuBLAS and attention workspaces. That leaves ~126-130 GiB of torch-reserved memory, split between (1) terms that are constant (parameters, optimizer state, comm buffers) and (2) terms that scale with sequence length (activations, recompute transients, the logits tensor). Only the second group moves when a knob changes.

**Host memory** becomes the wall as soon as optimizer and activation offload are both on, because both move their bytes to the same place. Ray kills workers at 0.95 of node RAM, so on a 2000 GB node the ceiling arrives while the cards still have room: a dense 27B run at 1.67M tokens holds 109.96 GiB of a card's ~130 GiB and still dies at the next length up, on host RSS of 175.52 GiB per rank across eight ranks.

Knowing which wall is binding is the whole diagnosis. `training_config.step_peak_memory_log` returns both peaks in the `/step` response for one MAX all-reduce per step; `DSS_MEM_BREAKDOWN=1` splits a rank's GPU memory into parameters, gradients, optimizer state, activations, and allocator slack. `dss-platform` [`docs/memory_diagnostics.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/memory_diagnostics.md) covers the rest.

### Leave a GPU safety margin

**Keep OOM as the capacity gate, with 20 GiB withheld on every GPU during every experiment.** Set `training_config.debug.gpu_mem_preallocate_gib=20` for original-config onboarding, diagnostic training runs, search candidates and final verification. Arctic Platform allocates a live, non-gradient CUDA byte tensor before model loading and retains it on the model through forward/backward and optimizer updates; native AP workers additionally retain it until engine/communicator teardown. The runtime default is zero (disabled), so experiment launchers must materialize and check 20 explicitly even when a source omits the setting or sets it to zero. A different margin requires explicit user instruction. Preserve the original recipe and record the effective margin. This uses a fixed binary-GiB margin, not a percentage or a sampled-memory threshold.

```json
{"training_config": {"debug": {"gpu_mem_preallocate_gib": 20}}}
```

**Keep the reserve implementation in Arctic Platform, including DSS-backed runs.** AP's [memory helper](../arctic_platform/model/implementations/debug/gpu_memory.py), [model specification](../arctic_platform/model/config.py) and [factory](../arctic_platform/model/factory.py) own validation, loader filtering and allocation. When the existing DSS MoE endpoint requires nested loader controls, call AP's [transport bridge](../arctic_platform/integrations/dss_training_config.py) before initialization and record the transformed payload separately. The bridge preserves flat deployment recipes and does not require modifying DSS; verify the effective reserve and dispatch chunk on every node rather than assuming unknown schema fields are applied.

**The buffer competes with all device allocations, including non-PyTorch libraries.** Cache eviction and peak-counter resets cannot reclaim a live tensor. A trial still needs complete successful updates and verified cleanup; buffer allocation failure is a GPU OOM, not permission to reduce the margin silently. Memory measurements include the buffer, so do not add 20 GiB again or claim 20 GiB remains physically free during the buffered run. Removing the tensor for deployment leaves that capacity available, but is not a guarantee against arbitrary data-dependent spikes. Mixture-of-experts (MoE) token routing can imbalance ranks and raise transient demand; model-specific margin selection remains future work, with 20 GiB the current tuning default.

**A changed margin starts a new measured configuration.** No-buffer passes and timings remain historical planning evidence, not proof of a pass with 20 GiB withheld. Include the setting in configuration hashes, bracket identity and performance-baseline acceptance; never relabel old evidence. Known OOMs without a buffer still exclude an otherwise unchanged configuration with a larger buffer, so do not repeat them merely because the margin changed. Preserve historical exported recipes rather than adding an unmeasured setting to a measured winner.

**Final deployment recipes omit debug configuration; qualification keeps the 20 GiB buffer.** Retain the buffered trial and effective-config snapshots, verify their exact equality before removing `training_config.debug` and any legacy `training_config.prime_rl.debug` block from an exported copy, and record that intentional difference. Do not remove the buffer from winner verification or present deployment timings as measured without it. A longer sequence may fit when the withheld memory is available, but that larger limit is unverified and the operator accepts the risk of OOM on new data. For example, an MoE input can route tokens unevenly among expert-parallel ranks: a rank receiving many more tokens than in a balanced trial can require substantially more peak GPU memory. The buffer reduces this risk; it does not guarantee that every routing imbalance or future component fits.

**Use allocator peaks for attribution, and watch allocator health separately.** `step_peak_memory_log` reports the exact retained PyTorch allocated high-water counter, not total device peak; existing `DSS_MEM_LOG`, `DSS_MEM_BREAKDOWN` (requires `DSS_MEM_LOG`) and `DSS_MEM_STAGED` provide rank diagnostics. Reserved-minus-allocated includes reusable cache and fragmentation, not live tensor demand; current device-used-minus-current-reserved estimates non-PyTorch usage at that instant, not its peak. GPU polling is not required to enforce the safety margin or obtain allocator peaks. Inspect every rank's logs for `N PyTorch allocator cache flushes since last step`: nonzero counts indicate allocation pressure and cache loss, which can hurt latency even when the trial passes. Keep the OOM outcome, flag the configuration as allocator-pressure affected, and investigate before selecting a performance winner. A cold-step-only warning remains initialization evidence; recurring warm-step warnings are a performance concern. Do not call `empty_cache()` in scored runs to hide them.

**A rank-0 response is not necessarily a rank-0 measurement.** Check the imported reducer: DSS's `peak_memory_across_ranks` takes a distributed MAX before rank 0 returns `/step`. With initialized distributed training, label `gpu_peak` the maximum allocated high-water counter across training ranks; it neither identifies the worst rank nor measures total-device memory. Despite its name, `cpu_peak` is the maximum current per-process host RSS sampled at `/step`, not a lifetime high-water counter or the sum of host memory across nodes. The helper falls back to local values without an initialized process group. Keep rank-local profiler snapshots distinct, and do not use an all-rank allocator maximum as a bound on each rank's non-PyTorch allocations or total-device pressure.

**Recovered allocation failures are pressure evidence too.** PyTorch can log `expandable_segments: memory mapping failed with OOM` and still complete the update after allocator recovery. A completed update remains a capacity pass, not an OOM upper bound, but the warning prevents an unsupported claim that the allocator was healthy. Preserve the warning's rank, timestamp and attempted allocation; absence of the DeepSpeed cache-flush message does not prove zero retries, especially on engines that do not emit that message. Check final verification and warm fixed-target trials before selecting a performance winner.

**Verify head selection at the loader, not just the trainer's enabled message.** For DSS-backed AP MoE training, top-level `fused_lm_head_token_chunk_size` and `fp32_lm_head` must reach the nested loader channel through AP's transport bridge. A trainer can log that chunking is enabled from the top-level request while AP actually injects `VanillaOutputLinear`. Check resolved AP options and the injection log on every rank before treating an OOM as evidence against the intended chunked configuration. AP's MoE logprob head tiles vocabulary at 8192 internally; a different top-level vocabulary chunk is unsupported and rejected by the bridge. RL needs per-token logprobs, so explicitly disable fused cross-entropy when selecting the chunked logprob head.

**Preserve raw worker logs before teardown when the runner removes node-local logs.** Aggregated Ray output can deduplicate messages across ranks, so absence of a warning there alone is not a complete all-rank audit. Collect the exact owned zone's worker stdout (`.out`) and stderr (`.err`) on every allocated node before teardown, scan both streams for allocator warnings, verify coverage of all training ranks, and distinguish cold warnings from warm warnings. A read-only incremental log collector avoids changing the trainer or relying on a narrow post-step inspection window.

## The knobs

### Already on, and worth leaving on

| Knob | Default | What it does |
| --- | --- | --- |
| `cuda_allocator_conf` | `"expandable_segments:True"` | Lets the caching allocator grow and reuse segments instead of stranding gaps between variable-sized activation buffers. Long-context runs fragment badly without it and OOM on a later step at a footprint that fit earlier. `dss-platform` [`docs/cuda_allocator.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/cuda_allocator.md) |
| `mb_spec.max_tokens_per_mb` | `10240` | Packs rows into one `[1, packed_tokens]` model call so no compute is spent on padding. It removes work rather than trading for memory. `dss-platform` [`docs/packing.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/packing.md) |
| `activation_checkpointing` | `True` | Whole-block recompute: the largest memory lever and the largest step-time cost here, about +29% FLOPs at long context. Also the precondition for activation offload. |
| `attn_implementation` | `"flash_attention_3"` (or 2/4) | An attention kernel with an O(S) memory footprint. An eager or math fallback materializes the `S x S` score matrix and no other knob will rescue that. |
| `ac_config.router_replay_recompute` | `True` | MoE only. Replays the router's `topk` on the backward recompute so tensor shapes inside a checkpointed block match the forward. Whole-block AC on an MoE model fails with `CheckpointError: recomputed values have different metadata` without it. |

### Activation-transient shavers

These cap a tensor whose size grows with tokens, without changing what is computed.

| Knob | Default | Effect |
| --- | --- | --- |
| `fused_lm_head_token_chunk_size` | unset | Tiles the `hidden @ lm_head.T` projection over tokens, so peak logits are `O(token_chunk x vocab_chunk)` instead of `O(tokens x vocab)`. |
| `fused_lm_head_vocab_chunk_size` | `8192` | The vocab extent of that tile. |
| `tiled_mlp_token_chunk_size` | unset | Shards a dense FFN over tokens and recomputes it shard by shard, holding ~`1/shards` of its intermediate. On MoE it reaches only the shared expert, which is not worth the recompute -- see the tiled-MLP section. `dss-platform` [`docs/tiled_mlp.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/tiled_mlp.md) |
| `prime_rl.fused_cross_entropy` | `"liger"` | Fuses head and loss so full-vocabulary logits never materialize at all. `"liger"` (or `True`) selects the Liger kernel and `False` opts out. The AP-owned GLM loader also supports `"quack"`; the AP-owned Qwen3.5 MoE loader rejects it when the model spec is built. Mutually exclusive with `fused_lm_head_token_chunk_size`: both select an lm_head implementation, and `load_ap_moe` rejects the pair before model construction. |
| `prime_rl.deepep_token_chunk_size` | `None` (unchunked) | MoE only. Chunks the expert all-to-all so a rank's per-chunk received tokens are capped at `ep x chunk`, independent of sequence length and of routing skew. |

The head is the largest of these on a large-vocabulary model. Hugging Face cross-entropy materializes `[tokens, vocab]` logits in bf16, keeps the gradient, and upcasts to fp32 inside the loss. On a 248320-token vocabulary that is about 2.53 GiB per 1,000 rank-local tokens -- roughly 44 GiB of a card at 24,000 tokens per rank, spent on the head alone. Chunking replaces it with a constant tile: at `16384 x 8192` in fp32, 0.5 GiB regardless of sequence length.

Three routes reach that state and they are not interchangeable. `model_provider="liger"` installs the Liger fused head for a dense model with nothing further to set. On the Prime-RL path `prime_rl.fused_cross_entropy` is already `"liger"` and `False` opts out; `"quack"` is a CuTe-DSL alternative only for AP-owned GLM. `model_provider="huggingface"` has no fused head at all, so it needs the explicit chunk sizes.

A fused head returns a scalar loss instead of logits once labels are present, which two request shapes cannot use: a non-binary SFT `loss_mask` routes through an external cross-entropy, and `loss_fn="causal_cross_entropy"` needs logits or per-token logprobs. Both raise rather than degrading quietly, and both are fixed by setting `fused_cross_entropy=False` and chunking the head instead.

**Choose the head for the actual training loss before tuning memory.** Group Relative Policy Optimization (GRPO) consumes differentiable per-token logprobs with advantages and a loss mask, not a scalar supervised fine-tuning (SFT) loss. On this Prime-RL MoE path, set `prime_rl.fused_cross_entropy=false` and a positive `fused_lm_head_token_chunk_size` to select the [chunked logprob head](../arctic_platform/model/implementations/moe/layers/lm_head.py); preserve the [GRPO request contract](../arctic_platform/integrations/_cortex_shared.py) during forward/backward. An SFT trial cannot qualify an RL configuration's memory or timing. A training-only GRPO stress test also does not qualify the recipe's sampling subjob; preserve that envelope and report sampling as unmeasured.

**Translate flat head controls before DSS initialization.** DSS's trainer-enabled predicate can fall back to the top-level chunk size, but the AP MoE loader receives nested options. Use the [AP transport bridge](../arctic_platform/integrations/dss_training_config.py) to carry the flat controls into that channel, then verify the resolved chunk and injected head as described [above](#leave-a-gpu-safety-margin). A trainer-enabled message alone does not establish that the carved loader applied the setting.

### Gradient reduction

**Inspect gradient-reduction buffers when a near-capacity run fails in ZeRO all-reduction.** ZeRO is DeepSpeed's sharded optimizer; its `ds_config.zero_optimization.reduce_bucket_size` controls the number of gradient elements grouped for communication, not a byte count. Query the installed default and actual communication dtype before estimating memory. For example, 500000000 BF16 elements occupy about 0.93 GiB in one buffer; 67108864 occupy 0.125 GiB. Count any dtype-conversion tensors and overlapping communication buffers separately. With contiguous gradients, a smaller bucket can leave more room for a late NCCL allocation, although an NCCL OOM alone does not prove that the gradient bucket caused the failure.

**Do not infer communication precision from model precision.** Read the resolved DeepSpeed precision in every worker's startup log. For the measured GLM RL EP32 run, all 32 training workers reported `communication_data_type=fp32` despite BF16 model settings. The installed default is 500000000 gradient elements, so one FP32 communication buffer is about 1.86 GiB; 67108864 FP32 elements occupy 0.25 GiB. Those are buffer-size estimates, not measured total savings: gradient storage, dtype conversion, allocator caching and NCCL allocations can coexist. Use the failure's actual collective traceback to justify a targeted bucket probe, then measure complete updates before accepting a larger limit.

**Put the controlled bucket change in the recipe, not an unchecked environment override.** The paired DSS runtime's [`_build_ds_config`](../../dss-platform-main/dss/ray_dss/jobs/gpu/training.py) shallow-merges `training_config.ds_config`: a supplied `zero_optimization` mapping replaces the earlier mapping, including any `DSS_ZERO_BUCKET_SIZE` adjustment. That environment variable also changes both reduction and all-gather buckets when it applies. For the single-knob probe, set only `training_config.ds_config.zero_optimization.reduce_bucket_size` and retain all other measured ZeRO settings. Check the imported merge behavior before assuming an environment flag reached the engine.

**A tiny collective warmup does not establish large-bucket feasibility.** The failing GLM RL run had successful DeepSpeed collective prewarm logs on all 32 training workers before its later NCCL allocation OOM. The existing prewarm uses a one-element tensor; do not treat its success as proof that every subsequent gradient reduction fits, or assume another identical warmup resolves the failure. Inspect the actual failing collective and its buffer settings first.

**Change only the reduction bucket for the first justified probe.** Preserve optimizer stage, precision, offloads, parallelism, workload, GBS1 and the 20 GiB reserve. Smaller buckets increase communication-call count and can hurt speed; score warm forward/backward time, never update 1. Require finite complete updates and unchanged runtime evidence. A changed bucket creates a new configuration identity, so re-establish its capacity bracket instead of importing OOMs from the larger-bucket configuration. This is a targeted memory tradeoff, not a blanket throughput recommendation.

**Use the existing full-recipe launcher's fresh qualification mode for a bucket refinement.** Set `TUNING_CAPACITY_REDUCE_BUCKET_SIZE=67108864`, `TUNING_CAPACITY_REQUALIFY_STEPS=5`, `TUNING_CAPACITY_SEED_RESULT` to the historical result supplying the measured length and controls, `TUNING_KEEPALIVE_RECEIPTS` to fresh allocation-matched idle receipts, and `TUNING_RUNTIME_PYTHON` to the prepared interpreter. Keep any required `TUNING_RUNTIME_PREPARATION` reference. The launcher changes only the ZeRO-2 reduction bucket, records the historical reference separately, checks five fresh updates and runtime-after, then stops without expansion or export. It rejects simultaneous expert-chunk, EP, diagnostic, resume, first-probe, old-failure and trial-limit settings. Verify the resolved reduction bucket and communication dtype in every training worker's logs before estimating savings; unchanged all-gather and optimizer settings must remain preserved.

**A superseded short pass can reconstruct controls, but cannot supply a capacity endpoint.** After a late-update OOM, preserve that failure and qualify cleanup and the full before/after runtime before refining the bucket. A historical two-update result at the failed length may supply only the source, workload and runtime context for the changed configuration's fresh five-update attempt. The launcher labels this as a reference, not a capacity bound. Require the changed configuration to pass five updates before starting its new history; carry the demonstrated five-update probe duration forward and do not import the previous bucket's passing or failing endpoints. If the new attempt fails, it supplies no passing seed.

### Recompute

`ac_config.mode` selects what the backward pass recomputes.

- **`"full"`** (default) wraps each whole transformer block, so autograd saves only the block input. Largest saving, one extra forward per block, and the only mode with a single per-block boundary that offload can stream.
- **`"selective"`** with `targets` (default `["norm"]`) checkpoints only the named submodules and keeps everything else resident. It recomputes less and saves less, and it cannot be combined with offload -- `offload_config.enabled=True` with `mode="selective"` raises a `ValueError`.

`ac_config.freq` applies checkpointing to every Nth block, which trades recompute against residency in between the two modes. `dss-platform` [`docs/activation_offload.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/activation_offload.md) has the full field list.

**Map checkpoint frequency to layer types before estimating savings.** The AP [`apply_ac`](../arctic_platform/model/implementations/qwen35/model_builder.py) selects zero-based indices satisfying `layer_id % freq == 0`, not an evenly distributed fraction of each layer type. With a repeating linear/linear/linear/full-attention pattern, frequency2 checkpoints only linear-attention layers and leaves every full-attention layer resident. Count checkpointed and uncheckpointed layers by type from the actual model configuration; equal layer counts need not imply equal saved bytes, recompute cost or communication cost.

**Partial checkpointing changes what activation offload copies.** The AP [saved-tensor hooks](../arctic_platform/model/implementations/gpu/activation_offload.py) cover eligible autograd saves throughout the wrapped forward, not only checkpoint inputs. An uncheckpointed block can therefore offload internal activations and eligible weight views as well as boundaries; repeated saves can create separate CPU slots. A frequency2/offload candidate is not the known frequency2/resident OOM configuration, but its host and transfer budgets must include these additional saves. `keep_last_n` counts eligible saved-tensor slots, not decoder layers. A pinned-cache cap limits retained cache, not active live offload slots; it cannot establish host feasibility by itself.

### Offload

Both offloads move bytes to host RAM. Together they are what turns a GPU-bound run into a host-bound one.

**Optimizer state**, through `ds_config.zero_optimization.offload_optimizer`. ZeRO stage 2 is the default; adding the offload key moves Adam state to CPU and switches the optimizer to `DeepSpeedCPUAdam` automatically (`_resolve_optimizer_name`). This is the single largest static saving and the precondition for everything below it.

```python
"training_config": {
    "ds_config": {
        "zero_optimization": {
            "stage": 2,
            "offload_optimizer": {"device": "cpu", "pin_memory": True},
        }
    }
}
```

**Activation-checkpoint boundaries**, through `ac_config.offload_config.enabled`. Full-mode checkpointing drops each block's internals but cannot drop the block *input*: autograd has to save it, because that is what the recomputation replays from. A completed forward therefore leaves one boundary hidden state per layer resident, `[tokens_per_rank, hidden]` each. For a 64-layer model at hidden 5120 in bf16 that is `64 x 5120 x 2` bytes = 640 KB per token, and it grows linearly with sequence length after everything else checkpointing saved has been freed. Offload streams those boundaries to pinned host memory on a dedicated stream and prefetches them back one step ahead in backward, leaving `keep_last_n` resident.

```python
"training_config": {
    "activation_checkpointing": True,
    "ac_config": {
        "mode": "full",                 # offload requires "full"; "selective" keeps intermediates on GPU
        "freq": 1,                      # checkpoint every Nth block
        "router_replay_recompute": True,  # MoE only; keeps recompute shapes equal to the forward
        "offload_config": {
            "enabled": True,            # off by default
            "keep_last_n": 1,           # boundaries left resident; backward needs the newest first
            "use_streams": True,        # overlap the copies with compute
            # omit tensor_size_threshold (or 1048576) for the 1 MiB floor; smaller saves pass through
            "pin_memory_enabled": True,        # False falls back to pageable buffers and slower copies
            "pin_memory_max_size_gib": "auto", # retained pinned-cache cap, or a hard GiB number
            "pin_memory_bucket_size_mib": 64,  # capacity rounding for contiguous pinned buffers
        },
    },
}
```

Every field is shown at its default except `enabled`, so a job that only wants the offload sets that one key:

```python
"training_config": {
    "ac_config": {"offload_config": {"enabled": True}}
}
```

`keep_last_n` and the three `pin_memory_*` fields are the ones to reach for when this offload is what pushed the run into the host-RAM wall: `keep_last_n` decides how many boundaries stay on the card instead of going to host (see below), `pin_memory_max_size_gib` caps what the staging cache retains, and `pin_memory_enabled=False` gives up copy speed to stop pinning host pages altogether. `dss-platform` [`docs/activation_offload.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/activation_offload.md) has the cache's retention and eviction rules.

The saved-tensor hooks that do this are *dynamically scoped*: they cover only tensors saved by code running inside the wrapped forward. Both the causal LM and its backbone are wrapped under one manager, because the chunked LM head calls the backbone directly to skip the full-vocabulary projection. A future rebinding of `forward` that runs the decoder blocks outside both wrappers would silently keep every boundary on the card -- measurably, that costs 640 KB per token and drops a dense 27B ceiling from 1.67M tokens to 680K, with no error to explain it.

### Parallelism

| Knob | Effect on the wall | Cost |
| --- | --- | --- |
| `sp_size` | The largest lever. Every token-shaped tensor in the backbone shrinks ~`1/sp_size`, attention included. | Eight all-to-alls per full-attention layer per step, on the critical path. About +11% forward/backward per doubling inside a node; a step change when the group crosses the node boundary. |
| `ep_size` | MoE only. Higher `ep` shards expert weights further but can grow dispatch/combine transients; check actual routing and ownership. | Backend/layout dependent; a group spanning nodes can add dispatch/combine latency. |

**The two degrees are independent axes over the same ranks, not a factorization of the world.** Nothing requires `sp_size * ep_size == world_size`. Each divides `world_size` on its own and the two are free to overlap completely, so `sp == ep == world_size` is a supported shape -- and it is one of the points measured below: `sp8·ep8` on a single 8xH200 node is `sp == ep == world == 8`, one SP group spanning every rank while the experts are sharded eight ways across those same eight GPUs. Every rank belongs to one SP group and one EP group and runs both families of collectives every step.

**Check EP placement against the selected backend, not a universal node-local restriction.** With `sp_size == world_size`, data parallelism is one and a supported node-local EP layout can keep expert groups within NVLink blocks while SP spans nodes. The installed [parallelism validator](../../dss-platform-main/dss/ray_dss/jobs/gpu/sp/config.py) also accepts host-complete EP groups spanning nodes; its GPU-per-node argument is placement metadata, not an EP-backend gate. The qualified GLM SP64/EP16 run uses UCCL and spans two eight-GPU nodes per expert group. Do not transfer a node-local DeepEP restriction to another backend or infer backend support from topology validation alone. Verify the selected communicator and actual worker groups during qualification.

**Resolve an omitted backend from the imported loader before proposing a backend-specific control.** An absent `prime_rl.ep_comm_backend` does not mean that expert communication is disabled or that another recipe's backend applies. Trace the transported options through the installed loader and model builder, recording resolved values and imported source paths/hashes on the intended hosts. The current [Flash-MoE loader](../arctic_platform/model/loaders/flash_moe.py) validates [Qwen3_5MoeOptions](../arctic_platform/model/loaders/qwen3_5_moe.py), whose omitted backend defaults to `deepep` and expert-token chunk defaults to `None`. Those defaults do not by themselves prove which kernel executed. Preserve existing evidence; when testing a new expert-chunk candidate, make the verified backend explicit in that copied configuration, confirm chunk propagation to the model, and establish fresh bounds for the changed configuration.

**Consider lowering EP to remove inter-node expert traffic when storage permits.** On eight-GPU nodes, a legal EP16-to-EP8 move can make dispatch/combine node-local while preserving the same world, SP, GBS1 and target tokens. Lower EP increases each rank's resident expert weights, and changes expert-data-parallel ownership of gradients and optimizer state; check the loader's actual storage dtypes and both GPU and host budgets with reserve20 before probing. Reuse the measured fitting config and choose this move only when its memory estimate fits and group placement actually removes a communication boundary. Compensate with a supported memory control when necessary; do not assume that every EP8 layout is faster or rerun an unchanged known OOM.

**Head divisibility depends on the actual attention path.** Ulysses head exchange requires `sp_size` to divide the exchanged head count; for a 16-head implementation this caps SP at 16 even when more nodes are available. Sequence-only context parallelism does not impose that constraint by itself, but a hybrid model's other layers may still require it: GLM's KDA exchange excludes SP40/SP48/SP56 with 64 heads. Check imported model metadata, the installed validator and every layer family before excluding an allocation. `dss-platform` [`docs/sequence_parallelism.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/sequence_parallelism.md) covers topology rules and layout selection.

The `ep` direction is counter-intuitive and holds at every `sp` tier measured. On Qwen3.6-35B-A3B, one 8xH200 node, sp8: `ep2` reaches 2.28M tokens, `ep4` 2.18M, and `ep8` 1.70M. Static expert weights fall as `ep` rises, but the DeepEP dispatch/combine buffers and the token-permutation activation rise faster. Keep `ep` at the smallest value that fits the expert weights.

**Measured utilization rises with sequence length, not with `sp_size`.** Every hardware FLOPs utilization figure here is taken at that configuration's own ceiling -- about 24% at `sp1`, 38% at `sp4`, 44.6% at `sp8` on one node, 47.4% at `sp16` on two -- and each ceiling is a longer sequence than the one before it, so the column tracks length and the degree only comes along with it. The mechanism is the `O(S^2)` term: on Qwen3.6-35B-A3B attention is about 89% of FLOPs at 512K and 95% at 1.15M, FlashAttention runs at high arithmetic intensity, and its quadratic work amortizes the fixed per-step overheads. Utilization plateaus around 48%.

**Rising utilization is not rising throughput.** The same `sp8·ep2` configuration at DeepEP chunk 1024 takes 12.68 secs per 100K tokens at a 1000K sequence and 24.45 secs per 100K at its 2.28M ceiling, while utilization goes from 39.0% to 44.6%. The GPU is busier and every token costs nearly twice the wall-clock, because the work per token itself grows with the sequence. Raising `sp` at a *fixed* length costs about 11% per doubling in forward/backward; what it buys is the ability to hold the longer sequence at all, not a cheaper token.

**That slowdown is an attention-dominated result, not a universal rule about longer sequences.** Here, growing attention work per token outweighs the reduction in fixed overhead per token. A different workload with substantial optimizer time and nearly constant forward/backward cost per token can show the opposite outcome: a longer packed call improves complete-step tokens/sec. [Optimizer amortization](#why-longer-packed-sequences-can-improve-throughput) explains that regime and the Flash-Next measurements below.

### Diagnostics

The first is a request config field; the rest are environment variables.

`step_peak_memory_log` is a request field, set in `training_config` beside every other knob in this guide:

```python
"training_config": {
    "step_peak_memory_log": True
}
```

It returns the job-wide maximum across ranks of peak GPU and host memory in the `/step` response, at a cost of one MAX all-reduce per step -- cheap enough to leave on for the whole tuning session, and the number a binary search on sequence length reads.

The remaining four are **environment variables on the trainer processes**. They do not appear in the request, and setting them requires reaching the worker environment rather than editing a payload:

| Environment variable | Use |
| --- | --- |
| `DSS_MEM_BREAKDOWN=1` | Per-rank split into parameters, gradients, optimizer state, activations, allocator slack, and non-PyTorch allocations. This is what says which term is binding. |
| `DSS_MEM_STAGED=1` | Attributes the fixed non-PyTorch tax to CUDA context, NCCL, DeepSpeed init, and first forward/backward. |
| `DSS_MEM_SNAPSHOT=<prefix>` | Records the CUDA allocator's full allocation history with Python stacks and writes a per-rank pickle. This is the one that names the module responsible for a peak -- see [Reading the memory allocator profiler](#reading-the-memory-allocator-profiler). |
| `DSS_ACT_OFFLOAD_LOG=1` | Offload counters per rank: boundaries offloaded, pinned allocations, reuses, evictions, cache size. A count of zero when offload is configured means the hooks are not covering the forward that runs the blocks. |
| `DSS_MOE_IMBALANCE=1` | MoE only. Per-rank `max_chunk_recv`: the largest received-token count of any DeepEP dispatch, which is the quantity that sizes the fp32 combine transient. Its spread across ranks is routing skew, and that spread is the headroom a ceiling measured on synthetic data does not account for -- it sizes the reserve described under `deepep_token_chunk_size` below. |

### Not levers

Each of these looks like a memory lever and measures as flat.

- **`train_batch_size` / batch size.** With `sp_size >= 2` the forward runs a `[1, tokens_per_rank]` shard per rank, so batch size only adds accumulation steps. Peak is a function of sequence length and the parallel degrees, not of batch size.
- **ZeRO comm buckets** (`DSS_ZERO_BUCKET_SIZE`). Shrinking the reduce/allgather buckets from 500M to 50M elements on Qwen3.6-35B-A3B at sp8·ep2 and 1000K tokens moves peak reserved from 79.7 GiB to 79.5 GiB and throughput from 441 TFLOPS to 445. The buckets are live during gradient reduction, which is disjoint from the instant that sets the peak.
- **The DeepEP `Config` buffer.** Fixed per-rank token capacity, so it does not grow with sequence length: `<=0.12 GiB` at `ep <= 8`. Shrinking it reclaims ~0.1 GiB of a ~13 GiB non-PyTorch tax.
- **`fp32_lm_head`.** This one costs memory rather than saving it -- it widens head arithmetic proportional to `vocab x hidden`. It exists so gradients do not depend on how tokens were grouped into model calls, which matters for parity tests and layout comparisons, not for reaching a length. `dss-platform` [`docs/lm_head_gradient_precision.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/lm_head_gradient_precision.md)
- **`compile.fullgraph`.** Incompatible with `tiled_mlp_token_chunk_size`; request validation rejects the combination.

## Tiled MLP pays off on dense models and not on MoE

The MLP tiling saving is proportional to the intermediate width of the FFN being tiled, and that width differs by more than an order of magnitude between the two architectures.

A dense SwiGLU FFN holds two `[tokens, intermediate]` tensors at once, and `intermediate` is typically three to five times `hidden`. Tiling it over tokens leaves ~`1/shards` of that resident, so on a dense model it caps the largest token-linear activation in the block after attention.

On an MoE model it saves almost nothing, for two reasons that compound:

- **The intermediate is small.** Qwen3.6-35B-A3B has `hidden_size=2048` with `shared_expert_intermediate_size=512` and `moe_intermediate_size=512`. The tiled tensor is a quarter of hidden width, where a dense model's is several times it.
- **Routed experts are deliberately excluded.** `apply_dense_tiled_mlp` skips any module with `experts` as a component of its qualified name. Tiling couples the ranks to one another, and routing decouples them. Under ZeRO-3 the tiled forward all-reduces its local shard count with `MAX` over the whole world before it tiles, so every rank executes the same number of tiles and the parameter all-gathers stay in one order; under ZeRO-1/2 `TiledMLP` instead defers the FFN weights' gradient reduction to the last shard. Both mechanisms assume the ranks agree on how many shards there are. A dense MLP runs exactly once per rank per layer per step, so they do. A routed expert runs only when the router sent it tokens on that rank, with a token count no peer shares -- so ranks can disagree about whether the collective is reached at all, which is a hang rather than a wrong shard count. The Prime-RL loaders therefore tile only the `FeedForward` / `BCFeedForward` shared expert, which every rank runs unconditionally. The routed path -- where an MoE model's token-linear FFN activation actually lives, at `topk` copies of every token -- is not tiled at all. It is bounded by `deepep_token_chunk_size` instead.

On Qwen3.6-35B-A3B, one 8xH200 node, sequence held at 1000K so memory is not the limiter, DeepEP chunk 4096, comparing tiling at 16k against tiling off entirely: `sp8·ep2` gives 79.7 GiB and 441 TFLOPS tiled against 79.1 GiB and 443 TFLOPS untiled, and `sp8·ep8` gives 82.2 GiB and 423 TFLOPS tiled against 82.2 GiB and 421 TFLOPS untiled. Tiling loses 0.6 GiB and 0.5% at `ep2` and gains 0.0 GiB and 0.5% at `ep8`. The two arms disagree in sign, which is what a difference below the noise floor looks like; 32k and 64k chunks fall inside the same 437-446 TFLOPS band. The sweep establishes that the *saving* is zero, not that the cost is.

The cost is not zero in principle, and it points the wrong way. `TiledMLP` runs the FFN on one token shard at a time and recomputes each shard in backward, so tiling adds a forward pass of the module it wraps. Full activation checkpointing is already on, so the FFN is computed once in the forward and again in the checkpoint recompute; tiling makes the tiled module pay a third. On a dense model that third pass buys back a large intermediate. Here it applies only to the 512-wide shared expert, which carries about a ninth of the FFN work -- one shared expert against `topk=8` routed experts of the same width -- so the extra pass is real and lands under the noise floor rather than being free.

Pushed to its own ceiling instead of held at 1000K, a finer 1k chunk moves the wall from 2.28M tokens to 2.31M -- 1.3% -- for a 1.6% slower step, and 4.64M to 4.70M for 2.3% slower on two nodes. That is the cost becoming visible once the chunk is small enough to multiply the launches.

**What to take from it.**

1. On a dense model, set `tiled_mlp_token_chunk_size` early: it is cheap and it caps a large tensor.
2. On an MoE model, leave it unset. It has nothing to cap -- the routed path is untiled by construction and the shared expert is a ninth of the FFN -- so enabling it pays a recompute pass for a saving that measures as zero. The MoE equivalent of this knob is `deepep_token_chunk_size`, and that one is neither free nor optional near the ceiling.

## The order to enable them

Ordered by step-time cost at the length you are trying to reach, cheapest first. Stop adding memory controls when the target fits. For an already fitting configuration, use [local performance refinement](#refine-a-fitting-target-configuration): a different combination of controls can fit with less total latency.

| # | Knob | Step-time cost | What it buys |
| --- | --- | --- | --- |
| 1 | `cuda_allocator_conf` | none; default `"expandable_segments:True"` | the allocator grows and reuses segments instead of stranding gaps between variable-sized activation buffers. Without it a footprint that fit on one step OOMs on a later one |
| 2 | `mb_spec.max_tokens_per_mb` | none; default `10240` | rows pack into one `[1, packed_tokens]` call, so no compute is spent on padding. It removes work rather than trading for memory |
| 3 | `attn_implementation` | none; default FlashAttention | attention with an O(S) footprint. An eager or math fallback materializes the `S x S` score matrix, and no row below can rescue that |
| 4 | `ep_size` **down**, on MoE | roughly neutral | 1.70M at ep8 to 2.28M at ep2, sp8 on one node |
| 5 | `ac_config.offload_config.enabled` | ~0%; the copies overlap compute | ~790K to ~1.15M at sp4·ep2. Host RAM becomes the new wall. Needs optimizer state off the card first -- see below |
| 6 | `fused_lm_head_token_chunk_size` + `fused_lm_head_vocab_chunk_size`, or a fused head: `prime_rl.fused_cross_entropy` is Liger by default, and `model_provider="liger"` fuses head and loss with no setting at all | ~1.5% | removes the `[tokens, vocab]` logits tensor. On a 248320-vocabulary dense 27B this alone moves the ceiling from 195K to 680K tokens |
| 7 | `ds_config.zero_optimization.offload_optimizer` | ~3% at the ceiling -- a 14-20 secs CPU Adam step against ~0.3 secs on GPU, inside a ~560 secs step at 2.28M tokens -- but dominant at short lengths | the gate: ~32K to ~790K at sp4·ep2, a factor of 24. Usually already on |
| 8 | `tiled_mlp_token_chunk_size` | ~3.6% | caps the dense FFN intermediate. Dense models only -- skip it on MoE, where it caps nothing and adds a recompute pass (previous section) |
| 9 | `sp_size` | ~+11% forward/backward per doubling within a node; a step change when the group spans nodes | the largest lever, ~2x context per doubling |
| 10 | `activation_checkpointing` | ~+29%. Full-mode recompute adds one forward pass, taking the causal FLOPs coefficient on the `S^2 d` attention term from 7 to 9, and attention is about 95% of FLOPs at 1.15M tokens. Derived from the FLOPs accounting rather than an A/B run -- see below | the largest memory lever in the document: drops every block's internal activation and leaves only the per-layer boundary, 640 KB per token on the dense 27B. On by default, and the precondition for activation offload |
| 11 | `prime_rl.deepep_token_chunk_size` | ~+54% forward/backward at 128K; -13% to -17% throughput going from 4096 to 1024 at 1000K | bounds the fp32 combine transient against routing skew. Not a length lever -- see below |

**Those numbers came off two specific models: treat them as a reference point rather than a prediction.** The measurements are 8xH200 nodes in bf16 with ZeRO-2, FlashAttention-3 and full activation checkpointing -- the MoE figures on Qwen3.6-35B-A3B at the configurations named under [Measured ceilings](#measured-ceilings), the vocabulary figure on a dense 27B with a 248320-token vocabulary.

The ranking is the part that holds up best: DeepEP chunking really is an order of magnitude dearer than the head, and activation offload really is close to free. Magnitudes usually land in the same band on a model of similar shape. The exact percentages will not reproduce, and one entry can change category outright rather than drift -- tiled MLP is a large saving on a wide dense FFN and too small to measure on this MoE, where the difference it makes sits inside the run-to-run spread.

What each cost tracks is what lets you carry a figure to a model of a different shape:

| Knob | Its cost scales with |
| --- | --- |
| lm-head chunking / fused CE | vocabulary against hidden size. Large vocabulary, large saving; a small one makes the knob pointless |
| `offload_optimizer` | the CPU Adam step as a fraction of the whole step, so it falls as sequence length grows and rises on a host with slower memory or fewer cores |
| `ac_config.offload_config.enabled` | whether the boundary copies still fit under compute. It stays near zero until the PCIe link saturates, then it stops hiding |
| `tiled_mlp_token_chunk_size` | the intermediate width of the FFN being tiled, and the number of shards it is cut into |
| `sp_size` | the share of time in full attention, and whether the SP group crosses the node boundary |
| `deepep_token_chunk_size` | the MoE layer count and how many dispatches the chunk size implies |
| `activation_checkpointing` | one extra forward pass, so it lands near +30% for any transformer. The 29% figure is the attention-dominated long-context case |

**Optimizer offload sits at its cost because it is usually already on.** When it is not, it comes before everything else regardless of cost, because activation offload cannot move a wall that Adam state is setting. At sp4·ep2 on Qwen3.6-35B-A3B with neither offload the card fills at about 32K tokens; that term is constant in sequence length, so lowering `ep_size`, streaming the checkpoint boundaries and chunking the head do not touch it. Optimizer offload takes it to ~790K, and only then does streaming the checkpoint boundaries buy the further ~1.15M. Read `DSS_MEM_BREAKDOWN` first and attack whichever term is binding; the ladder breaks ties.

**Activation checkpointing is the knob a job is most likely to be paying without having chosen it,** since it defaults to `True`. Its 29% is the one figure in the table that is not a subtraction between two runs: every measurement in this document was taken with full checkpointing on, so the cost comes from the FLOPs accounting instead -- full-mode recompute is one extra forward pass, and at 1.15M tokens attention dominates enough that the causal `S^2 d` coefficient going from 7 to 9 is the whole of it. The recompute never appears in the TFLOPS column, because hardware FLOPs utilization counts it as work the GPU genuinely did; it appears in wall-clock seconds per 100K tokens. Turning it **down** is a graded option whenever memory is not the binding term: `activation_checkpointing` takes `False` to stop paying the recompute outright, or a positive integer to checkpoint every Nth block (`activation_checkpointing_freq`, `gradient_checkpointing_freq` and `gradient_checkpointing` are aliases of the same field), and `ac_config.mode="selective"` with `targets` recomputes only the named submodules. Each recomputes less and saves less. Offload requires checkpointing enabled with `ac_config.mode="full"`, but does not require frequency1: [AP's config validator](../arctic_platform/model/config.py) accepts partial full-block checkpointing with offload. Its broader saved-tensor copies require the host and transfer accounting described under [Recompute](#recompute); selective mode remains incompatible with offload.

### Notes on `sp_size` and `deepep_token_chunk_size`

**Prefer a fitting node-local SP group, but let measured latency decide.** For contiguous SP groups, a degree that divides the GPUs per node can stay on NVLink; above the node size the same traffic leaves the node every layer, on a fabric with far lower per-GPU bandwidth. Verify the actual group placement: decoupled SP/EP layouts can cross nodes even at small SP degrees. A full-attention layer exchanges twice on the forward: sequence shards are traded for head shards before attention and traded back after. Query, key and value cross at the first point and the attention output crosses at the second, which is four `all_to_all` collectives as the code issues them -- three calls to `sequence_head_all_to_all` for query, key and value and a fourth for the output, all in AP's `_ulysses_attn_forward` (`arctic-platform` [`arctic_platform/model/implementations/qwen35/sequence_parallel.py`](../arctic_platform/model/implementations/qwen35/sequence_parallel.py)), and every one is differentiable, so the backward repeats them transposed. A GatedDeltaNet layer exchanges three times, packing its inputs into one; `dss-platform` [`docs/sequence_parallelism.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/sequence_parallelism.md) has both patterns with what each one moves. That is a step change, not a continuation of the slope, so `sp16` is a different regime from `sp8` rather than one more doubling of it, and it is worth timing on the target cluster rather than assuming a ratio. Degrees that do not divide the node size can place some contiguous groups across the boundary and some inside it, which makes step time depend on which group a rank is in.

Before taking SP across nodes, verify the EFA network plugin itself. aws-ofi-nccl 1.17.2 retained about 10 KiB of host memory per cross-node collective and grew without a plateau; 1.21.1 was flat at 0.0002 MiB/step over 5000 steps of the same bare collective probe. Use the tested 1.21.1 plugin and confirm the run selected `NET/OFI` with `Using network Libfabric` rather than silently falling back to sockets. `dss-platform` [`docs/sequence_parallelism_memory_map.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/sequence_parallelism_memory_map.md#upgrading-the-plugin-removes-it) records the version and transport controls.

The smallest-fitting-SP heuristic must be tested at the requested length, not inferred from separate ceilings. On Qwen3.6-35B-A3B each configuration at its own ceiling gives 14.63 secs/100K at `sp4*ep2` (1.15M) against 24.45 secs/100K at `sp8*ep2` (2.28M). The TFLOPS column moves the other way, 381 against 441, because both length and utilization rise together. Those different-length results do not establish which configuration is fastest at one fixed target.

**`deepep_token_chunk_size` bounds expert transients, not resident activations.** Chunking does not shrink the `O(tokens/sp)` resident activation, so it cannot remove a ceiling set by that storage. It can raise a measured ceiling when the binding allocation is a routed-expert transient: diagnose the allocation and qualify fresh bounds rather than excluding chunking from capacity recovery. Extra dispatches also cost time, so a smaller chunk is not automatically a performance improvement. Unchunked, the fp32 combine transient scales with `tokens/sp` and reaches roughly 16.8 GiB at 2.2M tokens on Qwen3.6-35B-A3B with balanced routing -- it rides at the wall, and a skewed batch OOMs there. Chunked, a rank's per-chunk received tokens are capped at `ep x chunk` whatever the routing does. Follow the [routed-expert diagnostic procedure](#what-to-look-for) when a transient, rather than resident storage, appears to bind capacity.

Because the default is `None` -- unchunked, the whole local shard in one dispatch -- a ceiling measured without the flag does not carry that bound. Real data routes with more skew than uniform-random probe data does, so a config tuned to its wall on synthetic tokens needs headroom left for it. Reserve roughly `(ep - 1) x chunk x topk x (2 x hidden + 3 x moe_intermediate) x dtype_bytes`, which at `ep4` and chunk 8192 on this model is ~4 GiB and matches the measured ~4 GiB inter-rank peak spread. Or shrink the chunk until the budget fits the headroom already there: 1024 cuts it about eightfold.

At the wall the two settings trade cleanly rather than one dominating: sp8·ep2 on one node reaches 2.28M tokens at 441 TFLOPS with chunk 1024, and 2.18M at 482 TFLOPS with chunk 4096. Take 1024 when context-bound and 4096 when not.

**Refine a snapshot-backed expert transient with a fresh long probe.** When allocator stacks identify the routed-expert FP32 combine as a large transient, try a smaller `deepep_token_chunk_size` while preserving the backend and workload. An omitted `prime_rl.ep_comm_backend` resolves to DeepEP in this AP path; confirm that default in the prepared worker runtime, rather than silently switching to UCCL. Explicit unsupported or null backend values are not that default. The existing full-recipe launcher accepts `TUNING_CAPACITY_EXPERT_CHUNK_SIZE=1024` only with `TUNING_CAPACITY_REQUALIFY_STEPS>=5`, an explicit historical seed and fresh allocation-matched idle receipts. It changes only the chunk control and performs a fresh qualification, without expansion, export or inherited unchunked bounds. A captured rank's large allocation does not prove another rank's failed allocation origin; retain that uncertainty and require the longer ordinary probe to pass.

**Qualify a supported expert-sharding alternative before declaring the selected capacity limit.** For the corrected GLM RL SP32/EP16 configuration with activation offload, the existing full-recipe launcher accepts `TUNING_CAPACITY_GLM_EP32=1` in fresh requalification mode with at least five updates, an explicit qualified historical seed and fresh allocation-matched idle receipts. The candidate changes only EP16 to EP32; sampling, SP, head/expert chunks, offload, GBS1 and the 20 GiB reserve remain unchanged. The launcher rejects combined refinements, diagnostics, expansion or inherited failing endpoints. A newly qualified EP32 seed needs its own measured pass/OOM bracket. A CUDA launch failure or collective watchdog under EP16 is not an EP32 bound, and a successful EP32 probe alone does not establish the previous failure's cause.

## Choose the node count

**When the objective is the fewest nodes, node count takes priority over latency.** Within the user-authorized range, find the smallest qualified allocation for the fixed target, then refine warm forward/backward latency on that allocation. Do not choose a faster larger allocation without changing the stated objective. Record both the available reservation and the nodes/GPUs actually assigned to the complete recipe; spare reserved nodes do not make a smaller experiment an eight-node result.

**Make the later capacity search's allocation scope explicit.** A minimum-node fixed-target winner does not establish the maximum length attainable on a larger authorized reservation. When the request seeks the largest length over a node range, consider the larger legal training worlds after preserving every sampling sub-job, and reuse an already qualified larger-world seed when its runtime and workload identity match. This avoids completing a smaller-world bracket only to restart on a larger world. If the operator fixes the capacity allocation or explicitly prioritizes node count for capacity too, retain that scope. Report the actual allocation and fixed-configuration ceiling; a legal layout or one successful length is not a measured maximum across untested controls.

**Prune illegal layouts before staging weights.** Read the actual model metadata and installed parallelism implementation, then check SP and EP divisibility, model-specific head exchange, expert ownership, group placement, and engine batch legality. With global batch size one, microbatch size one and one accumulation step, the current DeepSpeed engine requires one data-parallel group: active training world size equals SP. More active ranks at unchanged SP would duplicate the target and violate GBS1. For a hybrid model, inspect each attention path: sequence-only sparse MLA does not by itself require head divisibility, but another layer's head-parallel exchange can impose that constraint. Run the imported runtime's metadata-only preflight before treating a layout as legal. See AP [GLM context parallelism](../arctic_platform/model/implementations/glm53/context_parallel.py) and DSS [parallelism validation](../../dss-platform-main/dss/ray_dss/jobs/gpu/sp/config.py).

**Non-power-of-two node counts are not universally invalid.** For example, on eight-GPU nodes a GBS1 GLM model whose KDA layers have 64 exchanged heads cannot use all 40, 48 or 56 training GPUs: SP40/SP48/SP56 do not divide 64. SP64 is the next larger legal full-node layout after SP32. That is a model-specific topology exclusion, not a memory failure and not a rule that every recipe needs power-of-two nodes. Check EP independently; a legal SP does not prove that experts or process groups can be partitioned by the selected EP.

**Align capacity candidates to the selected SP, not only a power-of-two budget.** Use the least common multiple of the packing/kernel alignment and SP, and round any administrative search cap down to that alignment. For SP48 with a1024-token alignment, candidate budgets must be multiples of3072. A nearby aligned capacity seed is a new measured length, not a256K fixed-target pass. Preserve the required4K/8K bracket resolution; an alignment that prevents that resolution is not a completed search. Do not let preprocessing add padding to repair an ineligible length.

**Qualify a changed capacity seed at its actual length and loss.** Complete two finite training updates with fresh unpadded input, verify the exact buffered effective payload, every training rank's reserve, all-recipe release and unchanged per-node runtime. A fixed-target export gate that requires exactly256K cannot qualify an aligned264192-token seed; neither rounding nor metadata topology checks replace the new measurement. Reuse a compatible seed's evidence rather than rerunning it solely to fit a reporting label.

**Count sampling and training placement together.** Preserve every sub-job in an RL recipe and sum concurrently placed GPU requirements. A legal training topology may still need an additional node for sampling, so a five- or six-node complete recipe can be valid even when training alone uses four nodes. Verify actual placement against the experiment's staged subset hostfile. A partial-node layout is a separate candidate: record the exact active ranks and topology, and do not assume an unused node or GPU reduces training memory.

**Rejecting a saturated training world does not exclude a smaller placement.** If eight sampling GPUs leave 24 training slots on four nodes and SP24 violates head divisibility, inspect supported smaller worlds such as SP16 instead of declaring four nodes impossible. The [GLM RL metadata preflight](../tuning/glm_rl_topology_preflight.py) checks DP1 training worlds and EP2/4/8/16/32 candidates within the actual allocation cap, including partial-node placements. Its node counts are placement lower bounds, not measured placements or capacity passes; unsupported EP choices and smaller active counts outside the authorized range remain separate exclusions. Select expensive probes from memory evidence and compatible history, not from every legal metadata combination.

**Check the placement policy before counting a smaller candidate's nodes.** A CPU-only dry run of the imported [local placement backend](../../dss-platform-main/dss/ray_dss/placement/local.py) can determine how legal GPU requests pack onto the staged hostfile without provisioning zones. Preserve sampling first, then account for the training layout and count distinct occupied hosts. For example, an eight-GPU sampler plus SP16 training can occupy three eight-GPU nodes even when the hostfile lists four or five; an idle host does not make this a four-node configuration. Record the backend source identity, hostfile and predicted layouts, distinguish predictions from executed placement and capacity, and clarify authorization before probing below an explicitly bounded active-node range. Do not confuse a reservation limit with an occupied-node requirement.

**Subtract preserved sampling GPUs before selecting eligible training worlds.** Read the current source again when switching recipes; do not reuse an earlier recipe's counts. On eight-GPU nodes, 32 training plus eight sampling GPUs need at least five nodes; 32 training plus 16 sampling GPUs need at least six. Those total node counts can be valid even when a 40- or 48-rank training world is illegal. Conversely, SP64 training plus eight sampling GPUs needs at least nine nodes, so it is ineligible under an eight-node limit. The sum divided by slots per node and rounded up is only a placement lower bound: qualify actual placement, role-specific runtimes and capacity before claiming the minimum. Spare reserved GPUs are not permission to exceed the authorized active-node range.

**Use history to select the smallest useful probe, not a node-count grid.** For each smaller legal allocation, check static GPU and host-state feasibility with the 20 GiB reserve and identify any compatible fixed-target pass/OOM evidence. Skip an unchanged known failure. Reconsider a failing allocation only with a specific supported knob change that addresses the failed memory term; an OOM for one configuration does not exclude every configuration on those nodes. Start at the smallest unexcluded legal count, run two finite complete updates with the reserve, exclude update 1 from timing, verify all owned zones released, then move to the next legal count only when the result justifies doing so. A static estimate or successful model load is not qualification.

**An unavoidable transient can exclude smaller allocations independently of expert weights.** Derive tensor shapes and overlapping lifetimes from the actual attention/indexer implementation, using the pinned model dimensions and requested single-sequence shape. Include the live safety reserve and compare a lower bound, not a speculative full-model peak, against actual device capacity. For example, if an eager out-of-place operation must hold its input and output simultaneously, two such tensors plus the reserve can already exceed device memory before counting weights. EP changes or activation offload cannot remove that term. Record the implementation and shape evidence; do not extend this exclusion to a different backend, shorter packed rows or a future implementation with bounded tiles.

**Count the entire expression's live tensors and actual parameter storage dtypes.** Eager `scores = F.relu(scores * scale)` retains the old `scores`, the multiplication result and the out-of-place ReLU output until assignment: a two-tensor bound is valid but incomplete. Before increasing EP to compensate, add a conservative parameter-storage floor using the installed loader and dtype-cast behavior, not the training activation dtype or checkpoint byte count alone. A BF16 training recipe can preserve FP8 parameter storage and FP32 block scales. Check that EP divides both the training world and actual expert count; for 288 experts on world64, EP32 is legal but EP64 is not. A meta-model inventory can reject a layout without loading weights, but a floor below device capacity does not prove feasibility: optimizer buffers, activations, collectives and non-PyTorch allocations are still missing. Generic compilation or parameter offload is not an available escape unless the selected loader and EP runtime actually support those controls.

**Report an exhausted allocation range without inventing a winner.** If no candidate qualifies within the authorized node range, record the measured failures, analytical exclusions and untested supported alternatives separately. Say "no qualified configuration found" unless every legal layout is excluded by an unavoidable bound. Do not increase the allocation, remove the reserve, shorten the fixed target or drop a sampling sub-job to manufacture a pass. Preserve any previously qualified shorter configuration; in a multi-recipe assignment, record the unresolved fixed-target outcome before continuing to the next requested recipe.

**State how strongly the minimum is established.** Report the smallest tested passing count, lower counts rejected by topology or static feasibility, measured failed configurations, and any untested plausible alternatives. Claim a minimum only within the authorized range and supported layouts covered by that evidence, not across invented runtime changes or all possible tuning controls. Requalify source/runtime/checkpoint identity when the allocation changes. Once the fixed-target configuration is selected, use it as the seed for the later maximum-length search rather than interleaving two objectives.

## Refine a fitting target configuration

**This guide is the source of truth for search heuristics.** The [sequence-length tuning skill](../skills/seqlen-conf-tuner/SKILL.md) applies this method and records experimental evidence; trial runners execute selected configurations rather than maintaining a separate grid or knob-order policy. Put improvements to candidate selection here.

**Start from the supplied configuration and the existing trial history.** A long-length target usually already has most relevant memory controls enabled. Collect passing configurations, warm forward/backward timings, exact OOM configurations and failed phases, device and aggregate host-memory margins, and actual SP/EP group placement before proposing another trial. Reuse passing measurements only when the effective configuration, model/checkpoint, workload, hardware, runtime and timing diagnostics are compatible. Different-runtime results remain qualified planning evidence, not current ranking samples. Do not repeat a known OOM merely to rebuild the history; require a specific change that addresses its binding resource before reconsidering that branch.

**Reject impossible static host-state budgets before staging weights or launching a sweep.** With CPU Adam offload, count the master-weight partition, both moments and the persistent gradient partition using the installed runtime's actual dtypes and sharding. The installed DeepSpeed ZeRO-2 `initialize_optimizer_states` retains a gradient in the master partition's dtype on CPU; `DeepSpeedCPUAdam.step` allocates both moments lazily while that gradient and the master remain live. For FP32 masters, gradients and moments, the lower bound is 16 host bytes per trainable parameter, not 12. Use the actual expert-data-parallel groups to count replicas and partition ownership; SP does not automatically reduce this static floor. Compare each node's bound against physical RAM, cgroup limits and Ray's threshold, leaving room for nonexpert state, staging and activations. Disabling pinning or activation offload cannot eliminate these four CPU tensors. A bound exceeding the limit is a static-feasibility rejection, not a measured OOM or a sequence-length ceiling; obtain an authorized placement, allocation or precision change before probing length.

**Keep global batch size (GBS) at one in tuning experiments unless the user explicitly chooses another batch.** Here the engine counts packed microbatches, not the short source rows concatenated into a packed call. Keep one full target-length packed call globally and one optimizer update; do not add accumulation or duplicate the target across data-parallel (DP) groups when changing SP. DeepSpeed requires `GBS = microbatch_per_DP_rank * gradient_accumulation_steps * DP`, with `DP = active_world_size / SP`; see DSS [`_build_ds_config`](../../dss-platform/dss/ray_dss/jobs/gpu/training.py). With microbatch and accumulation both one, 16 active ranks at SP8 require GBS2, not GBS1. A GBS1 experiment needs a supported DP1 layout; reducing active ranks or changing the layout requires agreement on allocation scope and a fresh static GPU/host-memory check. Do not shorten the target, introduce zero-loss dummy calls, or relabel an engine GBS2 run as GBS1 to make a topology candidate appear legal. Record source rows, packed-call count, global tokens, engine batch fields and active GPU count separately.

**Choose a small local move that attacks a measured cost.** Use the cost ladder and subsystem descriptions above to match the dominant resource or latency term to a supported knob. If offload copies dominate, test increased GPU residency only with enough device margin. If recomputation dominates, relax checkpointing only when the saved activations plausibly fit. If repeated dispatches dominate, test a nearby larger DeepEP chunk within the transient and routing-skew budget. Do not explore optimizer placement when its static state cannot fit, tile a shared MoE expert to fix routed-expert memory, or toggle controls already in the desired state. Report estimates as estimates, not measured capacity.

**Refine logprob-head tiles independently of expert-dispatch chunks.** For an RL recipe using the [chunked logprob head](../arctic_platform/model/implementations/moe/layers/lm_head.py), count flattened rank-local tokens and vocabulary tiles in the actual implementation. Larger `fused_lm_head_token_chunk_size` can reduce repeated projection/reduction work without changing the loss, SP or expert dispatch. The FP32 score tile alone uses `token_chunk * vocabulary_tile * 4` bytes: with vocabulary tiles8192, token1024 uses32MiB and token8192 uses256MiB. This is only one live tensor, not the whole head's peak; include concurrent backward tiles, outputs and workspaces in the margin assessment, retain reserve20, and measure a nearby candidate. Stop enlarging when rank-local tokens already fit in one tile or a measured result gives no benefit. SFT and GRPO use different head/loss contracts: a fitting SFT configuration can inform memory planning for the same model, but cannot qualify an RL recipe's capacity or supply its ranking timing.

**Prune chunk sizes that cannot reduce the actual dispatch count.** Inspect the rank-local input to the routed-expert layer, not the global packed budget. The current [DeepEP chunk loop](../arctic_platform/model/implementations/moe/layers/moe.py) uses `ceil(local_tokens / chunk_size)`, with the maximum count agreed across the EP group. Once all ranks use one chunk, a larger chunk cannot remove another dispatch. For a balanced 16384-token local shard, chunk8192 uses two chunks and chunk16384 uses one; chunk32768 still uses one. Test the meaningful transition only when its larger receive/combine transient fits the estimated GPU margin, and stop increasing chunks after saturation or an unhelpful measured result. A smaller chunk can still be useful as a compensating control for another memory-saving or topology move.

**An allocator-pressure neighbor can justify one intermediate chunk, not a new sweep.** Chunk sizes need not be powers of two if the implementation supports the selected size. For example, a16384-token local shard takes eight dispatch chunks at2048, six at3072 and four at4096. If2048 is clean but4096 completes only with allocator-pressure warnings,3072 tests a specific compromise: fewer dispatches than the clean reference with a smaller transient than the pressure-affected candidate. Select it only after clean complete updates and a measured warm forward/backward improvement; retain the4096 capacity pass and its warning rather than turning it into an OOM bound. The [fixed-256K GLM results](../one-node-256k-tuning-results.md) document this measured example.

**Distinguish a per-chunk transient from retained state across chunks.** The [routed-expert loop](../arctic_platform/model/implementations/moe/layers/moe.py) retains chunk outputs until concatenation; autograd can also keep chunk intermediates live during checkpoint recomputation. A smaller dispatch chunk bounds an individual receive/combine allocation, not necessarily the sum of live blocks or the full-layer peak. If one justified chunk reduction still OOMs in the same phase, inspect a below-wall allocator snapshot before scheduling more reductions. Confirm offload coverage and compare concurrent allocations against the static floor; the line requesting memory at failure is not necessarily the largest consumer. Do not replace diagnosis with a descending chunk-size grid.

**Consider a topology change together with its compensating memory control.** On eight-GPU nodes, a cross-node SP16 configuration may be slower than a node-local SP8 configuration with activation offload, stronger supported checkpointing or a smaller dispatch chunk. Reducing SP increases token-shaped residency, so first identify which tensor would overflow and select a control that reduces that term; chunking does not solve resident checkpoint-boundary memory. The extra copies or recomputation can cost less than the inter-node collectives removed. An unchanged-knob SP8 failure does not reject this coupled candidate. Conversely, a known SP4 minimum does not freeze SP at four: SP8 may reduce local compute or transients enough to improve latency or remove another costly control. Verify group placement, batch legality and static state again rather than assuming that SP alone describes the experiment. Prefer one changed knob when it answers the question, but allow a small coupled move when either isolated change would OOM or miss the intended tradeoff.

**Prune configurations, not whole parallelism degrees without evidence.** A confirmed OOM rules out that configuration for the tested workload/runtime. Extend the exclusion only when the relevant memory term cannot decrease: for example, retaining still more activations cannot fix an activation-residency OOM with the remaining controls unchanged. Do not extrapolate an SP floor across a changed offload, checkpointing, EP layout or optimizer placement without checking the memory mechanism. Likewise, one slower SP8 recipe does not prove every SP8 recipe is slower; require a concrete new latency-saving mechanism before scheduling a different combination.

**A partial-checkpoint/offload host OOM needs a saved-tensor budget before another probe.** Boundary bytes alone do not bound the eligible internal saves, weight views, repeated copies or cache retention of uncheckpointed blocks. Do not repeat the failed configuration with only a smaller pinned-cache cap and assume active copies are capped. For a proposed `keep_last_n` change, estimate retained bytes from actual saved slots and their lifetimes, not a fraction of the decoder-layer count; confirm both GPU margin and host margin through the first optimizer update. Changing which layer types are checkpointed can be a different tradeoff, but requires its own recompute/residency analysis rather than a frequency sweep.

**Measure one warm forward/backward sample by default, never update 1.** For a new configuration or workload shape, run two complete updates: update 1 warms initialization/JIT/caches, and update 2 supplies the ranking sample. Time `/fwd-bwd` alone; execute optimizer `/step` separately for correct gradient reset and update qualification. Preserve cold timings for diagnostics but exclude them from every performance score and throughput denominator. Reuse compatible saved warm samples; do not rerun them to fill a preset sample count. With multiple valid warm samples, use their median and record count and range. A single sample has no measured variability; report that limitation. Add a few warm samples only for an unresolved tie or suspect timing, not a default five-update run or repeated fresh launches. A changed configuration or shape needs its own excluded warmup.

**Reassess after each selected trial and stop when no useful untested local move remains.** Before launching, record the exact changed knobs, evidence links, expected latency benefit, GPU and host-memory risks, and why the configuration is neither already tested nor excluded. Keep this rationale short and visible to the user. After verified cleanup, incorporate the result and choose the next move from the updated history; do not enumerate all SP/EP/offload/chunk combinations. Export the best qualified measured configuration with its original objective, not a global-optimum claim. Require a fresh two-update verification only when existing measurements do not already establish the selected configuration's qualification and runtime identity; do not repeat a verified unchanged winner just to complete a checklist. Report optimizer time and descriptive complete-update tokens/sec separately from the warm forward/backward score.

## Why longer packed sequences can improve throughput

**A longer packed sequence can improve tokens/sec, especially when optimizer time is significant and forward/backward cost per token stays roughly constant.** A complete training update includes both forward/backward and an optimizer update. The optimizer processes the model's parameters, gradients and state once per update, not once per input token, so its parameter-sized work can take approximately the same time at different packed lengths. More tokens in that update spread the optimizer cost over more useful work. The step can take longer while each token takes less time overall; this is higher complete-step throughput, not lower step latency.

**The packed length can increase without changing the engine microbatch size.** DSS concatenates multiple source samples into one `[1, packed_tokens]` model call. Packing 32 samples of 8192 tokens produces a 262144-token call; packing 102 samples of the same length produces an 835584-token call. Both can use engine microbatch size one, gradient accumulation one, and one optimizer update. The source-sample counts are not counts of microbatches: total packed sequence length is what changes.

**A simple cost model shows the amortization.** Let `N` be the actual global non-padding input tokens per update, `a` the approximately constant forward/backward seconds per token, and `T_optimizer` the approximately fixed optimizer seconds per update. With the same model, optimizer, allocation, parallelism and number of packed calls:

```text
complete_step_seconds ~= a * N + T_optimizer
seconds_per_token     ~= a + T_optimizer / N
tokens_per_second     ~= 1 / (a + T_optimizer / N)
```

Increasing `N` reduces the optimizer contribution per token. The benefit is especially visible with CPU optimizer offload, where a parameter-sized CPU Adam update can take tens of seconds; it diminishes once forward/backward dominates.

**The two opposite outcomes come from competing costs.** The earlier long-context measurement slows down because attention work per token grows; in the cost model above, `a` is then no longer constant. The Flash-Next comparison below has nearly constant measured forward/backward cost per token, so the falling `T_optimizer / N` term accounts for most of its throughput improvement. Extending the context each token attends to and increasing total packed tokens per update are distinct changes, even when the model-call batch dimension remains one. Neither optimizer amortization nor attention scaling alone determines the net result.

**The Flash-Next final runs illustrate this effect without an engine batch-size change.** Both ran on 16 H200s with `sp16`, `ep8`, one data-parallel group, engine microbatch size one and accumulation one. Every recorded update contained one packed model call and one optimizer update. The [Arctic Platform tuning results](../long-seq-tuning-results.md#timing-and-memory) record these warm medians, excluding the first update:

| Total packed tokens | Source samples | Forward/backward | Optimizer | Complete step | Complete-step input tokens/sec |
| --- | --- | --- | --- | --- | --- |
| 262144 | 32 x 8192 | 44.75 seconds | 40.28 seconds | 84.72 seconds | 3094.40 |
| 835584 | 102 x 8192 | 138.31 seconds | 40.77 seconds | 179.21 seconds | 4662.49 |

**Compare estimated common-token-update rates when both measured configs are available.** Use the [optimizer-only amortization estimate](#estimate-common-token-update-throughput) below to remove the different optimizer frequency per input token without running impractically large least-common-multiple accumulated updates. Keep the observed single-call rates in the table as measured evidence; the estimate is an additional reporting metric, not a new fixed-target ranking objective.

The longer packed call processes **3.1875 times** as many tokens, while the optimizer still takes about **40 seconds**. Its optimizer contribution falls from about **154 to 49 microseconds/token**. Forward/backward-only rates are much closer, approximately **5858 versus 6041 tokens/sec**, but complete-step throughput rises by about **1.51x**. The table's complete-step medians are computed from each update's summed durations; separate component medians need not add to the complete-step median.

**This is not a promise that the longest sequence is always fastest per token.** With dense attention, extending an individual sample increases quadratic attention work and can outweigh optimizer amortization, as the earlier `sp8·ep2` attention-dominated measurement shows. Packing more short samples can keep attention work per token approximately constant only when the backend actually isolates sample boundaries. Flash-Next's inspected QSA backend does not isolate packed rows; its measured runs are implementation stress tests, not independent-sample training certification. The two configs also differ in activation offload and dispatch chunk size, so this example is not a controlled sequence-length-only benchmark. Changes in offload, recomputation, routing or parallelism can offset the benefit; increasing tokens per optimizer update also changes training update frequency.

**Use the requested timing objective and report complete-step tokens/sec separately.** For fixed-target refinement, rank warm forward/backward time as described above unless the user requests another metric. To report complete-update throughput, count actual non-padding input tokens across data-parallel groups and accumulated microbatches once, not once per sequence- or expert-parallel rank. Divide by consistently measured warm forward/backward plus optimizer time, and report step latency, workload shape and memory margin alongside throughput. For an explicitly requested throughput objective with a flexible packed budget, test whether increasing occupied packed length reduces the optimizer cost per token before adding more memory-saving knobs.

### Estimate common-token-update throughput

**Use this optional estimate only with measured maximum-length and target-length configs.** Both workloads must have verified global non-padding input tokens and separate warm forward/backward and optimizer timings. Use the maximum workload's global tokens per update as the reference `N_ref`, and each workload's actual global tokens `N` to define `r = N_ref / N`. Use global work, not the sequence-length filename or SP rank count. Preserve measured single-call throughput and label the additional metric **estimated optimizer-amortized tokens/sec at N_ref tokens/update**.

```text
F = measured forward/backward seconds for one packed call
O = measured optimizer seconds for one update
equivalent seconds per original call = F + O / r
estimated tokens/sec = N / (F + O / r) = N_ref / (r * F + O)
```

**Divide only optimizer time, never the full update or forward/backward time.** For 256K versus 768K, `r=3`: a 40-second optimizer contributes 13.33 seconds per 256K call, but all of that call's forward/backward time remains. The estimate models three original forward/backward calls and one optimizer update. It assumes repeated calls and the one optimizer retain their measured costs; actual accumulation can change communication, memory residency and caching, so this is not a measured GAS3 result.

**Use paired warm samples and exclude update 1 unconditionally.** Compute `F_j + O_j/r` for each measured warm update `j`, take that duration's median, then divide `N` by the median. Do not add independently computed component medians. Report `N_ref`, `N`, `r`, warm count and runtime identity. A fractional ratio is an analytical normalization, not executable gradient accumulation: 835584/262144 is 3.1875, whereas an exact common integer update would need 51 and 16 calls, which this estimate does not run.

**The estimate corrects optimizer frequency, not every workload difference.** Check model/checkpoint, precision, optimizer, hardware, topology, safety margin, diagnostics and runtime compatibility before attributing a difference to configuration efficiency. Different attention contexts, packed-row isolation, offload and routing still change work per token. Keep historical estimates with their original measurements; a PyTorch or imported-source change requires new timings before claiming a current-runtime comparison. If either measured config or either timing component is missing, report the estimate as unavailable rather than extrapolating another length.

## Measured ceilings

Two reference points, both on 8xH200 nodes in bf16 with ZeRO-2, optimizer CPU offload, full activation checkpointing with CPU offload at `keep_last_n=1`, `tiled_mlp_token_chunk_size=16384`, and FlashAttention-3. Every figure is a binary search: the longest length that completes two steps, adjacent to the first that OOMs.

**Dense, Qwen3.8-27B** (64 layers, hidden 5120, 24 query / 4 KV heads, vocabulary 248320), one node, `sp8·ep1`. The three rows differ only in how the head computes the loss.

| --- | --- | --- | --- | --- |

| Chunked logprobs, `16384 x 8192` | 1.67M | 116.07 GiB | 179.59 GiB | host RAM |
| Liger fused cross-entropy | 1.67M | 109.96 GiB | 175.52 GiB | host RAM |

Per 1,000 rank-local tokens the unchunked head costs about 2.80 GiB of GPU total, of which 2.53 GiB is the logits tensor and its gradient. The other two rows cost 0.30 GiB and 0.27 GiB, so the card is no longer the limiter for either -- both stop at the same 10K-wide bracket against node RAM, with about 20 GiB of the card unused.

## What the two offloads move to host

Both offload knobs buy GPU memory with host RAM, and host RAM is a wall of its own rather than free space: every rank on the node draws from one budget, with a cgroup limit near 1900 GiB against 2 TB physical. Exceeding it kills the job as surely as filling the card, which is what "host RAM becomes the new wall" in the ladder means.

The two terms behave differently, and that difference is why they are worth separating. Optimizer state is fixed by the parameter count and the sharding, so it does not move with sequence length. Activation boundaries scale with tokens per rank until the pinned staging cache hits its retention cap, and then they plateau.

### Qwen3.8-27B dense, one 8xH200 node, sp8·ep1

Per-rank figures are measured; the per-node column is eight ranks of them.

| Term | Host per rank | Host per node | Measured at |
| --- | --- | --- | --- |
| Optimizer offload -- ZeRO-2 Adam state on CPU | 43.8 GiB | 350 GiB | flat across 500K to 680K: 43.55, 43.63, 43.72, 43.81 GiB |
| Activation offload -- 64 block boundaries at `keep_last_n=1` | 135.8 GiB | 1086 GiB | the difference at 1.0M to 1.67M, where the pinned cache has plateaued |
| **Both** | **179.6 GiB** | **1437 GiB** | 179.48 at 1.0M, 179.58 at 1.5M, 179.59 at 1.67M; 1.68M is a host OOM |

The optimizer figure is close to what the arithmetic predicts: Adam keeps an fp32 master weight plus two fp32 moments, 12 bytes per parameter, and ZeRO-2 shards that over the 8-rank group, giving `27e9 x 12 / 8` = 37.7 GiB. The measured 43.8 GiB is that plus pinned staging buffers and the process itself.

The activation term is the one that stops growing. It rises at about 5.3 GiB per 1,000 rank-local tokens and then flattens at ~179.6 GiB per rank, unchanged from 1.0M to 1.67M, because `pin_memory_max_size_gib` caps what the staging cache retains rather than letting it track the sequence.

### Qwen3.6-35B-A3B MoE, one 8xH200 node, sp4·ep2

Per-node figures are measured here; the per-rank column divides by eight.

| Term | Host per rank | Host per node | Measured at |
| --- | --- | --- | --- |
| Neither offload | negligible | negligible | ceiling is ~32K tokens |
| Optimizer offload -- ZeRO-2 Adam state on CPU | 62.5 GiB | 500 GiB | at its ~790K ceiling; constant in sequence length |
| Activation offload -- per-layer boundaries at `keep_last_n=1` | 94.5 GiB | 756 GiB | the difference at 1.17M |
| **Both** | **157 GiB** | **1256 GiB** | against a ~1900 GiB node limit |

The optimizer term is larger per rank than the dense model's despite a similar parameter count, because expert parameters do not shard over all eight ranks. `ep_size=2` halves the expert weights a rank holds, but their optimizer state is then sharded only across the expert-data-parallel replica group, which at `sp4·ep2` is four ranks rather than eight. Raising `ep` does not reduce this in the way the parameter count suggests.

### Reading these against the node limit

Two cautions before using the totals as a budget. The per-node column sums the ranks' resident sets and is a **lower bound** on what the node is using: at the dense model's 1.67M ceiling the sum of ranks is ~1437 GiB while the node itself measured ~1902 GB of 2000 GB, the remainder being the Ray object store, page cache, and everything else on the box. And the two terms are not independent budgets -- they compete for the same cgroup allowance, so the question at the wall is whether their sum plus that overhead clears the limit, not whether either fits alone.

The practical consequence is that on a long dense run the host term is dominated by activation offload by roughly three to one, so `pin_memory_max_size_gib` and `keep_last_n` are the knobs that move it. On the MoE model the split is closer to two to one, and the optimizer half of it cannot be reduced by any setting in this guide short of a different ZeRO stage.

### Splitting the boundaries between the two walls

The choice is not all 64 boundaries on the card or 63 of them on host. `keep_last_n` is where the set divides: a boundary is offloaded only once `keep_last_n` newer ones exist, so the N most recent stay resident and everything older streams out. Raising it hands bytes back from the host budget to the card one boundary at a time, and the offload keeps working on the rest.

One boundary is `tokens_per_rank x hidden x 2` bytes. On the dense 27B at its 1.67M ceiling a rank holds 208.75K tokens, so a boundary is `208750 x 5120 x 2` = 1.99 GiB on the card against 135.8 GiB per rank on host for the 63 that leave. That run's GPU peak is 109.96 GiB of a card's ~130, so about ten boundaries fit in the headroom -- 19.9 GiB per rank back onto the cards, 159 GiB per node off a budget whose limit is ~1900 GiB. Take fewer than the headroom allows: the resident boundaries add to the peak that measured 109.96, so claiming all of it puts the card back at the wall it was moved away from.

That arithmetic bounds the trade rather than predicting it. The card side is exact -- the boundary shape is known. The host side falls by at most the bytes no longer offloaded, and by less where the pinned staging cache is retaining to its capacity cap rather than tracking live boundaries, which is what the flat 135.8 GiB from 1.0M to 1.67M shows.

Step time does not pay for it. The resident boundaries are the ones backward reaches first, whose offload-then-immediate-reload is pure latency; keeping them removes a copy pair instead of adding one.

Which way to move it follows from which peak is closer to its limit: raise `keep_last_n` when the host figure times the ranks approaches the node limit and the card has room, leave it at 1 when the card is binding.

## Finding max seqlen for a given model

Follow these steps:

1. Run the target length once with the `step_peak_memory_log` field on and read both peaks. If the GPU peak is near 126-130 GiB the card is binding; if the host figure times the ranks approaches the node limit, host RAM is.
2. Split the binding peak with the `DSS_MEM_BREAKDOWN=1` environment variable. A large optimizer-state term means optimizer CPU offload; a large activation term means `ep_size`, activation offload, tiled MLP and `sp_size`.
3. Binary-search an established pass/OOM bracket rather than stepping toward the wall. Two passing points give a slope in GiB per 100K tokens; project the wall from it, overshoot, and bracket. Stop when the gap is at most **4096 tokens (4K)** if the largest passing length is **below 32768 tokens (32K)**, or **8192 tokens (8K)** at 32K and above. A bracket crossing 32K retains 4K resolution until a passing bound reaches 32K. Round to valid packing/SP/kernel alignment, avoid duplicate probes and do not bisect further unless the operator requests finer resolution. Record both endpoints and the resolution, then freshly qualify the passing endpoint with five complete updates and the unchanged safety buffer. An alignment that prevents the required resolution is not a completed bracket.

**An explicit NCCL CUDA allocation failure is a GPU-memory bound; a generic collective error is not.** NCCL can report `ncclUnhandledCudaError` with `Cuda failure 2 'out of memory'` when its own CUDA allocation fails, without a PyTorch allocator exception. Require that explicit allocation-error evidence; do not infer OOM from a timeout, illegal-memory-access error or generic NCCL failure. Preserve the raw result and any previous classification. If teardown failed, independently recover the exact owned zone, record process-exit acknowledgments and idle GPUs on every node, then reuse the confirmed OOM rather than repeating it. A corrected classifier must not silently erase a historical cleanup failure.
**A final-verification OOM supersedes an earlier pass at that length, even when both runs requested five updates.** Preserve every completed update and the raw failure, verify whole-allocation release, and use the failed length as the new upper endpoint with a compatible lower passing trial. Refine only if the new gap exceeds the stopping resolution, then repeat final verification; do not export the failed candidate, repeat its known OOM, or remove the reserve. A final candidate can have a different source hash because its length limits were pinned before submission. Reuse that failure only after verifying both original source hashes, exact equality after the documented length-only transformation, the buffered effective payload, runtime, loss, controls and workload. Any other control or sampling-subjob change requires a separate configuration history.

**Select the lower seed explicitly after a final-verification failure.** In the existing [full-recipe capacity launcher](../tuning/full_recipe_capacity_stas_dev_7.sh), set `TUNING_CAPACITY_SEED_RESULT` to the compatible lower passing result, `TUNING_CAPACITY_FAILURE_RESULT` to the failed final result, and `TUNING_CAPACITY_PROBE_STEPS` to the required qualification duration. Supply the historical root as the second positional argument, but omit the third positional resume root: ordinary resume selection can choose the superseded search pass at the failed final length and override the explicit lower seed. Qualify both endpoints, unchanged runtime and whole-allocation release before submission, retain fresh idle keepalive receipts, and preserve the existing stopping resolution and fresh-final export gate.

**Match capacity-probe duration to an observed late-update failure.** If a candidate passes two updates but final verification OOMs later, two-update passes no longer establish feasibility for that history's required duration. Use five complete updates for subsequent probes when the failure occurred within the five-update final run. Requalify a shorter historical passing seed at the longer duration before accepting it as the lower endpoint, even when the old bracket already meets the stopping resolution. Keep shorter passes as planning evidence, preserve every confirmed OOM, and retain the same reserve, loss, workload and runtime. A failed seed requalification leaves no qualified lower bound: choose a compatible lower candidate rather than refining against the invalid short pass. This is a capacity-validation correction, not a default five-update performance sweep; update 1 remains excluded from every timing score. Stop bisection at the existing 4K/8K resolution, then apply the unchanged final-export gate.

**Requalify one historical seed without starting expansion.** The existing [full-recipe capacity launcher](../tuning/full_recipe_capacity_stas_dev_7.sh) accepts `TUNING_CAPACITY_REQUALIFY_STEPS=5`, `TUNING_CAPACITY_SEED_RESULT=/path/to/historical/result.json` and `TUNING_KEEPALIVE_RECEIPTS=/path/to/fresh/receipts`. Select the same prepared interpreter through `TUNING_RUNTIME_PYTHON`. This mode requires fresh allocation-matched idle-GPU receipts, preserves the measured source, runtime and controls, then runs the historical length through the full recipe and checks runtime-after and the required update count. It stops without expansion or export. Do not combine this mode with resume, first-probe or reused-failure arguments. An operator must still refresh keepalive during long active waits before the recorded deadline.

4. Pin every knob explicitly in the recipe, including the ones at their defaults. `deepep_token_chunk_size` defaults to unchunked and `fused_lm_head_token_chunk_size` to unset, so a recipe that omits them is not the configuration it looks like.

## If the knobs aren't enough to meet the required seqlen

What happens if all the knobs are on and you're still struggling with reaching the target seqlen.

Often times this could be an indication of a bug where one or more of the knobs are configured but misfire.

But more likely there is some inefficient code that needs a very large gpu peak memory. For example, manifesting full logits is one such example and we already have knobs to overcome it. The next thing to do to dianose the issue is to run your code under torch cuda memory profiler while keeping your seqlen short enough so that you don't get OOM, generate the memory profiler trace and then study it and fix the code in question.

The following sections will guide you through the process.

### Reading the memory allocator profiler

DSS is already instrumented to run the memory profiler, so it just needs to be enabled.

- `step_peak_memory_log` reports the peak GPU and host figures, which settles which wall is binding.
- `DSS_MEM_BREAKDOWN=1` splits the GPU peak into parameters, gradients, optimizer state, activations and allocator slack, which settles which category is large. Neither names a line of code, so when the binding category is activations and every knob left on the ladder costs step time, the open question is which tensor. That is the one the allocator profiler answers, and it is how a submodule that allocates a single oversized buffer gets found and fixed.

Reading its output takes the allocator's own vocabulary, because the quantity the card limits is not the one the model asks for. PyTorch does not go to the driver per tensor: it reserves large **segments** and carves **blocks** out of them, reusing a freed block for the next request that fits. **Allocated** is the bytes that live tensors hold. **Reserved** is the bytes those segments hold from the card, and reserved is what runs out -- an OOM is the allocator failing to obtain another segment, which can happen while allocated still has room. The gap between the two is slack: freed blocks not yet reused, plus holes the wrong size for what is being asked for next. Keeping that gap small is what `expandable_segments:True` is for.

A snapshot records that machinery instead of summarizing it. With history enabled the allocator keeps a ring buffer of every allocation and free, each tagged with the Python stack responsible, and the dump writes that history together with the current segment layout into a pickle. Both halves are load-bearing. The history is a timeline, which locates a peak that a short-lived transient sets -- a per-step maximum reports only its height, never where in the step it happened. The layout is a map, which shows fragmentation directly rather than leaving it inferred from a reserved-minus-allocated gap.

The worker wires all of this to `DSS_MEM_SNAPSHOT`, and the rest of this section is the workflow: turn recording on, collect the pickle from the one rank that writes it, and read the plots it supports.

### Turning it on

Set these on the gateway or launcher process; `worker_env()` forwards the whole family to every worker.

```bash
DSS_MEM_SNAPSHOT=/some/shared/path   # path prefix; setting it is what enables recording
DSS_MEM_SNAPSHOT_RANK=0              # default 0 -- one rank records, not all of them
DSS_MEM_SNAPSHOT_ITERS=3             # default 3 -- dump after this many completed fwd/bwd
DSS_MEM_SNAPSHOT_ENTRIES=200000      # default 200000 -- ring buffer of allocation events
DSS_MEM_SNAPSHOT_STACKS=python       # default python -- C++ frames are noise at this level
```

Recording starts at the first `/fwd-bwd`. After `DSS_MEM_SNAPSHOT_ITERS` completed iterations the worker writes `<prefix>-rank<N>.pickle`, stops recording, and logs `[mem-snapshot] dumped`. Run it **below** the wall: the dump is triggered by a completed iteration, so a job that OOMs never produces one. For the OOM itself the failure path emits its own allocator snapshot without any flag, which `dss-platform` [`docs/memory_diagnostics.md`](https://github.com/snowflake-eng/dss-platform/blob/main/docs/memory_diagnostics.md) describes.

**Dump before a known late-update failure without weakening capacity qualification.** If update 3 OOMs after two complete updates, use a two-update diagnostic and dump at iteration 2, rather than waiting for the failing iteration to trigger a snapshot. The existing [full-recipe capacity launcher](../tuning/full_recipe_capacity_stas_dev_7.sh) accepts `TUNING_CAPACITY_MEMORY_DIAGNOSTIC=1` with an explicit historical `TUNING_CAPACITY_SEED_RESULT`, prepared `TUNING_RUNTIME_PYTHON` and fresh idle `TUNING_KEEPALIVE_RECEIPTS`. It preserves the full recipe, single-row workload, loss, source length, runtime and 20 GiB reserve; captures rank-0 history with four million entries; and checks both updates, all-rank reserves, runtime-after and all-node release. Its `diagnostic-controls.json` marker prevents importing the trial as a capacity seed or failure endpoint, and it neither expands nor exports. Do not combine this mode with search/resume or seed-requalification arguments. Inspect the actual failing rank before selecting rank 0; another rank needs an explicitly adapted diagnostic. Counter-only automatic failure snapshots do not supply allocation stacks. Ordinary capacity probes still require the demonstrated late-failure duration, and profiler-on timing is not performance qualification.

### Viewing the trace

**Capture the failing rank and preserve the failed chunk control in a below-wall diagnostic.** Resolve the failed Ray worker PID to its logged global rank; CUDA device0 alone does not imply rank0. The existing launcher accepts `TUNING_CAPACITY_DIAGNOSTIC_RANK` (default0, checked against the training world) and can retain `TUNING_CAPACITY_EXPERT_CHUNK_SIZE` in diagnostic mode without seed-requalification arguments. Select an explicit shorter historical reference that completed two updates, preserve its remaining controls, and verify the transformed candidate before interpreting the snapshot. The historical result supplies controls, not a capacity endpoint for the changed chunks. Require the selected rank's snapshot, two finite updates, all-rank reserves, matching runtime-after and all-node release. Diagnostic snapshots and timings never qualify capacity or performance; ordinary probes still require the demonstrated longer duration.

Drop the pickle on <https://pytorch.org/memory_viz>, or render it locally:

```bash
python -m torch.cuda._memory_viz trace_plot   snap-rank0.pickle -o trace.html
python -m torch.cuda._memory_viz segment_plot snap-rank0.pickle -o segments.html
python -m torch.cuda._memory_viz compare      before.pickle after.pickle -o diff.html
```

`trace_plot` draws allocated memory over time and attributes every block to the Python stack that allocated it, which is the view that names the offending module. `segment_plot` shows how those blocks pack into allocator segments, which is where fragmentation is visible rather than inferred. `compare` flamegraphs what changed between two snapshots -- the direct way to confirm a knob did what it claimed instead of trusting a peak number that moved for another reason.

If <https://pytorch.org/memory_viz> crashes, when the trace is 1GB or higher, use this tool instead https://github.com/Da1sypetals/SnapViewer

### What to look for

- **A tall narrow spike.** One allocation, briefly held, that sets the high-water mark by itself. The stack names the module, and a shape of `[tokens, something-wide]` marks it as a chunking candidate. The lm-head logits tensor and the fp32 MoE combine transient both look like this.
- **A term that does not shrink when you shard.** Snapshot at two `sp_size` values and `compare` them. Whatever is unchanged is not token-parallel -- parameters, optimizer state, or a buffer sized by the model rather than the batch -- and no activation knob will move it.
- **A wide plateau instead of a spike.** Memory resident across the whole backward is saved state, not a transient. That is the activation-offload case; `DSS_ACT_OFFLOAD_LOG=1` then confirms whether the hooks are actually covering it.
- **Reserved sitting far above allocated.** Fragmentation rather than demand. Confirm `expandable_segments` is on before spending a knob on it.

Recording timestamps every allocation and walks a Python stack for each one, so it costs step time. Treat throughput measured with a snapshot running as indicative, and re-measure with it off.

**Check history coverage before attributing a peak.** The event history is a bounded ring: reaching `DSS_MEM_SNAPSHOT_ENTRIES` can evict earlier allocation stacks even though the final segment map still contains live blocks. Record the retained timestamp window and distinguish unattributed pre-history blocks from allocations with known stacks. A replay must include blocks awaiting stream completion until `free_completed`, and account for allocator block rounding; do not treat `free_requested` as immediate device-memory release. Compare the reconstructed peak against the logged allocator peak, but do not claim complete-step attribution from a truncated window or use a smaller diagnostic length as target qualification.

**Distinguish a multiplication temporary from the tensor autograd retains for backward.** Smaller expert chunks can limit each FP32 allocation while retaining FP32 activation casts for many chunks until backward. When allocator stacks support this diagnosis and implementation changes are authorized, AP's [routing-weight helper](../arctic_platform/model/implementations/moe/routing_weights.py) saves the original activation and routing scores, recomputes their FP32 casts in backward, and preserves the original FP32 multiplication and score-gradient reduction. Both score-before-expert and score-after-expert sites in [UCCL](../arctic_platform/model/implementations/moe/distributed/ucclep.py) use the helper; communication and expert dispatch are unchanged. Require forward/gradient reference parity at both sites and an actual CUDA retained/peak-memory check with the 20 GiB reserve before full-model qualification. An isolated memory reduction neither predicts the full-model peak nor proves a new length fits.

**Requalify a routing implementation correction through the existing launcher, without old bounds.** For GLM RL, `TUNING_CAPACITY_RUNTIME_REQUALIFICATION=1` with `TUNING_CAPACITY_REQUALIFY_STEPS=5` accepts a completed, independently qualified allocator diagnostic as a controls reference only. Supply that diagnostic's exact baseline result and candidate, the prepared interpreter and fresh allocation-matched idle receipts. The launcher checks every node's runtime, allowing only the corrected AP UCCL source and newly tracked routing helper to differ; model, roles, packages, transport and DSS sources must match. It records the source hashes, assigns a new runtime identity, removes profiler controls and runs five ordinary full-recipe updates at the diagnostic's measured length, preserving all training controls and the 20 GiB reserve. It does not search, export or import diagnostic endpoints. Require unchanged runtime-after and all-node release before using a successful fresh result as a new capacity seed.

**Use the routed-expert chunk control for a diagnosed combine transient, including UCCL.** The shared [MoE routed-expert path](../arctic_platform/model/implementations/moe/layers/moe.py) applies `deepep_token_chunk_size` before dispatch for both DeepEP and UCCL; the name does not restrict the control to DeepEP. An unset value dispatches the entire rank-local token window. When allocation stacks identify large FP32 routing-weight multiplication or its gradients in [UCCL combine](../arctic_platform/model/implementations/moe/distributed/ucclep.py), test a smaller positive token chunk while preserving the model, workload, EP/SP, precision and reserve. Check the AP transport and typed loader options, then qualify the full recipe at the required probe duration. Smaller chunks add dispatch calls and do not guarantee uniform routed-token counts. A truncated rank-0 trace can justify a candidate, but cannot prove another rank's earlier OOM allocation came from the same operation. Changed chunk controls require fresh capacity bounds; do not inherit an unchunked OOM endpoint.

**Record the exact controls reference when qualifying an expert-chunk refinement after a late OOM.** Use the existing full-recipe launcher with `TUNING_CAPACITY_EXPERT_CHUNK_SIZE` and `TUNING_CAPACITY_REQUALIFY_STEPS=5`, fresh allocation-matched idle receipts, and the prepared interpreter. A superseded short pass may reconstruct the source configuration, workload and runtime only after its later failure and cleanup are independently qualified; it cannot supply a passing capacity endpoint. The launcher records `historical_reference_result` and labels that history as a reference rather than a new bound. Preserve every other control from that exact source, including its reduction bucket or verified omitted default. Returning to an earlier source after a failed bucket refinement does not retain the smaller bucket. Inspect the new failure stack: a routed-expert FP8 unpadding OOM is not evidence that the previous FP32 combine or gradient-reduction allocation failed again. Require five fresh finite updates before establishing the changed configuration's bounds; if one justified chunk reduction still fails, follow the retained-state diagnostic rule above instead of sweeping smaller chunks.
