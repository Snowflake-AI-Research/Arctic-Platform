# Fixed-Length Performance Tuning

**Optimize normalized tokens/sec at the requested length, not the longest length that fits.** Start from a known fitting config. Keep model weights, precision, loss, optimizer semantics, hardware and input lengths fixed. Default to complete-step throughput; honor an explicit step-latency objective while still reporting tokens/sec. Do not reuse maximum-capacity timings as the fixed-length baseline.

## Workload And Timing

**Define what the target length means before comparing candidates.** An individual sequence, total request tokens and per-data-parallel-group packed tokens are different quantities. A data-parallel (DP) group receives a share of request rows; sequence parallelism (SP) splits each group's packed call across its ranks. At fixed world size, `dp=world/sp`. Decreasing SP while filling each group to the same packed budget increases global tokens per update. Such step times are not equal-work comparisons.

**Keep the requested per-group packed length full when optimizing that length.** Send `target_tokens * dp` global non-pad tokens, with equal short-row lengths, balanced rows on every DP group, aligned local token widths and no zero-loss padding calls. Global tokens per update grow with DP, so rank normalized complete-step tokens/sec by default and report both batch work and step latency. If the user explicitly requests latency, rank complete step time instead. Neither objective is an equal-global-work comparison. For an individual-sequence target, never shorten rows to accommodate more DP groups.

**Use fixed-global work as a separate comparison, not a substitute for the target workload.** Send identical total non-pad tokens, short-row lengths, request row count, seeds and loss boundaries across candidates. Record global tokens, per-group packed tokens, local tokens and model-call count. At fixed world size, this comparison keeps local tokens approximately constant as SP falls and therefore does not test spending GPU memory on longer local shards. If packed rows are not isolated, the per-group context also shrinks: equal token count then does not imply identical attention work. Never silently mix full-target and fixed-global timing tables. If the user explicitly defines a fixed-global-batch objective, rank that workload instead and separately qualify promised per-group capacity.

**Check the scope of reported packing metrics.** Current DSS aggregation retains `sft_model_calls` and `sft_packed_rows` from worker 0, not every worker. Verify the DP split through the actual dispatcher and its tests, then use those metrics as a runtime worker-0 check. Do not claim that a worker-0 count observes all DP groups.

**Rank by normalized complete warm-step throughput unless latency is explicitly requested.** Add forward/backward and optimizer durations for each update, then divide actual global non-pad input tokens per update by the median warm complete-step duration. Follow the [shared normalization rules](../SKILL.md#deliver), including counting SP/EP copies only once and labelling the statistic. Separate initialization and the first update's JIT/cache effects. Use at least one warm feasibility measurement; remeasure close candidates with more warm steps before deciding. Report tokens/sec, global tokens per update, median seconds/step and timing spread together. HTTP-client timing includes endpoint overhead; keep the same measurement method across candidates. Never rank by forward/backward alone or reduce the optimizer-update workload to obtain a speedup.

**Include TFLOPS when a supported existing estimator is available.** Follow the [shared throughput, timing and FLOPS reporting requirements](../SKILL.md#deliver); report estimator scope and availability in the candidate table and final result. Estimated TFLOPS supplements normalized complete-step tokens/sec and latency; it does not replace the requested ranking metric.

## Search Algorithm

1. Measure the fitting baseline with every DP group at the requested length. Capture total NVML device used/total/free, allocator allocated/reserved peaks, aggregate host/cgroup memory, finite losses and gradient norms, successful updates and cleanup.
2. Step SP down through legal divisors, for example 16, 8, 4, 2, 1. Keep EP fixed initially and reconcile DeepSpeed engine batch size at every change. Crossing from inter-node to node-local SP is particularly worth measuring. Do not stop at the first slower point: topology boundaries and kernel shapes can make the curve non-monotonic. Reject illegal topologies before loading weights.
3. On the best fitting SP candidates under the requested metric, spend GPU headroom on one change at a time: disable activation offload; relax checkpoint frequency or use supported selective checkpointing; increase DeepEP dispatch chunks, for example 1024, 4096, 8192 or unchunked; remove optimizer offload only if static GPU state can fit. If fully resident activations do not fit, try partial residency with `keep_last_n`, using measured saved-tensor roles rather than assuming one eligible tensor per decoder layer. This can reduce host pressure and copies without retaining every activation. Retain fused/tiled vocabulary projection. Offload requires full checkpointing, and routed MoE recomputation requires router replay. Do not assume a model supports the guide's generic checkpoint targets.
4. Test a nearby SP degree again after a promising memory/performance change. SP and offload/checkpoint settings interact; a one-dimensional SP sweep is not a global optimum. Test lower legal EP only when resident expert weights plausibly fit and dispatch cost is material. Keep the requested GPU allocation unless the user authorizes changing it.
5. Keep a table of candidates, their exact knobs, full-target warm complete-step tokens/sec and times, global work, feasibility/memory margin and failures. A useful five-update probe has three full-target updates (first cold, next two warm) followed by two fixed-global comparison updates (first changed-shape warmup, second warm). Explicit GPU/host OOM eliminates that candidate, not the target length; diagnose other failures separately. After each trial, require verified release on every node before proceeding. Stop a finite local search once legal SP alternatives and useful nearby knob variants have been measured, or an explicit user/execution cap is reached. Describe the result as best measured under the requested metric, not globally optimal; do not relabel an earlier latency winner as a throughput winner.
6. Verify the winner in a fresh job for five total complete steps at the full requested per-group length, using strictly pad-free data and clean timing settings. Do not add another five-step comparison phase. Exclude the first update from warm timing. Export exactly the measured config to the repository root with a hyphen-separated filename containing the total allocated GPU count as `<count>gpus`, following the [shared export requirements](../SKILL.md#deliver). Preserve the original envelope and maximum-capacity recipe, and record runtime dependencies and the full absolute output path in the report's TLDR and final response.

## Diagnostics

**Diagnostic timings are not final performance timings.** Reuse existing `DSS_MEM_LOG`, `DSS_MEM_BREAKDOWN`, `DSS_MEM_STAGED`, `training_memory_telemetry` and `step_peak_memory_log` controls for diagnosis. Disable expensive synchronized staged/breakdown/telemetry probes and allocator snapshots during clean timing comparisons. Keep the cheap per-step peak response and the same NVML sampling interval for all candidates. Record which diagnostics were enabled. Do not invent new memory variables or counters.

**Unset presence-gated debug flags instead of setting them to `"0"`.** DSS's debug memory helpers check for a nonempty environment value; `"0"` therefore enables those helpers. Remove the variables from the clean timing environment and explicitly disable structured `training_memory_telemetry`. Verify the exact imported implementation because other controls may parse boolean strings differently.

**Unused GPU memory is a performance opportunity, not a success metric.** Report total device usage before allocator usage, including sampled NVML peaks and observed margin. Allocator reserved-minus-allocated is cache/slack; device-used-minus-reserved is an approximate same-instant residual outside PyTorch. Host OOM can still bind with GPU headroom. Increasing GPU residency may remove offload copies, but qualify it through complete updates before calling it an improvement.

**A completed forward/backward call is not a passing performance candidate.** The first optimizer update may allocate host state and cross Ray's node-memory threshold. Record the failed phase and any completed call duration, but leave complete-step timing unavailable when no optimizer update succeeds. An observed low GPU peak before a host OOM does not predict the GPU peak of an uncompleted backward or optimizer phase.

**Resume completed-but-unrecorded candidates without rewriting evidence.** A sweep can exit after saving `result.json` but before saving its progress entry, especially when cleanup verification fails. Validate the saved candidate envelope and effective payload, raw source SHA256, runtime identity, GPU/SP/EP degrees, target budget and request shape against the resumed candidate before adopting the result. Require an explicit OOM for capacity failures. Recover only the exact owned zone and obtain fresh process-exit and idle-device acknowledgments on every node. Save that acceptance separately with the original result hash; preserve the failed cleanup result and recovery log. Missing or mismatched artifacts are not permission to overwrite or rerun a known OOM.

**Keep backend correctness limitations visible.** Current Flash-Next QSA does not isolate packed rows. Its short-row packed stress tests can compare implementation performance with controlled shape, but cannot establish independent-sample correctness or expected short-row attention scaling. Do not change the attention algorithm, precision or pretrained weights merely to win a timing comparison.

**Check vocabulary-sharded lookup with rank-distinct IDs.** The [Flash-Next lessons](flash-next.md) record a demonstrated PLE embedding error under distinct EP inputs. Finite training metrics do not certify model correctness. A backend repair changes runtime identity and needs fresh timings rather than reuse of pre-repair results.

**Measure topology rather than inferring it from SP degree.** With world16, EP8 and eight GPUs per node, current `auto` selection uses contiguous decoupled SP groups for degrees 16, 8 and 4. SP2 instead selects node-local EP with cross-node SP pairs `[0,8]` through `[7,15]`; SP1 uses standard EP without SP collectives. Thus stepping from SP4 to SP2 does not necessarily reduce network communication. Verify the imported topology helpers and startup group logs.
