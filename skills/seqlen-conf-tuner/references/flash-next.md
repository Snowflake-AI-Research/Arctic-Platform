# Flash-Next Tuning Lessons

These observations come from `Qwen/Qwen3.8-Flash-Next`: two-node capacity tuning on `stas-dev-2`, two-node fixed-length performance tuning on `stas-dev-3`, and single-node feasibility probes on `stas-dev-5`. Each node has eight H200 GPUs and about 2000 GiB host RAM. The maintained [results document](/code/users/stas/github/sf/stas-dss-repro/arctic-platform-qwen38-flash-max-len/long-seq-tuning-results.md) holds trial evidence and the current verification status. The `arctic-platform` [long-sequence guide](../../../docs/long-seqlen-tuning-guide.md) remains the foundation.

## Runtime Lessons

- FA3 installed and imported successfully, but the Flash-Next loader rejected the generic `flash_attention_3` backend before weight loading. This model requires `qsa_flex` or its `flex_attention` alias.
- An explicit JSON null is not stable across DSS transport: the gateway omits nulls, and the zone's schema parse reinstates the generic FA3 default. Pin the supported backend.
- Training via `python -m` imported the working checkout while a file-execution probe imported an installed wheel. Package metadata alone does not establish imported-source provenance.
- Multi-node setup nested another all-node optimizer build and raced on shared extension directories. Provision locally when the caller already fans out, serialize warmup, preserve interrupted directories, and warm both Fused Adam and CPU Adam. Preserve H200/B200 architecture-specific package branches.
- Select an isolated tested OFI plugin through the launcher environment rather than replacing libraries during an active bracket. Check the plugin actually selected in NCCL logs and capture its binary hash.

## Workload Lessons

**Tokenizer metadata can define padding even when model metadata does not.** The pinned checkpoint's model config has null pad IDs, but its tokenizer maps `<|endoftext|>` to pad ID `248044`. Sampling uniformly from the whole vocabulary can therefore introduce padding IDs into an apparently full-length random row. Exclude the runtime tokenizer's pad ID explicitly and audit every request.

**Packed budget and individual context are different measurements.** A 835584-token configuration can receive one long row or 102 short input rows of 8192 tokens. The second workload fills the same packed budget; independent-sample semantics require boundary-aware attention and recurrent-state resets. Send rectangular `[102, 8192]` tensors with all-ones masks. The total is divisible by CP16, so DSS inserts no divisibility-padding positions. Verify backend isolation, actual packed-row counts and model-call occupancy; finite loss alone does not prove row isolation. Do not present packed throughput as evidence of individual-context speed.

**The inspected QSA backend does not isolate packed rows.** `select_qsa_token_ids` masks future physical blocks, not blocks from earlier samples; `_qsa_indexer_forward` compresses global keys without segment boundaries. The context-parallel backbone reconstructs boundaries only for GatedDeltaNet. Row-local rotary positions do not fix sparse routing. PLE cross-rank convolution boundary handling is another unverified property. A pad-free 102-row run is therefore a packed stress test, not evidence of independent-sample correctness or the expected independent-short-row attention speedup. Model-backend changes are outside this config-tuning run.

**The current EP-sharded PLE lookup fails rank-distinct ID equivalence.** On `stas-dev-3`, a two-rank CPU/Gloo check of the actual `EPShardedEmbedding` passed the identical-ID control but mismatched all 12 elements per rank with distinct IDs. The implementation masks rank-local IDs against a vocabulary shard and elementwise all-reduces outputs; that requires identical IDs at corresponding EP positions or equivalent gather/scatter handling. The installed Transformers 5.17.0 caller hashes local IDs and directly invokes the lookup, without distributed ID gathering. Different SP windows and DP rows exercise this case. Capacity and timing results remain implementation stress tests, not certification of correct pretrained-model training. A backend repair changes communication/memory work and requires fresh evidence; no repair was folded into these config-tuning edits. See the results document's embedding-correctness section and `tuning/check_ple_lookup.py`.

**Short search passes are not sustained-memory verification.** The historical single-row search reached 835584 passing and 843776 failing, an 8192-token bracket. The failure was Ray host OOM during the first optimizer step. A fresh two-step recheck passed with 112.9 GiB PyTorch GPU peak, 197.0 GiB maximum rank RSS and 1682.2/1675.2 GiB sampled node peaks. Those older inputs did not exclude pad IDs, so the measurements are historical evidence, not strict pad-free certification.

**Final verification passed the revised five-step requirement with 19 completed steps.** The user shortened the active 25-step run to five steps. Preserve all 19 completed updates: each used fresh random data, 102 rows x 8192 non-pad tokens, one DSS model call totaling 835584 tokens, zero pad IDs, finite loss and gradient norm, and an advancing optimizer counter. Both nodes released the exact owned zone, before/after runtime manifests matched, and the exported recipe matched the measured payload. The original run's cancellation is a duration change, not a capacity failure or a completed 25-step run. The saved `user-shortened-validation-result.json` records acceptance separately. No new search is required; the older single-row bracket remains historical evidence, not a strict pad-free packed-workload maximum.

**Three minutes means one warm complete training step, not 13 steps.** Across steps 2-19, mean forward/backward time was 139.0 seconds and mean optimizer time was 40.8 seconds, totaling 179.8 seconds per update. The first step took 277.5 seconds; all 19 complete steps totaled 3514.6 seconds, excluding initialization, client overhead and teardown. The QSA boundary limitation means these timings do not demonstrate the expected independent-short-row attention speedup.

**Normalize the two final outcomes using global input tokens, not seconds/step alone.** Both use world16/SP16/EP8, one DP group and 8192-token non-pad input rows. The maximum run sends 102 rows, totaling 835584 input tokens per update; its 18 warm updates have a complete-step median of 179.214104637 seconds, giving **4662.49 tokens/sec**. The 256K run sends 32 rows, totaling 262144 tokens; its four warm updates have a median of 84.715664140 seconds, giving **3094.40 tokens/sec**. These are allocation-wide median-step rates (`global_nonpad_input_tokens / median_complete_step_seconds`); allocation averages across 16 GPUs are 291.41 and 193.40 tokens/sec/GPU. Never multiply the token numerator by SP or EP degree.

**A shorter packed microbatch can have lower latency but lower normalized throughput without any engine batch-size change.** Both final configs use engine microbatch size one, accumulation one and one DP group; every recorded update reports one packed model call. The 102 or 32 source rows are concatenated within that call, not processed as 102 or 32 microbatches. Total packed length changes from 835584 to 262144 tokens. Warm optimizer medians are nearly fixed at 40.77 and 40.28 seconds because the parameter-sized update still runs once, while forward/backward medians are 138.31 and 44.75 seconds. The longer packed call amortizes optimizer work over 3.1875 times as many tokens. Equal source-row lengths do not imply equal attention work: QSA does not isolate packed rows, and the configs also differ in activation offload and dispatch chunks. The observed 1.51x token-rate ratio is not an equal-work speedup or a newly optimized throughput winner; the 256K export was selected by the original latency objective.

**The reporting-only estimate removes the unequal optimizer frequency.** At the historical maximum's 835584-token reference, paired warm `F + O/r` medians give **4662.49 tokens/sec** for the maximum (`r=1`) and **4576.83 tokens/sec** for the historical 256K config (`r=3.1875`, equivalent duration 57.2764 seconds per original call). These are estimated optimizer-amortized rates, not measured accumulation or new-runtime timings. Follow the guide's [common-token-update estimate](../../../docs/long-seqlen-tuning-guide.md#estimate-common-token-update-throughput); never amortize forward/backward time or use this estimate without both measured configs.

## Memory And Recovery Lessons

- The measured configuration uses world16/SP16/EP8, full activation checkpointing with router replay, activation CPU offload, CPU Adam under ZeRO-2, optimizer `pin_memory=false`, Liger fused cross-entropy and 1024-token DeepEP chunks. The smaller reference model's EP2 setting was not assumed to fit this approximately 180B-parameter model.
- Flash-Next's offload retention counts eligible saved-tensor occurrences, not decoder layers. A fused head can save eligible tensors outside checkpointed blocks. Measure tensor roles before interpreting `keep_last_n`.
- Optimizer `pin_memory=false` reduced measured node memory without eliminating CPU Adam's parameter, gradient or moment payload. Pinned-cache retention limits do not cap live offloaded tensors.
- Host-memory failure can arrive while GPUs still have space. Watch aggregate node usage through optimizer allocation; do not substitute maximum rank RSS multiplied by rank count for a measured node peak.
- DSS `/destroy` HTTP success and an autorunner `EXIT 0` did not reliably prove success or release. Use saved training results, all requested update counters, process-exit acknowledgments and idle GPU checks on every node.
- Exact owned-zone identification must exclude `latest` symlinks and recovery launchers carrying the same zone argument. Check process start times, include actual descendants and wait for exit; never kill unrelated Ray clusters.
- A timed-out GPU query is unknown, not zero usage. Preserve the confirmed OOM bound, retry scoped release verification, and do not launch another trial until release is established.

**Check whether activation offload contributes before tuning retention.** The single-node 8K SP8/EP8 and SP1/EP8 probes on `stas-dev-5` both exhausted host memory during their first CPU Adam updates, with activation offload already disabled. Ray observed 1900.04 and 1900.28 GiB used out of 1999.96 GiB, crossing its 95% threshold. Their nominal five-second sampled NVML maxima were 69.30 and 88.20 GiB out of 140.40 GiB; neither completed an optimizer update. Increasing `keep_last_n` cannot reclaim activation-offload RAM when `offload_config.enabled=false`; checkpoint activations are already resident. With offload enabled, the guide's [partial-retention tradeoff](../../../docs/long-seqlen-tuning-guide.md#splitting-the-boundaries-between-the-two-walls) remains useful: retain some eligible tensors, potentially about half if device headroom permits, and measure the result rather than interpreting the flag as a literal layer count or assuming host caches immediately shrink. Both failed jobs released their owned workers; no passing one-node config was exported.

**Expert-state sharding and precision determine the static single-node floor.** World8/EP8 has one replica per expert shard, at both SP8 and SP1; lowering SP does not add replicas for expert optimizer-state sharding. It can change dense-state sharding and token-shaped work, which must be measured separately. Inspect the resolved DeepSpeed precision: `ds_config` is shallow-merged, so `bf16={"enabled":true}` replaces DSS's BF16 master/state defaults and leaves FP32 CPU Adam state. Do not silently enable reduced-precision master weights or moments to call the same recipe feasible.

**Verify optimizer placement support before spending GPU headroom.** The [installed-source probe](/code/users/stas/ai/autorun/logs/job-stas-dev-5-0-20261013T162831Z-1179154-000-132918748.log) confirms that DeepSpeed 0.19.7 CPU Adam creates moments lazily at the first update. Its `offload_optimizer.ratio` is a ZeRO-3 control, not partial placement for the measured ZeRO-2 recipe. The installed engine's MoE gate requires AutoEP for stage 3, while the Arctic Platform adapter uses its own EP implementation. Do not infer a supported hybrid placement from schema acceptance alone. Activation retention cannot move optimizer tensors; alternative precision or placement would be a separate, unverified configuration, not evidence that the failed recipe fits.

### Single-Node GPU Optimizer Feasibility

**Activation-only offload cannot fit the measured FP32 optimizer/master configuration on eight H200s, regardless of token budget.** A CPU-only read of the pinned checkpoint index and all 96 routed-expert tensor headers verifies 48 MoE layers, each with BF16 `gate_up_proj=[512,1280,2560]` and `down_proj=[512,2560,640]`. Their total is `48 * 512 * 3 * 2560 * 640 = 120795955200` trainable expert parameters. [GroupedExperts](/code/users/stas/github/sf/stas-dss-repro/arctic-platform-qwen38-flash-max-len/arctic_platform/model/implementations/moe/layers/moe.py) retains three trainable matrices per BF16 expert; the [conversion](/code/users/stas/github/sf/stas-dss-repro/arctic-platform-qwen38-flash-max-len/arctic_platform/model/implementations/qwen38/converting_qwen4_exp.py) splits the combined gate/up tensor without changing its element count. EP8 places `15099494400` expert parameters on each GPU; world8/EP8 has one replica per expert shard, so ZeRO-2 does not divide their optimizer state further.

| Expert-only component | Dtype | GiB per GPU |
| --- | --- | --- |
| Model weights | BF16 | 28.125 |
| Master weights | FP32 | 56.250 |
| Adam first moment | FP32 | 56.250 |
| Adam second moment | FP32 | 56.250 |
| Persistent subtotal, excluding gradients | | **196.875** |
| Gradient partition during update | FP32 | 56.250 |
| Subtotal including that gradient partition | | **253.125** |
| NVML-exposed device capacity | | **140.401** |

**The persistent lower bound already rejects the trial without assumptions about gradient-buffer overlap.** Routed-expert weights plus FP32 masters and moments require 1575 GiB across the node versus 1123.21 GiB total device capacity; including FP32 gradient partitions gives 2025 GiB. These figures exclude frozen PLE weights, replicated non-expert weights and their optimizer state, activations, CUDA contexts, communication buffers and allocator slack. The [PLE embedding](/code/users/stas/github/sf/stas-dss-repro/arctic-platform-qwen38-flash-max-len/arctic_platform/model/implementations/qwen38/modeling_qwen4_exp.py) is explicitly frozen: do not multiply the approximately 180B checkpoint total by a trainable-parameter byte factor. This is a mathematical lower bound under preserved precision and placement, not a measured NVML peak or a new GPU OOM.

**Neither activation retention nor smaller SP removes the static deficit.** Activation-only offload moves saved activations, not expert weights, masters or moments. For world8, changing EP changes expert weight replication, but expert optimizer partition size remains `(P_expert / EP) / (8 / EP) = P_expert / 8`; EP8 already minimizes resident expert weight bytes. Do not run another 8K GPU-optimizer trial, length growth or a final verification for this infeasible variant. A different supported storage layout, precision, optimizer or allocation requires a fresh feasibility calculation and explicit scope agreement; none was validated here. Checkpoint revision is `de4b8e4d43b917e7706784d8bb445c9af86a3540`, and index SHA256 is `99e815241ef03325536b0aaa4441deea45174c17fae31e10f0bb456410c590de`.

### Total-Device Accounting

**Total device usage was about 126 GiB, not 116 GiB.** Final-run NVML-backed `nvidia-smi` samples reached 125.8 GiB on head GPU2 and 126.0 GiB on peer GPU2, out of 140.4 GiB exposed per H200. Worst observed remaining device memory was 14.4 GiB. These are nominal five-second sampled maxima, with four timed-out queries across the two nodes; they are lower bounds on actual total-device peaks, not continuous high-water counters. PyTorch's separately measured allocation peak reached 116.5 GiB; the maximum step-response rank RSS was 197.0 GiB. Do not subtract these independently timed/ranked peaks to claim a fixed non-PyTorch charge. PyTorch reserved memory includes allocator slack; same-rank simultaneous reserved and device-used readings are needed to separate slack from non-PyTorch allocations.

**The adjacent failure exhausted the effective host budget, not GPU memory.** At 843776 tokens, Ray killed a worker during the first optimizer step at 1901.61 / 1999.96 GiB node usage, above its 95% threshold. The final packed run's sampled node peaks were 1685.5 / 1676.2 GiB. Historical failing-run activation-offload counters reported 58.67 GiB saved tensors, 61.89 GiB logical pinned buffers and 116.64 GiB host-pinned allocator reservation per logged rank, consistent with a host allocator threshold rather than smooth token-proportional growth. These are host allocations, not extra GPU usage. Unused GPU space does not remove that fixed-configuration host OOM. More capacity might be possible with different GPU/CPU retention or allocator settings, but those settings were not verified and would require a new bracket; the user requested completion at 835584.

**Use the existing DSS instrumentation for future attribution.** The sources are DSS's `dss/ray_dss/jobs/debug/memory.py`, `jobs/gpu/training.py` and diagnostic tests; Arctic Platform supplies the model backend. Enable the existing `DSS_MEM_LOG`, `DSS_MEM_BREAKDOWN`, `DSS_MEM_STAGED`, unique `DSS_MEM_LOG_PATH`, and structured `training_memory_telemetry` as appropriate. Allocator peak resets already cover the forward/backward plus optimizer cycle. Staged/breakdown device-used readings are current `mem_get_info` samples, not NVML high-water marks. The completed run did not save the allocator-reserved/device-used breakdown, so its cache versus non-PyTorch split is unavailable; do not fabricate that attribution or rerun completed work solely to fill the missing field.

## Fixed-Length Lessons

**Lower SP does not guarantee lower step latency.** On the two-node `stas-dev-3` allocation, a 256K-per-DP-group probe measured SP16 at 93.1 seconds per warm complete update and SP8 at 129.1 seconds, with activation offload and chunk1024 fixed. SP8 processes 524288 global tokens versus SP16's 262144, so SP8 has greater tokens/second despite worse step latency. These historical runs do not compare identical global work. For future fixed-target refinement, follow the guide's [GBS1 workload and warm forward/backward objective](../../../docs/long-seqlen-tuning-guide.md#refine-a-fitting-target-configuration), reporting complete-update tokens/sec separately. Preserve the historical latency-selected export rather than declaring it a throughput winner without a new search.

**Spend measured GPU headroom on copies and dispatch overhead.** SP16 resident activations reduced the warm median to 89.1 seconds; activation offload with chunk4096 measured 88.2 seconds; combining resident activations with chunk4096 measured 85.4 seconds. Chunk8192 then measured 85.17 seconds with resident activations. These five-update probe medians are not a global optimum. Each candidate completed three full-target and two secondary updates, with two warm full-target measurements. Reduced checkpointing requires its own complete-step memory and timing check rather than assuming it fits.

**An OOM at lower SP does not identify every resident variant as infeasible.** SP4, SP2 and SP1 with activation offload/chunk1024 exhausted host memory, not a proved universal 256K GPU ceiling. Offload settings, local token volume and topology interact. Record the failed phase, keep uncompleted GPU peaks qualified and distinguish the finite set of tested configs from all possible combinations.

**Checkpoint relaxation can spend far more memory than activation residency alone.** At 256K with SP16 resident activations/chunk4096, full checkpointing sampled about 98 GiB total device usage. Checkpointing every second block then failed during its first forward with 132.81 GiB PyTorch allocated, 1.22 GiB unused reservation and 138.90 GiB including non-PyTorch memory for that worker. A 384 MiB request exceeded the remaining 187.5 MiB. Keep checkpoint relaxation as a measured candidate, not a projected fit from the prior free-space estimate. Record allocator values separately from total-device evidence; CUDA's reported usable capacity and NVML's exposed total can differ.

**Treat close chunk timings as uncertainty, not a demonstrated speedup.** Resident SP16/chunk4096 measured 85.35 seconds with 98.0 GiB sampled device usage; chunk8192 measured 85.17 seconds with 103.9 GiB. A 0.19-second median difference from two warm updates per candidate does not establish a meaningful advantage. Save both exact configs and timing spreads, and qualify numerical winner selection. The historical search rechecked its selection in a fresh five-step run; future refinement follows the guide's two-update default and adds warm samples only for a tie or questionable timing. The larger approximately 8.5% improvement from the 93.12-second starting recipe combines activation residency and less restrictive dispatch chunking.

**Fresh final verification measured 3094.40 tokens/sec at 84.72 seconds per warm step, not the earlier probe median.** Five complete full-target updates passed with 32 x 8192 strictly non-pad tokens per update. SP16/EP8, resident activations, frequency1 and chunk8192 gave four warm timings spanning 84.61-86.89 seconds, about 9.0% less latency than the 93.12-second starting recipe. The normalized allocation-wide rate divides 262144 input tokens by the unrounded warm median complete-step time. Both nodes released and runtime manifests matched. Worst sampled NVML was 103.93 / 140.40 GiB, leaving 36.47 GiB observed free, with no query errors; aggregate host peaked at 1191.0 / 2000.0 GiB. PyTorch allocated peak separately reached 91.12 GiB. Clean timing omits reserved-memory attribution, so do not present the difference between those peaks as exact non-PyTorch memory. Both final recipes omit the nested provider settings block and rely on verified top-level chunk/length controls and Liger defaults.

**Both-node loader checks protect flattened exports from ignored settings.** The maximum recipe resolves 835584 tokens/chunk1024, and the performance recipe resolves 262144 tokens/chunk8192, matching their own measured effective payloads after schema transport on both nodes. Keep `model_provider="prime_rl"` as a selector without adding a settings block. These recipes require the paired DSS schema/translation changes in `tuning/flat-deepep-config.patch`; verify support when moving to another runtime. An older schema can accept an unknown field without forwarding it. Compare manifests and exported JSON structurally: equivalent JSON may have different node/key order, whitespace and byte hashes.
