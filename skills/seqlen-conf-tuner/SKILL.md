# Sequence-Length Configuration Tuner

**Choose the requested action before tuning.** In capacity mode, find a measured limit with a pass/OOM bracket. In fixed-length performance mode, keep the requested length fixed and minimize warm complete optimizer-step time, spending available memory to remove communication, copies and recomputation. Preserve the requested model, training precision, loss, deployment and allocation. Use at least two complete forward/backward and optimizer steps per feasibility probe, then five fresh final steps.

**For a specified length, read [fixed-length performance tuning](references/fixed-length-performance.md).** Do not run a sequence-length bisection in this mode. Fewer parallel ranks are candidates, not the objective: measured complete-step time decides; prefer less parallelism only when timings are indistinguishable. Fill every DP group's requested packed length unless the user defines a fixed-global-batch objective; report changing global tokens per update and keep equal-global comparisons separate.

## Foundation

**Read the maintained guide before tuning.** The foundation for this skill is the `arctic-platform` [Tuning for long sequence length guide](../../docs/long-seqlen-tuning-guide.md). Consult its linked `dss-platform` subsystem docs when a knob needs diagnosis. The guide's measured ceilings are reference results for specific models and hardware, not promises for another model.

**Distinguish the searched quantity.** `max_seq_len` is the maximum length of an individual sequence; `training_config.mb_spec.max_tokens_per_mb` is the token budget of a packed model call before sequence/context sharding. Sequence parallelism (SP) divides token-shaped work among ranks; expert parallelism (EP) shards mixture-of-experts (MoE) weights and dispatches routed tokens. Verify actual local and global shapes in the running implementation. For a single-sequence limit, vary the input sequence length along with the token budget. Raising a budget while sending short rows does not test a longer sequence. Several short packed rows are a different experiment from one long row.

**Use short packed rows for a packed-token-budget search.** When the target is `max_tokens_per_mb`, fill that budget with multiple short input rows unless the user requests an individual-sequence limit. DSS's tensor request contract requires equal-length rows: choose a row length that divides the candidate budget, and send matching rectangular input, position and label tensors. An example is 102 rows x 8192 tokens = 835584 packed tokens. Keep per-row positions and label boundaries, then verify the attention backend actually isolates rows before claiming independent short-row attention. Changing between single-row and packed-row workloads changes the experiment; report their evidence separately.

**Never put padding tokens or positions in capacity-test data.** Resolve every pad ID from the actual tokenizer and model configuration, even when the model config has a null pad ID. Exclude those IDs during random generation; do not insert them and rely on a mask to hide them. Generate fresh random rows every step, use all-ones attention masks, and assert zero pad IDs before sending each request. Record seeds, pad IDs, per-row non-pad lengths, unmasked token count and total occupied tokens. Per-row ignored final labels are loss boundaries, not input padding. Align candidate occupancy to the SP/context-parallel degree and kernel requirements so preprocessing inserts no alignment padding. Require real tokens, model-call tokens and the candidate budget to match; a padded trial does not qualify.

**Read model-specific evidence when relevant.** For Qwen3.8-Flash-Next, consult [the observed runtime and workload lessons](references/flash-next.md). Its measured configuration is a reference, not a portable ceiling.

## Prepare And Baseline

**Establish the runtime on every allocated node.** Follow the available remote-runner and multi-node skills. Check fresh runner heartbeat, allocation hostfile, GPU count and memory, host/cgroup limits, running workloads, installed package versions, imported checkout, CUDA toolkit, model revision, and model-specific attention and parallelism support through the remote runner. Do not infer worker state from the agent's CPU environment.

**Run user-requested setup first, then test the source config unchanged.** Preserve the original config and save its hash plus the effective runtime config. Unwrap transport envelopes only as required by the local endpoint; do not silently change GPU count, optimizer, attention, sequence length, or offload for the baseline. Record baseline errors separately from memory-capacity failures. Check the model's runtime dependencies and installed source revision on every node; gate architecture-specific extensions on the actual GPU family rather than reusing H200 binaries for B200.

**Keep every node alive only during active work.** Use the available heartbeat-gated GPU keepalive skill on every node. Refresh only while the agent is working; do not add an unattended heartbeat loop. Serialize trials on the allocation and scope shutdown to processes/jobs this experiment owns.

**Use actual weights unless the user requests an architecture-only experiment.** Stage a pinned checkpoint onto each node's fast local storage and verify completeness. Record random initialization, changed layer counts, synthetic data, or other workload substitutions explicitly; do not present their ceiling as a verified production-data limit.

**Validate the exact runtime schema before expensive trials.** A pinned release can differ from the local checkout. Prime-RL uses `debug.random_init`, not a top-level `random_init`; an unset chunked head may require `"disabled"` instead of JSON `null`. Do not fabricate a managed-cache readiness manifest to bypass staging checks.

**Pin the supported attention backend explicitly.** A null field is not a reliable request for the model's own default: DSS gateway serialization can omit nulls, causing the zone's next schema parse to restore generic FA3. A wheel being installed and importable does not mean a model-specific loader accepts that backend.

**Reconcile engine batch size after changing SP.** DeepSpeed's engine `train_batch_size` equals `train_micro_batch_size_per_gpu * gradient_accumulation_steps * (world_size / sp_size)`. At world16/SP16 with microbatch and accumulation both one, set the engine batch to one. Logical request row count is separate; do not confuse it with this engine field.

**Do not add a provider settings section just to restate defaults.** Preserve the user's recipe structure. A provider selector such as `model_provider="prime_rl"` is not a `prime_rl` settings block. Use supported top-level controls when available and verify loader translation, schema round-trips and effective defaults. In this paired checkout, `training_config.deepep_token_chunk_size` now reaches the MoE loader directly and `max_seq_len` supplies its sequence limit. The old nested block remains supported for existing callers; conflicting chunk values are rejected. Exported flattened recipes require that DSS change. Never move arbitrary nested keys to the top level and assume unknown-field acceptance means they take effect.

**Compare loader options against the measured effective config, not a pre-override input.** Trial CLI overrides can change nested sequence limits as well as top-level budgets. Preserve both snapshots, but use the saved effective payload as the equivalence reference. Remote fanout wrappers can return zero despite child failures; require explicit success from every distinct allocated node before accepting a check.

**Verify row isolation before claiming independent packed attention.** Finite loss and gradients, row-local position resets, and DSS packing counts do not prove that concatenated rows are independent. Compare packed and separate rows on the exact attention backend, including a test that changes an earlier row and checks a later row's outputs or gradients. Check sparse route selection, compression, recurrent-state resets, and cross-rank convolution context, not just the final attention mask. Current Qwen3.8 QSA routes do not respect packed-row boundaries; label such runs packed stress tests, not independent-sample verification or evidence of short-row attention speedups. Record the limitation and do not silently broaden a tuning task into an attention-backend rewrite.

## Choose Memory Knobs

**Report total device usage first, not just the PyTorch allocator.** Use the existing NVIDIA Management Library (NVML) measurements to report per-GPU used/total/free memory and the worst rank, alongside aggregate node/cgroup RAM and its limit. An NVML-backed `nvidia-smi` query also measures total device usage. Label sampled NVML peaks and their interval; do not confuse them with allocator high-water counters. Turn on `training_config.step_peak_memory_log`; `/step` returns `peak_memory.gpu_peak` and `cpu_peak` in bytes, reduced with MAX across ranks. Per-rank host RSS is not aggregate node/cgroup memory.

**Reuse DSS's existing debug instrumentation; do not invent new memory controls or counters.** DSS Platform and Arctic Platform are used together: [DSS's debug/memory.py](/code/users/stas/github/sf/stas-dss-repro/dss-platform/dss/ray_dss/jobs/debug/memory.py) owns worker diagnostics, while Arctic Platform owns this model implementation. Search both imported checkouts and DSS tests rather than assuming diagnostics live under Arctic Platform. Enable `DSS_MEM_LOG=1`, `DSS_MEM_BREAKDOWN=1` and `DSS_MEM_STAGED=1`, with the existing `DSS_MEM_LOG_PATH` pointing to a unique trial log. `DSS_MEM_BREAKDOWN` alone does not emit the breakdown: its caller is gated by `DSS_MEM_LOG`. The lifecycle resets allocator peaks at forward/backward entry and after reporting `/step`, so allocator transients are captured without polling them. Staged/breakdown probes synchronize and use `mem_get_info` for current total device usage and non-PyTorch accounting. Existing structured `training_memory_telemetry` exposes allocated/reserved high-water counters too. Those resets do not create a total-device/NVML high-water counter: distinguish current device readings from allocator peaks and sampled NVML maxima. `DSS_MEM_FLUSH=1` is a diagnostic-only cache-release comparison, not a normal throughput setting. Consult [memory diagnostics](/code/users/stas/github/sf/stas-dss-repro/dss-platform/docs/memory_diagnostics.md), `tests/test_training_diagnostics.py` and `tests/test_step_peak_memory.py` for exact flags, reset semantics and examples; verify emitted fields against the imported source.

**Explain why the limiting resource is full, even when the GPU counter looks low.** DSS's `gpu_peak` is `torch.cuda.max_memory_allocated`, not total device usage. Report PyTorch allocated and reserved memory separately from driver-visible used/total/free memory. Reserved-minus-allocated is allocator slack; driver-used-minus-reserved approximates allocations outside PyTorch, including CUDA contexts and communication workspaces. Use synchronized same-rank readings to attribute those differences; subtracting independently measured peaks does not isolate non-PyTorch usage. Driver samples can miss brief peaks. The field named `cpu_peak` is maximum current rank RSS at the step response, not a sampled node-wide peak. Report aggregate node/cgroup RAM and its effective limit too. A confirmed host OOM is a valid ceiling for fixed offload settings even with unused GPU memory; unused GPU memory alone does not prove that more tokens fit. Moving saved activations back to GPU may improve that ceiling, but changes the knobs and requires a new bracket.

**Follow the guide's memory-first tradeoffs, adapting to the model.**

- Pin `cuda_allocator_conf="expandable_segments:True"` and use token-budget packing. Preserve the model's supported efficient attention backend; eager/math attention can allocate quadratic score tensors. Qwen3.8-Flash-Next specifically uses `qsa_flex`/FlexAttention and its own context-parallel implementation, not the guide's generic FlashAttention example.
- Keep full activation checkpointing at `mode="full", freq=1`; for MoE, pin `router_replay_recompute=true` so recompute routing shapes agree.
- Bound vocabulary projection with a fused head or explicit token/vocabulary tiles. On the current Prime-RL loader, Liger fused cross-entropy is the default; verify that resolved default without adding a provider settings block. Existing nested `prime_rl.fused_cross_entropy` is supported where an explicit override is needed. Do not combine fused CE with `fused_lm_head_token_chunk_size`. Weighted/non-binary SFT masks or a loss requiring per-token logprobs may require unfused tiled projection.
- If static optimizer state is binding, enable `ds_config.zero_optimization.offload_optimizer={"device":"cpu","pin_memory":true}`. Confirm DeepSpeed selects CPU Adam and its extension builds with the matching CUDA toolkit.
- Enable `ac_config.offload_config.enabled=true` only with full checkpointing. Start with `keep_last_n=1` and stream/pinned-buffer defaults. Confirm offload hooks are active with `DSS_ACT_OFFLOAD_LOG=1`; configured-but-zero counters are not a memory saving.
- On dense models, tile the MLP (feed-forward network) early. On MoE, leave `tiled_mlp_token_chunk_size` unset unless measurements justify it: the shared expert is tiled, routed experts are not.
- Test lower legal `ep_size` values when expert dispatch/combine transients bind, but verify the larger resident expert weights still fit. Never assume the guide's EP2 choice fits a larger model.
- Increase legal `sp_size` when token-shaped memory binds. SP and EP each divide the world independently; their product need not equal the world. Check model-specific restrictions: Ulysses head sharding needs divisible head counts, while a dedicated context-parallel backend may use different rules.
- Pin the supported DeepEP chunk control explicitly, using 1024 as the guide's context-bound starting point and 4096 for a throughput comparison. This paired checkout supports `training_config.deepep_token_chunk_size`; older runtimes may require the nested provider setting. Chunking bounds routing-skew spikes, not resident activation growth.

**When activation offload binds host memory, trade resident boundaries against available GPU headroom.** The guide's [Splitting the boundaries between the two walls](../../docs/long-seqlen-tuning-guide.md#splitting-the-boundaries-between-the-two-walls) describes this graded tradeoff: raising `ac_config.offload_config.keep_last_n` retains more recent eligible tensors on GPU while older tensors still offload. First check `offload_config.enabled` and actual offload counters. With `enabled=false`, checkpoint activations are already GPU-resident; increasing `keep_last_n` cannot reclaim any more activation-offload RAM and does not move CPU optimizer state. With offload enabled, try partial retention, including approximately half the measured eligible boundaries when GPU headroom permits, rather than assuming the choice is all or nothing. Recheck complete optimizer updates and both memory budgets after each change. Adjust retained pinned-cache limits if necessary, recognizing that cache retention caps do not cap live offloaded tensors. A per-layer boundary costs approximately `local_tokens * hidden_size * dtype_bytes`; leave GPU headroom instead of consuming the arithmetic maximum.

**Verify which tensors the retention knob counts.** Flash-Next's offloader counts eligible saved-tensor occurrences, not decoder layers, and a fused head may save eligible tensors outside checkpointed blocks. Do not equate `keep_last_n=N` with exactly N resident decoder boundaries without measuring tensor roles. Optimizer `pin_memory=false` can reduce pinning/allocator overhead without changing CPU Adam's parameter, gradient, or moment payload; test its actual node-memory benefit independently.

**Treat optimizer-state host OOM separately from activation retention.** Inspect the installed engine's actual master-weight, gradient and moment dtypes, devices and replica-group sharding. Lower SP does not necessarily add expert replicas. Partial CPU/GPU optimizer placement and NVMe offload require support in the exact ZeRO stage and model path; accepted schema fields alone do not establish support. Changing FP32 master weights or Adam moments to BF16 changes training precision and must not be presented as a placement-only improvement.

**Calculate the static GPU floor before replacing optimizer offload with activation-only offload.** Count trainable and frozen parameters separately from checkpoint tensor metadata and model construction; frozen weights consume device memory but have no gradients, master weights or Adam moments. For each rank, add resident model-weight bytes and the actual ZeRO partitions of master weights and both Adam moments, then account for gradient partitions and simultaneously live reduction/update buffers. Use each parameter group's real replica degree, not `world_size`, SP degree or the number of experts selected per token: all trainable experts need optimizer state. In the current EP layout, expert state is partitioned over `world_size / ep_size` replicas after EP shards the weights. Compare the worst-rank floor against NVML device capacity, leaving room for contexts, communication workspaces, activations and allocator slack. If even the persistent floor without gradients exceeds capacity, record arithmetic infeasibility and do not launch an activation-only trial or bisect sequence length. If the floor permits a trial, it is only a necessary condition: test a low, fully occupied token budget through complete optimizer updates. Preserve precision; changing master/state dtypes or optimizer algorithms is a separate configuration decision. Flash-Next world8/EP8 with the measured FP32 Adam/master settings already requires **196.875 GiB per GPU for routed-expert weights and persistent optimizer tensors alone**, versus **140.40 GiB available**; see [the model-specific calculation](references/flash-next.md#single-node-gpu-optimizer-feasibility).

**Verify cross-node transport before trusting a long search.** Confirm EFA runs selected `NET/OFI` and Libfabric when appropriate. The guide reports an aws-ofi-nccl 1.17.2 host leak and a tested flat result on 1.21.1; record the actual plugin version instead of assuming more SP nodes imply usable capacity.

**Watch host memory through optimizer steps, not just forward/backward.** Adjacent token budgets can hit allocator or retained-buffer thresholds, so a slope from passing lengths does not prove smooth host-memory growth. Sample aggregate node/cgroup memory through the first optimizer update and later steps; per-rank RSS alone misses node overhead. Inspect actual pinned-buffer allocations before attributing a jump to an allocator setting.

## Bracketed Search

**Keep knobs and runtime fixed within each search.** Save one effective config per trial. A changed EP/SP/offload/head configuration or CUDA/package/transport runtime starts a new bracket; passing lengths from another configuration or runtime are not bounds. Store a runtime identity with trial results and reject incompatible seeds.

1. Establish a passing lower bound with at least two training steps. A model-load OOM is a static-capacity problem: fix the configuration before searching length.
2. Exponentially increase the tested token budget until a confirmed GPU or host-memory failure gives an upper bound. With two passing points, use peak-memory slope to choose a useful overshoot. Respect any user-specified context, time, or cost cap.
3. Binary-search between the passing and failing lengths. Round candidates to a valid packing/SP/kernel alignment and avoid duplicate probes. Stop when the pass/OOM gap is at most **4096 tokens (4K)** if the largest passing length is **below 32768 tokens (32K)**, or **8192 tokens (8K)** at 32K and above; do not bisect further unless the user requests finer resolution. A bracket crossing 32K uses 4K until a passing bound reaches 32K. Save both endpoints and the effective resolution, then run final verification at the passing endpoint. Alignment must permit that resolution; an unrefinable larger gap is not a completed bracket.
4. Count only confirmed capacity failures as failing bounds. Import failures, authentication/download errors, unsupported kernels, invalid group sizes, timeouts, non-finite results, and collective hangs do not establish a memory ceiling. Diagnose an actionable non-capacity failure, rerun the same candidate, or stop and report the blocker.
5. After a failure, destroy the owned training job and verify workers and GPU allocations are released on every node before another candidate. An HTTP-success teardown response alone is insufficient. If recovery is necessary, identify the exact owned zone and descendants and verify process start times before signaling PIDs. Stop the search if release remains unverified. Use fresh ports and unique log/output paths; do not delete existing logs or kill unrelated clusters.
6. Recheck the selected passing candidate in a fresh job. Default to **five complete steps** with fresh random, strictly non-pad data, unless the user specifies another duration. Keep the selected workload shape; for packed trials verify one intended model call contains all expected short rows. Require finite loss and gradient norm, successful updates and advancing engine step counters for every requested step. If the user shortens an active verification after enough steps have passed, preserve all observed steps, end the owned run with verified cleanup, and record the changed requirement rather than launching another run or claiming the original duration completed. Test a separate reserve setting only within the user's scope; omit it when the user requests maximum-only completion.

**Resume an interrupted bracket without repeating known OOMs.** Reuse both endpoints only when their configuration hash, runtime identity, workload shape and measured outcome match the resumed search. A confirmed memory failure remains evidence even if its teardown failed, but it cannot authorize another trial until current release is independently verified on all nodes. Ignore convenience `latest` log symlinks when identifying an exact zone, and distinguish real zone-server processes from recovery launchers carrying identical zone-ID arguments.

**A completed bracket and successful cleanup are separate facts.** If the bracket is already within resolution but its last OOM left a cleanup error, recover that exact owned zone, require process-exit acknowledgments and idle GPUs on every node, then run the selected final verification. Do not repeat the known failure or falsely rewrite its search status. Give each recovery attempt a new log path; preserve the original evidence.

**Check that each candidate saturates the searched budget.** Record actual packed-call occupancy, not only configured limits. The packer can admit an oversized row as a singleton; reject a trial that exceeds its intended budget. When raising a budget no longer changes input occupancy or grouping, the workload is saturated: enlarge the input consistently with the requested experiment or report saturation without a capacity claim.

**Diagnose oversized transients without changing the searched meaning.** If configured knobs do not take effect, record a below-wall CUDA allocator snapshot using `DSS_MEM_SNAPSHOT` and inspect allocation stacks. Do not use snapshot-on timings as final throughput measurements. Do not replace a long row with short packed rows merely to obtain a pass.

## Deliver

**Report the evidence and uncertainty together.** Save the original config, explicitly pinned optimized config, largest passing and smallest failing token budgets, search resolution, two-step losses and gradient norms, GPU and host peaks, node totals, step times, binding resource, workload shape, model/code revisions, remote job IDs, and log paths. State whether the search reached a memory boundary or merely a configured cap. Never label an untested candidate as optimized or maximum.

**Make timing and memory units unambiguous.** Give forward/backward, optimizer and their combined per-step duration separately; distinguish per-step time from all-step total and initialization. Label binary memory units as GiB. Name each memory measurement's accounting scope, say which resource caused the adjacent OOM and why GPU headroom did not invalidate that bound, and distinguish the tested fixed-configuration limit from a global optimum across untested configurations.

**Report complete-step time and estimator availability for both actions.** Include the selected maximum-capacity config's timing even though capacity, not speed, was the search objective. For both capacity and fixed-length winners, report warm median seconds per complete optimizer update, the warm-step count and spread, and separate the cold first step. Preserve historical diagnostic timings as such rather than presenting them as clean throughput comparisons.

**Report estimated TFLOPS only when the existing estimator supports the exact model and workload.** TFLOPS is trillions of floating-point operations per second, not a directly measured hardware counter. Search the imported runtime for existing FLOPS counters and emitted metrics; verify model support and attention/MoE accounting before using them. Record the estimator source/version, global non-pad tokens, GPU count, whether throughput is aggregate or per GPU, the timing denominator and whether recomputation is counted. Prefer complete-step throughput when a supported per-update FLOP estimate is available; label forward/backward-only throughput separately and do not compare it as complete-step throughput. Model FLOPs utilization (MFU) is a dimensionless ratio, not TFLOPS. If the model is unsupported, no estimate was collected, or the accounting cannot be verified, explicitly report **TFLOPS: unavailable** with the reason. Do not replace a missing estimator with a generic parameter-count formula, silently extrapolate another architecture, or implement a new estimator as part of tuning.

**Export the configuration that was actually measured.** Snapshot the source before final verification, preserve its transport envelope, and compare the exported training payload structurally against the saved effective config. Keep `max_seq_len`, `mb_spec.max_tokens_per_mb`, and provider-specific limits consistent with the selected deployment; short verification rows do not require lowering those config limits. Save config hashes and before/after per-node runtime manifests, including imported source paths, plugin binaries and checkpoint revision. Record necessary launcher environment settings separately because JSON does not encode every runtime dependency.

**Maintain readable progress during long searches.** Keep a results Markdown document with a short TLDR at the top, then setup/dependency evidence, a trial table, the current pass/fail bracket, and unresolved failures. Include the full absolute final-config path in the TLDR as soon as it is written, clearly distinguishing preliminary, two-step and longer-final verification. Update after milestones. Status questions and documentation requests do not cancel unfinished authorized work; continue until the requested objective is complete, an explicit stop/pause, or an execution/permission limit.
