# Sequence-Length Configuration Tuner

**First test the original configuration on the assigned setup and GPU count, with the 20 GiB reserve.** Before capacity search, performance refinement or tuning-knob changes, follow the guide's [original-config validation gate](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first). Complete any required setup and checkpoint staging, then attempt at least two complete training updates. Keep the source file unchanged and preserve its original training and batch settings in the experiment copy, adding `debug.gpu_mem_preallocate_gib=20` before transport. The reserve applies to every experiment, including onboarding; never disable it to make a baseline pass. A static estimate, successful model load or another recipe's result does not satisfy this gate. Diagnose a failure before choosing a tuning move: infrastructure, unsupported-kernel and correctness failures must be resolved first, but a confirmed capacity OOM starts the guide's [fitting-configuration recovery](../../docs/long-seqlen-tuning-guide.md#recover-a-capacity-failing-baseline) when the user requested a fitting config. Do not require an impossible unchanged baseline to pass, repeat a compatible known OOM, or treat its failure as a maximum-length bound for a different config. Tuning after the original attempt uses GBS=1.

**Choose the requested action before tuning.** In capacity mode, find a measured limit with a pass/OOM bracket and report its normalized tokens/sec. In fixed-length performance mode, keep the requested length fixed and minimize warm forward/backward time, excluding optimizer `/step` time. Honor a different explicitly requested objective, but still report normalized complete-update throughput separately. Preserve the requested model, training precision, loss, deployment and allocation. Use at least two complete forward/backward and optimizer steps per capacity feasibility probe. Fixed-length timing defaults to two total updates, with only update 2 scored; reuse compatible existing measurements and add warm samples only to resolve a tie or questionable timing. Never score update 1.

**For a specified length, read [fixed-length performance tuning](references/fixed-length-performance.md).** Do not run a sequence-length bisection or start a fresh config grid. Apply the guide's history-based local refinement, including coupled topology/memory moves. Keep GBS=1 and the target workload unchanged unless the user explicitly requests another batch; check engine batch legality before changing active ranks or SP.

**When switching SFT/RL recipes, retain planning evidence but requalify the actual loss.** Follow the guide's head-contract, request-level loss qualification and logprob-tile refinement rules. Read the loss from training requests and measured results, not a presumed `loss_fn` recipe field. A same-model SFT pass is not an RL capacity pass or ranking sample. Preserve sampling sub-jobs, qualify finite GRPO updates, and distinguish training-only synthetic stress tests from end-to-end sampling/rollout qualification.

**Do not label a loss-head correction as the original baseline.** Follow the guide's [loss-head correction rule](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first): qualify the modified copy separately, preserve the original failure and resolve any missing original attempt before capacity search. Select the unchanged mode in the recipe launcher as well as the trial runner, and validate the preceding recipe's actual outcome when changing phases. Bind capacity handoffs to the exact completed owner and measured final length, not a planned maximum. A request-contract preflight is diagnostic evidence, not completed baseline training.

**Bind Qwen onboarding to the current preparation too.** Follow the guide's [Qwen launcher setup](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first), selecting `original-baseline` before `head-corrected` and supplying the actual setup, staging, setup-owner log and fresh idle receipts. Historical launcher filenames do not authorize reusing old hostnames or interpreters.

## Foundation

**The maintained guide is the source of truth for tuning heuristics.** Read the `arctic-platform` [Tuning for long sequence length guide](../../docs/long-seqlen-tuning-guide.md), including [fixed-target refinement](../../docs/long-seqlen-tuning-guide.md#refine-a-fitting-target-configuration). Add search-efficiency improvements there rather than creating a parallel method in this skill or a runner. Consult its linked `dss-platform` subsystem docs when a knob needs diagnosis. The guide's measured ceilings are reference results for specific models and hardware, not promises for another model.

**Do not reuse a seed that requires a removed runtime control.** The closed PR247 SP exchange barrier is no longer implemented in this checkout. Follow the guide's historical-runtime qualification rule before reusing results that depended on it; setting an obsolete environment variable does not restore the implementation.

**Distinguish the searched quantity.** `max_seq_len` is the maximum length of an individual sequence; `training_config.mb_spec.max_tokens_per_mb` is the token budget of a packed model call before sequence/context sharding. Sequence parallelism (SP) divides token-shaped work among ranks; expert parallelism (EP) shards mixture-of-experts (MoE) weights and dispatches routed tokens. Verify actual local and global shapes in the running implementation. For a single-sequence limit, vary the input sequence length along with the token budget. Raising a budget while sending short rows does not test a longer sequence. Several short packed rows are a different experiment from one long row.

**Use short packed rows for a packed-token-budget search.** When the target is `max_tokens_per_mb`, fill that budget with multiple short input rows unless the user requests an individual-sequence limit. DSS's tensor request contract requires equal-length rows: choose a row length that divides the candidate budget, and send matching rectangular input, position and label tensors. An example is 102 rows x 8192 tokens = 835584 packed tokens. Keep per-row positions and label boundaries, then verify the attention backend actually isolates rows before claiming independent short-row attention. Changing between single-row and packed-row workloads changes the experiment; report their evidence separately.

**Never put padding tokens or positions in capacity-test data.** Resolve every pad ID from the actual tokenizer and model configuration, even when the model config has a null pad ID. Exclude those IDs during random generation; do not insert them and rely on a mask to hide them. Generate fresh random rows every step, use all-ones attention masks, and assert zero pad IDs before sending each request. Record seeds, pad IDs, per-row non-pad lengths, unmasked token count and total occupied tokens. Per-row ignored final labels are loss boundaries, not input padding. Align candidate occupancy to the SP/context-parallel degree and kernel requirements so preprocessing inserts no alignment padding. Require real tokens, model-call tokens and the candidate budget to match; a padded trial does not qualify.

**Read model-specific evidence when relevant.** For Qwen3.8-Flash-Next, consult [the observed runtime and workload lessons](references/flash-next.md). Its measured configuration is a reference, not a portable ceiling.

## Prepare And Baseline

**Check CPUAdam cache readiness for CPU optimizer offload.** Follow the guide's [extension-readiness preflight](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first) on the actual assigned training nodes. Classify a build-lock wait as infrastructure, and preserve any verified stale-lock archive separately from recipe qualification.

**Renew keepalive five minutes early.** Follow the guide's deadline scheduling: persist the earliest expiry and renewal time, renew before a wait would cross the renewal time, and advance deadlines only after all-node receipt qualification.

**Choose the active allocation before staging or tuning.** Follow the guide's [node-count selection](../../docs/long-seqlen-tuning-guide.md#choose-the-node-count), including its exhausted-range reporting rule. When the user requests the fewest nodes, minimize the qualified active-node count first, then warm forward/backward latency on that allocation. Read the current recipe's counts and reserve every preserved sampling sub-job before selecting training worlds within the remaining GPU budget. Prune illegal model-specific SP/EP, engine-batch and placement layouts before costly probes; node counts need not be powers of two, but a particular model and GBS1 can exclude intermediate counts. Reuse compatible history without repeating unchanged OOMs, record skipped counts and their evidence, and never call a merely legal or estimated layout a measured minimum. Keep capacity search separate until the requested fixed-target outcomes are complete.

**Qualify topology and communication backend separately.** Follow the guide's [parallelism rules](../../docs/long-seqlen-tuning-guide.md#parallelism): head-exchange constraints are model-path specific, and a node-local EP restriction for one backend does not exclude a supported cross-node backend. Check actual worker groups before proposing a locality-saving EP move.

**A rejected full-node world does not exclude the node count.** Follow the guide's [smaller-placement rule](../../docs/long-seqlen-tuning-guide.md#choose-the-node-count): inspect supported smaller training worlds after preserving sampling, check how the imported placement policy packs those worlds, bound metadata checks by the current allocation, and qualify actual placement and capacity before claiming a minimum. Do not count idle reservation hosts as occupied recipe nodes or silently probe below an explicitly authorized active-node range. Legal metadata combinations and placement dry runs are not capacity passes or a GPU sweep.

**Recompute length alignment when changing the capacity topology.** Follow the guide's [node-count alignment rule](../../docs/long-seqlen-tuning-guide.md#choose-the-node-count). Non-power-of-two SP can require a different aligned seed and cap; never turn padding or an untested rounded seed into a fixed-target pass. Qualify a changed capacity seed at its exact aligned length and actual loss, rather than applying a fixed-target-only export gate to it.

**Preserve separate outcomes when the operator requests another node count.** Follow the guide's [smaller-node maximum rule](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly): retain the larger-node export, qualify fresh capacity bounds on the requested active topology, and distinguish occupied GPUs from the full reservation.

**Set up every experiment through the guide's [local gateway and full-recipe workflow](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly).** Use the requested allocation and its verified staged hostfile, the setup-provided environment and an owned `--backend gpu --placement local` gateway. Never use onprem, a managed Snowflake endpoint or an unrelated shared Ray cluster. Give the gateway an available port and unique zone logs, verify `/health`, and check actual AP/DSS imports and model paths on every node. The gateway creates per-sub-job zones; it does not own an allocation-wide Ray cluster.

**Rebuild role metadata, not the tuning method, when moving jobs or switching recipes.** Follow the guide's actual-host role mapping and interpreter-path checks, including when a changed sampling count frees a host for training on the same allocation. Do not inherit a previous reservation's hostnames, environment prefix or capacity endpoints without requalification, or modify an environment used by an active experiment.

**Retain the qualified preparation reference across GLM RL capacity roots.** Follow the guide's `TUNING_RUNTIME_PREPARATION` rule when a completed refinement directory lacks preparation metadata; require allocation, role, interpreter and model agreement before the unchanged all-node runtime check. A missing preparation file is a setup failure, not a memory bound or permission to weaken the check.

**Qualify useful expert-sharding moves without importing the old bounds.** Follow the guide's expert-sharding alternative rule for GLM RL: use the existing full-recipe launcher's fresh EP32 qualification while preserving every other knob, then establish new capacity bounds from measured results. Do not stop at an EP16 obstruction when a supported, previously planned EP32 alternative remains untested.

**Forward experiment settings explicitly when running remote preflights.** Follow the guide's environment-forwarding and absolute-artifact-path rules; coordinator exports and working directories alone do not establish the cache, model resolution, imported runtime or artifact lookup on `ds_ssh` workers.

**Gate remote preparation on every node's receipt.** Follow the guide's [preparation checks](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly): an outer EXIT0 or fan-out success is insufficient. Require matching successful staging receipts and actual offline loader lookup on every intended host. Preserve failed artifacts and reuse already-qualified role environments for a staging-only retry.

**Submit the whole recipe through the unauthenticated local CortexTrainingClient, not direct worker initialization.** Preserve the `sub_job_configs` envelope and all sampling/training sub-jobs. Construct `CortexTrainingClient(base_url="http://127.0.0.1:<port>", database="dev", schema="dev", endpoint="cortex-training", ...)` directly, without host/PAT or recipes `make_client`; ensure `poll_max_interval >= poll_interval`. Use `create_job_from_body` then `wait_for_job`, saving parent and child/zone IDs. Apply any required AP transport adaptation only to training sub-jobs in a copied envelope and save both complete bodies. A parent becoming `running` is readiness only: require two complete finite training updates to pass onboarding. Direct `/initialize`, `/fwd-bwd` and `/step` probes are diagnostics, not validation of the original recipe; clearly label their synthetic workload and scope.

**Verify backend execution and whole-experiment cleanup.** A backend name or installed wheel is not proof of the kernel used. Record the actual training-worker implementation before comparing FlashMLA on/off memory; a pre-attention OOM or tiny CUDA dispatch check cannot establish full-model attention memory cost. Track and cancel the parent through the local client when needed, then verify every owned training and sampling zone has released its GPUs on every node. Follow the guide for model-path resolution, timeout bounds, source manifests and client/CLI examples.

**Check the exact request before reporting training progress.** Follow the guide's [controller/request distinction](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly). A live controller or absent `result.json` can mean cleanup after a failed request, not an active update. Qualify the outcome and release separately before changing a bound or starting another trial.

**Diagnose an apparent stall without shrinking the memory bracket.** Follow the guide's [experiment diagnostics](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly): compare compatible cold timing, check advancement in computational threads with guarded exact-zone stacks, and distinguish a synchronization wait from its unproven cause. High GPU utilization is not progress evidence. Preserve a cancelled or stalled probe as infrastructure evidence and retry the same length only after verified release.

**For a pre-input timeout, follow the guide's checkpoint-coordination diagnosis.** Compare the earliest unfinished collective across ranks rather than attributing downstream waits to training capacity; preserve exact-zone service logs before teardown. A repeated loader failure requires an isolated diagnostic, not another length reduction.

**For a reproduced stall, apply the guide's isolated-diagnostic gate before another full-model retry.** Verify each field's shape and dtype against the imported implementation. An exact-shape collective/kernel probe narrows diagnosis; it is not capacity qualification.

**Requalify scheduling changes without diagnostic controls.** Follow the guide's existing-synchronization-control procedure, verify the selected control on every training worker, and keep changed runtime bounds separate from historical passes, OOMs and synchronized diagnostics.

**Treat a fresh final stall as failed deployment qualification.** Follow the guide's final-stall rule: preserve memory history, diagnose the collective evidence after verified release, and do not export or advance dependent recipe phases from an earlier short pass alone.

**Preserve measured length overrides when qualifying a seed.** Follow the guide's [buffered-seed validation](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first): retain source hashes and raw results, reconstruct only recorded length changes, and require exact measured-payload equality. Carry required AP scheduling settings through capacity qualification and report them separately from deployment JSON.

**Establish the runtime on every allocated node.** Follow the available remote-runner and multi-node skills. Check fresh runner heartbeat, allocation hostfile, GPU count and memory, host/cgroup limits, running workloads, installed package versions, imported checkout, CUDA toolkit, model revision, and model-specific attention and parallelism support through the remote runner. Do not infer worker state from the agent's CPU environment.

**Complete the original-config attempt and failure diagnosis before tuning.** Preserve the source config and save its hash, effective runtime config, allocation/runtime identity, completed-update evidence and logs. Unwrap transport envelopes only as required by the local endpoint; preserve training semantics and record the transformed payload separately. Check the model's runtime dependencies and installed source revision on every node; gate architecture-specific extensions on the actual GPU family rather than reusing H200 binaries for B200. Keep original-baseline failures separate from fitting-copy qualification and maximum-length outcomes, and verify owned-worker release on every node before proceeding.

**Use the stack provided by that setup.** Verify installed packages and transport libraries on every node rather than building a parallel stack from source. Capture selected plugin paths and binary hashes; historical custom-runtime results are not identity evidence for a fresh allocation. If a necessary dependency is missing or incompatible, report the exact failure and follow the user's provisioning constraints before changing the runtime.

**Keep every node alive only during active work.** Follow the guide's [per-node keepalive qualification](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly), including successful CUDA-touch receipts before setup/staging, at trial boundaries and at least every 20 minutes during active work or long waits. Persist each node's successful check and the next deadline before a long wait or handoff, and bound observation waits by that deadline. A live daemon or touch timestamp alone is insufficient. Use the available heartbeat-gated GPU keepalive skill on every node, explicitly select agent-gated mode and do not add an unattended heartbeat loop. Keep touches outside scored training intervals. Serialize trials on the allocation and scope shutdown to processes/jobs this experiment owns.

**Distinguish active-job checks from idle setup.** Follow the guide's helper-selection rule: validate the actual touch selection, retain failed raw evidence, and never claim busy GPUs were touched. Fresh active-job receipts require separate current-job inspection; they do not replace the default all-eight-GPUs-per-node idle provisioning gate.

**Use actual weights unless the user requests an architecture-only experiment.** Stage a pinned checkpoint onto each node's fast local storage and verify completeness against the loader's actual lookup, including the guide's [offline snapshot qualification](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first) when applicable. Record random initialization, changed layer counts, synthetic data, or other workload substitutions explicitly; do not present their ceiling as a verified production-data limit.

**Validate the exact runtime schema before expensive trials.** A pinned release can differ from the local checkout. Prime-RL uses `debug.random_init`, not a top-level `random_init`; an unset chunked head may require `"disabled"` instead of JSON `null`. Do not fabricate a managed-cache readiness manifest to bypass staging checks.

**Preserve model-default attention for the baseline; pin the supported backend for tuning afterward.** Follow the guide's [transport-preservation rule](../../docs/long-seqlen-tuning-guide.md#validate-the-original-configuration-first): AP's bridge materializes an explicit-null MoE attention setting through the existing registered loader before DSS serialization can replace it with generic FA3. Keep the source unchanged, save the transport payload separately and verify the actual loader. A wheel being importable does not prove a model-specific loader accepts that backend. Preserve and diagnose any pre-correction baseline failure rather than silently editing its attention field.

**Preserve AP's automatic loader selection across DSS transport too.** Follow the same guide section when the source omits `model_provider`: map a verified supported AP MoE loader to the existing DSS route in the transport copy only. Preserve explicit providers, reject unmapped loaders, and qualify the actual DSS model-dependent parallelism preflight on every node; schema round-trips alone cannot prove the job will select that loader.

**After the unchanged baseline, keep GBS=1 and validate batch legality before a tuning trial.** Follow the guide's [batch and topology constraints](../../docs/long-seqlen-tuning-guide.md#refine-a-fitting-target-configuration). DeepSpeed's engine `train_batch_size` equals `train_micro_batch_size_per_gpu * gradient_accumulation_steps * (world_size / sp_size)`. At world16/SP16 with microbatch and accumulation both one, set the engine batch to one; world16/SP8 instead requires two and is not a GBS1 candidate. Do not silently increase batch size, shorten the target or change active GPU count. Logical request source-row count is separate; record the packed-call count and actual global work too.

**Separate source rows, packed model calls and total packed length in performance explanations.** Multiple source samples can be concatenated into one packed microbatch with a batch dimension of one. If both runs have one packed call and one optimizer update, changing source-row count at fixed row length changes total packed tokens, not the number of microbatches. Describe that comparison as a packed-length change, not an engine batch-size change. The parameter-sized optimizer work can remain roughly fixed per update, so longer packed calls amortize it over more tokens even without changing the batch dimension or accumulation. Verify actual model-call counts; do not infer them from source-row counts.

**Do not add a provider settings section just to restate defaults.** Preserve the user's recipe structure. A provider selector such as `model_provider="prime_rl"` is not a `prime_rl` settings block. Use supported top-level controls when available and verify loader translation, schema round-trips and effective defaults. When AP recipes need DSS loader transport adaptation, invoke AP's [DSS transport bridge](../../arctic_platform/integrations/dss_training_config.py) on training sub-jobs in a copied create-job envelope before submitting the complete recipe; it carries `deepep_token_chunk_size`, the sequence limit and reserve through the existing loader channel without patching DSS. Preserve other sub-jobs and the flat deployment recipe, and record the complete transformed body separately. Reject conflicting chunk values and unsupported providers rather than trusting unknown-field acceptance to apply a control.

**Compare loader options against the measured effective config, not a pre-override input.** Trial CLI overrides can change nested sequence limits as well as top-level budgets. Preserve both snapshots, but use the saved effective payload as the equivalence reference. Remote fanout wrappers can return zero despite child failures; require explicit success from every distinct allocated node before accepting a check.

**Verify the injected head before refining its chunk size.** Follow the guide's [loader head-selection check](../../docs/long-seqlen-tuning-guide.md#leave-a-gpu-safety-margin). A trainer's config-derived "chunked head enabled" message alone does not prove the AP loader applied that setting; compare resolved options and all-rank injection logs. Correct a dropped control before interpreting the resulting OOM as a failure of the intended configuration.

**Verify row isolation before claiming independent packed attention.** Finite loss and gradients, row-local position resets, and DSS packing counts do not prove that concatenated rows are independent. Compare packed and separate rows on the exact attention backend, including a test that changes an earlier row and checks a later row's outputs or gradients. Check sparse route selection, compression, recurrent-state resets, and cross-rank convolution context, not just the final attention mask. Current Qwen3.8 QSA routes do not respect packed-row boundaries; label such runs packed stress tests, not independent-sample verification or evidence of short-row attention speedups. Record the limitation and do not silently broaden a tuning task into an attention-backend rewrite.

## Choose Memory Knobs

**Declare the capacity allocation separately from fixed-target node minimization.** Follow the guide's [capacity allocation scope](../../docs/long-seqlen-tuning-guide.md#choose-the-node-count) before selecting a bracket seed. Reuse qualified larger-world evidence within the authorized range when maximizing length; preserve a fixed or minimum-node capacity scope when the operator specifies it.

**Use the guide's [GPU safety margin](../../docs/long-seqlen-tuning-guide.md#leave-a-gpu-safety-margin) while retaining OOM as the gate.** Materialize `training_config.debug.gpu_mem_preallocate_gib=20` for every experiment, including original-config validation, candidates and final verification. Do not preserve a source's absent or zero reserve in an experiment; keep the original source separately and require 20 in the effective and transported configs unless the user explicitly changes the margin. Arctic Platform retains the tensor on every rank through optimizer updates; no memory-sampling threshold is needed for this gate. Include the margin in effective-config identity: older no-buffer runs are planning evidence, not buffered passes. Existing otherwise-unchanged OOMs need no retry merely because the buffer increased. Inspect all-rank allocator cache-flush warnings and flag warm-step pressure before selecting a performance winner; follow the guide for accounting and model-dependent MoE caveats.

**Disclose the safety margin and deployment risk in the outcome report.** State that qualification withheld 20 GiB per GPU (or the explicitly chosen amount). A longer sequence may fit without that buffer, but no larger limit is established by the buffered result; the operator accepts the OOM risk when spending that headroom on new data. Give the MoE example: uneven token routing can send far more tokens to some expert-parallel ranks than a balanced input, causing substantially higher peak GPU memory on those ranks. Neither balanced synthetic data nor a fixed reserve guarantees all inputs will fit.

**Report total device usage first, not just the PyTorch allocator.** Use the existing NVIDIA Management Library (NVML) measurements to report per-GPU used/total/free memory and the worst rank, alongside aggregate node/cgroup RAM and its limit. An NVML-backed `nvidia-smi` query also measures total device usage. Label sampled NVML peaks and their interval; do not confuse them with allocator high-water counters. Turn on `training_config.step_peak_memory_log`; `/step` returns `peak_memory.gpu_peak` and `cpu_peak` in bytes, reduced with MAX across ranks. Per-rank host RSS is not aggregate node/cgroup memory.

**Reuse DSS's existing debug instrumentation; do not invent new memory controls or counters.** DSS Platform and Arctic Platform are used together: [DSS's debug/memory.py](../../../dss-platform-main/dss/ray_dss/jobs/debug/memory.py) owns worker diagnostics, while Arctic Platform owns this model implementation. Search both imported checkouts and DSS tests rather than assuming diagnostics live under Arctic Platform. Enable `DSS_MEM_LOG=1`, `DSS_MEM_BREAKDOWN=1` and `DSS_MEM_STAGED=1`, with the existing `DSS_MEM_LOG_PATH` pointing to a unique trial log. `DSS_MEM_BREAKDOWN` alone does not emit the breakdown: its caller is gated by `DSS_MEM_LOG`. The lifecycle resets allocator peaks at forward/backward entry and after reporting `/step`, so allocator transients are captured without polling them. Staged/breakdown probes synchronize and use `mem_get_info` for current total device usage and non-PyTorch accounting. Existing structured `training_memory_telemetry` exposes allocated/reserved high-water counters too. Those resets do not create a total-device/NVML high-water counter: distinguish current device readings from allocator peaks and sampled NVML maxima. `DSS_MEM_FLUSH=1` is a diagnostic-only cache-release comparison, not a normal throughput setting. Consult [memory diagnostics](../../../dss-platform-main/docs/memory_diagnostics.md), `tests/test_training_diagnostics.py` and `tests/test_step_peak_memory.py` for exact flags, reset semantics and examples; verify emitted fields against the imported source.

**Explain why the limiting resource is full, even when the GPU counter looks low.** DSS's `gpu_peak` is `torch.cuda.max_memory_allocated`, not total device usage. Follow the guide's reduction-scope rule: a response returned by rank 0 can contain an all-rank MAX, so verify the imported reducer before labeling a counter rank-local. Report PyTorch allocated and reserved memory separately from driver-visible used/total/free memory. Reserved-minus-allocated is allocator slack; driver-used-minus-reserved approximates allocations outside PyTorch, including CUDA contexts and communication workspaces. Use synchronized same-rank readings to attribute those differences; subtracting independently measured peaks does not isolate non-PyTorch usage. Driver samples can miss brief peaks. The field named `cpu_peak` is maximum current rank RSS at the step response, not a sampled node-wide peak. Report aggregate node/cgroup RAM and its effective limit too. A confirmed host OOM is a valid ceiling for fixed offload settings even with unused GPU memory; unused GPU memory alone does not prove that more tokens fit. Moving saved activations back to GPU may improve that ceiling, but changes the knobs and requires a new bracket.

**Follow the guide's memory-first tradeoffs, adapting to the model.**

- Pin `cuda_allocator_conf="expandable_segments:True"` and use token-budget packing. Preserve the model's supported efficient attention backend; eager/math attention can allocate quadratic score tensors. Qwen3.8-Flash-Next specifically uses `qsa_flex`/FlexAttention and its own context-parallel implementation, not the guide's generic FlashAttention example.
- Keep full activation checkpointing at `mode="full", freq=1`; for MoE, pin `router_replay_recompute=true` so recompute routing shapes agree.
- Bound vocabulary projection with a fused head or explicit token/vocabulary tiles. On the current Prime-RL loader, Liger fused cross-entropy is the default; verify that resolved default without adding a provider settings block. Existing nested `prime_rl.fused_cross_entropy` is supported where an explicit override is needed. Do not combine fused CE with `fused_lm_head_token_chunk_size`. Weighted/non-binary SFT masks or a loss requiring per-token logprobs may require unfused tiled projection.
- If static optimizer state is binding, enable `ds_config.zero_optimization.offload_optimizer={"device":"cpu","pin_memory":true}`. Confirm DeepSpeed selects CPU Adam and its extension builds with the matching CUDA toolkit.
- Enable `ac_config.offload_config.enabled=true` only with checkpointing enabled and `mode="full"`; this mode does not require frequency1. Follow the guide's [layer-type and saved-tensor checks](../../docs/long-seqlen-tuning-guide.md#recompute) before a partial-checkpoint/offload performance move. Start with `keep_last_n=1` and stream/pinned-buffer defaults. Confirm offload hooks are active with `DSS_ACT_OFFLOAD_LOG=1`; configured-but-zero counters are not a memory saving.
- On dense models, tile the MLP (feed-forward network) early. On MoE, leave `tiled_mlp_token_chunk_size` unset unless measurements justify it: the shared expert is tiled, routed experts are not.
- Test lower legal `ep_size` values when expert dispatch/combine transients bind, but verify the larger resident expert weights still fit. Never assume the guide's EP2 choice fits a larger model.
- Increase legal `sp_size` when token-shaped memory binds. SP and EP each divide the world independently; their product need not equal the world. Check model-specific restrictions: Ulysses head sharding needs divisible head counts, while a dedicated context-parallel backend may use different rules.
- Pin the supported DeepEP chunk control explicitly, using 1024 as the guide's context-bound starting point and 4096 for a throughput comparison. This paired checkout supports `training_config.deepep_token_chunk_size`; older runtimes may require the nested provider setting. Chunking bounds routing-skew spikes, not resident activation growth.

**For a near-capacity gradient-collective OOM, consult the guide's [gradient-reduction refinement](../../docs/long-seqlen-tuning-guide.md#gradient-reduction).** Diagnose the installed buffer settings before deciding whether to change the configuration or shorten the input. Use the existing full-recipe launcher's reduction-only five-update mode and its historical-reference rules after a late OOM. A bucket change requires fresh measured bounds; do not import passing or OOM endpoints from the previous configuration.

**When activation offload binds host memory, trade resident boundaries against available GPU headroom.** The guide's [Splitting the boundaries between the two walls](../../docs/long-seqlen-tuning-guide.md#splitting-the-boundaries-between-the-two-walls) describes this graded tradeoff: raising `ac_config.offload_config.keep_last_n` retains more recent eligible tensors on GPU while older tensors still offload. First check `offload_config.enabled` and actual offload counters. With `enabled=false`, checkpoint activations are already GPU-resident; increasing `keep_last_n` cannot reclaim any more activation-offload RAM and does not move CPU optimizer state. With offload enabled, try partial retention, including approximately half the measured eligible boundaries when GPU headroom permits, rather than assuming the choice is all or nothing. Recheck complete optimizer updates and both memory budgets after each change. Adjust retained pinned-cache limits if necessary, recognizing that cache retention caps do not cap live offloaded tensors. A per-layer boundary costs approximately `local_tokens * hidden_size * dtype_bytes`; leave GPU headroom instead of consuming the arithmetic maximum.

**Verify which tensors the retention knob counts.** Flash-Next's offloader counts eligible saved-tensor occurrences, not decoder layers, and a fused head may save eligible tensors outside checkpointed blocks. Do not equate `keep_last_n=N` with exactly N resident decoder boundaries without measuring tensor roles. Optimizer `pin_memory=false` can reduce pinning/allocator overhead without changing CPU Adam's parameter, gradient, or moment payload; test its actual node-memory benefit independently.

**Treat optimizer-state host OOM separately from activation retention.** Inspect the installed engine's actual master-weight, gradient and moment dtypes, devices and replica-group sharding. Lower SP does not necessarily add expert replicas. Partial CPU/GPU optimizer placement and NVMe offload require support in the exact ZeRO stage and model path; accepted schema fields alone do not establish support. Changing FP32 master weights or Adam moments to BF16 changes training precision and must not be presented as a placement-only improvement.

**Calculate the static GPU floor before replacing optimizer offload with activation-only offload.** Count trainable and frozen parameters separately from checkpoint tensor metadata and model construction; frozen weights consume device memory but have no gradients, master weights or Adam moments. For each rank, add resident model-weight bytes and the actual ZeRO partitions of master weights and both Adam moments, then account for gradient partitions and simultaneously live reduction/update buffers. Use each parameter group's real replica degree, not `world_size`, SP degree or the number of experts selected per token: all trainable experts need optimizer state. In the current EP layout, expert state is partitioned over `world_size / ep_size` replicas after EP shards the weights. Compare the worst-rank floor against NVML device capacity, leaving room for contexts, communication workspaces, activations and allocator slack. If even the persistent floor without gradients exceeds capacity, record arithmetic infeasibility and do not launch an activation-only trial or bisect sequence length. If the floor permits a trial, it is only a necessary condition: test a low, fully occupied token budget through complete optimizer updates. Preserve precision; changing master/state dtypes or optimizer algorithms is a separate configuration decision. Flash-Next world8/EP8 with the measured FP32 Adam/master settings already requires **196.875 GiB per GPU for routed-expert weights and persistent optimizer tensors alone**, versus **140.40 GiB available**; see [the model-specific calculation](references/flash-next.md#single-node-gpu-optimizer-feasibility).

**Verify cross-node transport before trusting a long search.** Confirm EFA runs selected `NET/OFI` and Libfabric when appropriate. The guide reports an aws-ofi-nccl 1.17.2 host leak and a tested flat result on 1.21.1; record the actual plugin version instead of assuming more SP nodes imply usable capacity.

**Watch host memory through optimizer steps, not just forward/backward.** Adjacent token budgets can hit allocator or retained-buffer thresholds, so a slope from passing lengths does not prove smooth host-memory growth. Sample aggregate node/cgroup memory through the first optimizer update and later steps; per-rank RSS alone misses node overhead. Inspect actual pinned-buffer allocations before attributing a jump to an allocator setting.

## Bracketed Search

**Keep knobs and runtime fixed within each search.** Save one effective config per trial. A changed EP/SP/offload/head configuration or CUDA/package/transport runtime starts a new bracket; passing lengths from another configuration or runtime are not bounds. Store a runtime identity with trial results and reject incompatible seeds.

1. Establish a passing lower bound with at least two training steps. A model-load OOM is a static-capacity problem: fix the configuration before searching length.
2. Exponentially increase the tested token budget until a confirmed GPU or host-memory failure gives an upper bound. With two passing points, use peak-memory slope to choose a useful overshoot. Respect any user-specified context, time, or cost cap.
3. Binary-search between the passing and failing lengths. Round candidates to a valid packing/SP/kernel alignment and avoid duplicate probes. Stop when the pass/OOM gap is at most **4096 tokens (4K)** if the largest passing length is **below 32768 tokens (32K)**, or **8192 tokens (8K)** at 32K and above; do not bisect further unless the user requests finer resolution. A bracket crossing 32K uses 4K until a passing bound reaches 32K. Save both endpoints and the effective resolution, then run final verification at the passing endpoint. Alignment must permit that resolution; an unrefinable larger gap is not a completed bracket.
4. Count only confirmed capacity failures as failing bounds. Import failures, authentication/download errors, unsupported kernels, invalid group sizes, timeouts, non-finite results, and collective hangs do not establish a memory ceiling. Diagnose an actionable non-capacity failure, rerun the same candidate, or stop and report the blocker.
5. After a failure, destroy the owned training job and verify workers and GPU allocations are released on every node before another candidate. An HTTP-success teardown response alone is insufficient. If recovery is necessary, identify the exact owned zone and descendants and verify process start times before signaling PIDs. Stop the search if release remains unverified. Use fresh ports and unique log/output paths; do not delete existing logs or kill unrelated clusters.
6. Recheck the selected passing candidate in a fresh job. Default to **five complete steps** with fresh random, strictly non-pad data, unless the user specifies another duration. Keep the selected workload shape and safety-buffer size; for packed trials verify one intended model call contains all expected short rows. Require finite loss and gradient norm, successful updates and advancing engine step counters for every requested step. If the user shortens an active verification after enough steps have passed, preserve all observed steps, end the owned run with verified cleanup, and record the changed requirement rather than launching another run or claiming the original duration completed. Do not silently reduce or remove the buffer for final verification.

**Resume an interrupted bracket without repeating known OOMs.** Reuse both endpoints only when their configuration hash, runtime identity, workload shape and measured outcome match the resumed search. A confirmed memory failure remains evidence even if its teardown failed, but it cannot authorize another trial until current release is independently verified on all nodes. Ignore convenience `latest` log symlinks when identifying an exact zone, and distinguish real zone-server processes from recovery launchers carrying identical zone-ID arguments.

**An interrupted expansion can resume from its qualified passing trial alone.** Follow the guide's [completed-trial reuse rule](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly), keeping the original result and its enclosing runtime evidence. Choose a history-informed next probe; cancellation does not supply an OOM endpoint.

**Accept longer seed verification without weakening the required duration.** Follow the guide's minimum-duration rule: validate every recorded update, require the demonstrated late-failure duration when applicable, and independently qualify artifacts after a bookkeeping failure rather than trusting an outer EXIT0 or rerunning successful training.

**Use the guide's planning checkpoint before an expensive automatic expansion.** A bounded probe's deliberate trial limit leaves the search incomplete, not failed infrastructure or an OOM endpoint. Reuse its checked result and runtime/release evidence to choose the next length; maximum export and dependent recipe phases still require a completed bracket and final qualification.

**Do not mistake an empty process tree for release after Ray teardown.** Follow the guide's [orphan-worker recovery rule](../../docs/long-seqlen-tuning-guide.md#set-up-each-experiment-correctly): renamed, reparented actors can retain GPU memory after their zone parents disappear. Require provable exact-zone ownership and guarded PID identity for recovery, then independently verify idle GPUs on every node before reusing the bracket.

**A completed bracket and successful cleanup are separate facts.** If the bracket is already within resolution but its last OOM left a cleanup error, recover that exact owned zone, require process-exit acknowledgments and idle GPUs on every node, then run the selected final verification. Do not repeat the known failure or falsely rewrite its search status. Give each recovery attempt a new log path; preserve the original evidence.

**Retain pressure-affected capacity passes.** Follow the guide's [recovered-allocation warning rule](../../docs/long-seqlen-tuning-guide.md#leave-a-gpu-safety-margin): successful finite verification remains a capacity pass even if the allocator recovered from pressure. Preserve all-rank warning evidence in the export/report, flag the result, and do not treat it as a clean performance qualification.

**Check that each candidate saturates the searched budget.** Record actual packed-call occupancy, not only configured limits. The packer can admit an oversized row as a singleton; reject a trial that exceeds its intended budget. When raising a budget no longer changes input occupancy or grouping, the workload is saturated: enlarge the input consistently with the requested experiment or report saturation without a capacity claim.

**Diagnose oversized transients without changing the searched meaning.** If configured knobs do not take effect, record a below-wall CUDA allocator snapshot using `DSS_MEM_SNAPSHOT` and inspect allocation stacks. Follow the guide's [late-update diagnostic rule](../../docs/long-seqlen-tuning-guide.md#turning-it-on) to dump before a known failing update while retaining the longer ordinary capacity gate. Do not use diagnostic artifacts as bounds or snapshot-on timings as final throughput measurements. Do not replace a long row with short packed rows merely to obtain a pass.

**For FP32 expert-combine pressure, follow the guide's routed-expert chunk rule.** The shared AP path also honors `deepep_token_chunk_size` with UCCL. Verify loader propagation, retain the required probe duration and establish fresh bounds after changing it; limited-rank or truncated history does not prove a different rank's OOM origin.

**If smaller chunks still retain FP32 activation casts, follow the guide's autograd saved-state rule.** An authorized AP routing correction requires reference parity and CUDA memory checks before the existing launcher's five-update runtime requalification. A completed allocator diagnostic supplies controls only; verify the exact allowed source changes on every node, use a new runtime identity, retain the reserve and establish fresh bounds.

**Requalify after an authorized implementation correction.** Follow the guide's [bounded-transient recovery](../../docs/long-seqlen-tuning-guide.md#recover-a-capacity-failing-baseline), including repository ownership, reference parity and CUDA memory checks. This AP workflow keeps the paired DSS checkout read-only unless the operator explicitly authorizes changes there. A correction creates a new runtime identity: old OOM-derived length and node-count exclusions must be reassessed, not carried forward as measured bounds.

## Deliver

**Target the actual failed worker in allocator diagnostics.** Follow the guide's [selected-rank diagnostic rule](../../docs/long-seqlen-tuning-guide.md#viewing-the-trace): resolve the worker's global rank rather than assuming CUDA device0 means rank0, retain the failed expert-chunk control, and use a below-wall two-update diagnostic without creating capacity bounds or weakening the ordinary probe duration.

**Qualify a chunk refinement before searching again.** Follow the guide's snapshot-backed expert-transient procedure, including verified omitted-backend defaults, the existing launcher's fresh five-update refinement mode, and invalidation of historical unchunked bounds. After a late OOM, follow its exact-controls-reference rule: record the historical result, preserve the source's other controls, distinguish a changed failure allocation, and never treat a superseded short pass as a new capacity endpoint.

**If fresh final verification OOMs, follow the guide's [final-failure rule](../../docs/long-seqlen-tuning-guide.md#finding-max-seqlen-for-a-given-model).** Retain the raw failure, recover a compatible bracket without repeating that OOM, and qualify a lower candidate with the unchanged reserve before export. Use the guide's explicit lower-seed/final-failure launcher arguments; ordinary resume selection must not restore a superseded pass at the failed final length.

**Requalify short passes after a late-update OOM.** Follow the guide's capacity-probe-duration rule in that same section: increase feasibility probes to the demonstrated final-verification duration and recheck historical short seeds before treating them as passing endpoints. Keep two-update performance ranking unchanged.

**Report the evidence and uncertainty together.** Save the original config, explicitly pinned optimized config, largest passing and smallest failing token budgets, search resolution, two-step losses and gradient norms, GPU and host peaks, node totals, step times, binding resource, workload shape, model/code revisions, remote job IDs, and log paths. State whether the search reached a memory boundary or merely a configured cap. Never label an untested candidate as optimized or maximum.

**Make timing and memory units unambiguous.** Give forward/backward, optimizer and their combined per-step duration separately; distinguish per-step time from all-step total and initialization. Label binary memory units as GiB. Name each memory measurement's accounting scope, say which resource caused the adjacent OOM and why GPU headroom did not invalidate that bound, and distinguish the tested fixed-configuration limit from a global optimum across untested configurations.

**Report normalized tokens/sec, complete-step time and estimator availability for both actions.** Include the selected maximum-capacity config's throughput even though capacity, not speed, was the search objective. For both capacity and fixed-length winners, report actual global non-padding input tokens per optimizer update, warm median seconds per complete update, the warm-step count and spread, and separate the cold first step. Preserve historical diagnostic timings as such rather than presenting them as clean throughput comparisons.

**Normalize with verified global work and a consistent timing statistic.** For a constant token count, report `median-step tokens/sec = global_nonpad_input_tokens_per_update / median(warm_fwd_bwd_seconds + warm_optimizer_seconds)`, summing each update's durations before taking the median. Count actual input tokens across all microbatches and DP groups exactly once; do not multiply by SP or EP ranks or count recomputation. With equal per-group occupancy, `global_tokens = per_group_tokens * (world_size / sp_size)`; verify that formula against dispatch/input audits rather than treating configured limits or worker-0 metrics as global measurements. Boundary labels ignored by the loss are still input tokens; loss-target throughput is a separate metric. Label allocation-wide tokens/sec and, if useful, the allocation average `tokens/sec/GPU = tokens/sec / allocated_GPU_count`. For variable token counts, use `sum(warm_global_nonpad_tokens) / sum(warm_complete_seconds)` and label it warm-window throughput. Do not silently mix median-step and warm-window statistics.

**With measured maximum-length and target-length configs, add estimated optimizer-amortized tokens/sec.** Follow the guide's [common-token-update estimate](../../docs/long-seqlen-tuning-guide.md#estimate-common-token-update-throughput), using the maximum workload's verified global tokens as the reference. Amortize only optimizer time by `r = reference_tokens / workload_tokens`: divide the workload tokens by the median of paired warm `fwd_bwd_seconds + optimizer_seconds/r`, never by a scaled complete-step time. Exclude update 1. Label the result estimated, record the reference and ratio, and preserve measured single-call rates alongside it. Do not launch accumulated workloads for this reporting feature or describe a fractional ratio as actual GAS. Check runtime compatibility; the estimate corrects optimizer frequency, not different attention work, routing or offload. If either measured config or timing component is absent, report unavailable. Fixed-target selection still minimizes warm forward/backward latency; an estimate does not redefine a historical winner.

**Report estimated TFLOPS only when the existing estimator supports the exact model and workload.** TFLOPS is trillions of floating-point operations per second, not a directly measured hardware counter. Search the imported runtime for existing FLOPS counters and emitted metrics; verify model support and attention/MoE accounting before using them. Record the estimator source/version, global non-pad tokens, GPU count, whether throughput is aggregate or per GPU, the timing denominator and whether recomputation is counted. Prefer complete-step throughput when a supported per-update FLOP estimate is available; label forward/backward-only throughput separately and do not compare it as complete-step throughput. Model FLOPs utilization (MFU) is a dimensionless ratio, not TFLOPS. If the model is unsupported, no estimate was collected, or the accounting cannot be verified, explicitly report **TFLOPS: unavailable** with the reason. Do not replace a missing estimator with a generic parameter-count formula, silently extrapolate another architecture, or implement a new estimator as part of tuning.

**Export the measured training controls without tuning-only debug configuration.** Snapshot the source before final verification and preserve its transport envelope. First require exact structural equality between the selected buffered payload and the saved effective config; then remove `training_config.debug` and any legacy `training_config.prime_rl.debug` block from the deployment copy only. Retain the buffered snapshots and record the deliberate export omissions and both config hashes. Keep `max_seq_len`, `mb_spec.max_tokens_per_mb`, and provider-specific limits consistent with the selected deployment; short verification rows do not require lowering those config limits. Save before/after per-node runtime manifests, including imported source paths, plugin binaries and checkpoint revision. Record necessary launcher environment settings separately because JSON does not encode every runtime dependency.

**Write final outcome configs directly in the repository root with hyphen-separated filenames.** Apply this convention to both capacity and fixed-length performance outcomes unless the user specifies another destination or filename. Use `-`, not `_`, between filename words, and identify the model, total allocated GPU count and outcome. Use `<count>gpus`, not a node count: nodes do not necessarily have eight GPUs. Name capacity outcomes `<model>-<count>gpus-max-<K>K.json`, with the verified token budget truncated to whole decimal thousands (`tokens // 1000`); name fixed-length performance outcomes `<model>-<count>gpus-<target>.json`, using the requested length label. Keep the exact token budget in the JSON and results; the filename is shorthand, not a config override. Keep trial configs, logs and raw evidence under `tuning/` or the existing trial-artifact directory, not mixed with the final exports. Preserve the original config and use distinct filenames for the two outcomes. Put each final config's full absolute path in the results TLDR and final response so the user can locate it without searching trial directories. Keep concrete outcome paths in the run's results report, not in this reusable skill or its references; generated configs are not skill dependencies.

**Maintain readable progress during long searches.** Keep a results Markdown document with a short TLDR at the top, then setup/dependency evidence, a trial table, the current pass/fail bracket, and unresolved failures. Include the full absolute final-config path in the TLDR as soon as it is written, clearly distinguishing preliminary, two-step and longer-final verification. Update after milestones. Status questions and documentation requests do not cancel unfinished authorized work; continue until the requested objective is complete, an explicit stop/pause, or an execution/permission limit.
