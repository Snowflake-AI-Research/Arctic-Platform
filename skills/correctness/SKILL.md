# Arctic Platform Correctness

**This checkout registers seven correctness tests, including two reinforcement-learning (RL) comparisons.** `single-step-grads`, `single-step-optimizer`, `checkpoint-resume-loss`, `inference-checkpoint-loss`, `e2e-sft-train-validate`, `rl-weight-sync` and `rl-router-replay` are the registered IDs. The first five tests retain their existing workload identities and prerequisites. The two RL tests require narrowly scoped, opt-in trainer/sampler evidence: actual tensor-send and receiver-write records for weight synchronization, and received routing plus forward/backward router invocations for replay. CLI discovery and help do not import these observers; ordinary training and sampling calls leave them disabled. Keep measurement and first-two participation capture inside `arctic_platform/correctness/`. Production integrations for the RL tests are limited to descriptive, opt-in `maybe_...` evidence observers under `arctic_platform/debug/`; do not restore unrelated startup, allocation or model-specific diagnostic workarounds. Reject unsupported capabilities explicitly rather than count missing coverage as a pass.

**Preserve the prediction-layer fixture admission boundary.** Seed-0 reduced pretrained `prime_rl` fixtures with positive `mtp_num_hidden_layers` in `qwen3_5_moe_text` or `qwen4_exp_text`, or positive `num_nextn_predict_layers` in `glm5_next_text`, require native prediction-weight loading and authentication unavailable on unchanged main. Report that prerequisite error. Absent or zero counts pass this admission check unchanged; do not zero counts, omit weights, or change reviewed configurations to make onboarding pass.

## Onboarding And Regression

**An onboarding request needs only the configs and tests to onboard.** Discover the execution context, run the selected tests independently, prepare their compatible references and maintain `correctness-progress.md` using [the exact report template](references/group-report-format.md). Add requested configs with pending `?` outcomes before execution; preserve compatible prior successes. These are skill responsibilities, not extra instructions the operator must repeat. Respect supplied GPU-job details and existing authorization boundaries.

### Multi-Node Job Operation

**Read [GPU job operation](references/gpu-job-operation.md) before using autorunner or launching on more than one GPU.** It gives the submit/watch protocol, all-node probe and setup procedure, single-node and multi-node correctness commands, and distributed diagnostic launch patterns. Apply it to the operator's selected allocation; do not ask the operator to supply launcher commands that the runbook already defines.

**Launch correctness once on the allocation head, not once per GPU or node.** Autorunner executes the submitted script on one host. The correctness CLI starts its owned DSS gateway with the verified same-job hostfile; that gateway starts the target workers. Use `--gpu-pool` for the selected target widths and keep single-node HF calibration separate. Do not wrap `onboard` or `run` in `torchrun`, `deepspeed`, or all-host `ds_ssh`.

**Keep coordination proportional to the task.** Continue as the execution owner unless a genuinely active command already owns the same source or allocation. An old handoff file or unrelated runner job is not evidence of conflicting ownership. Do not replace requested onboarding with agent-role negotiation or an open-ended audit; use the concrete probe, setup, execution and result steps in the runbook.

**Operate the selected GPU allocation, not just the node running the agent.** Honor the operator's chosen job and use its supported command-execution tool or authorized connection to run on the allocation head. If the agent runs on a CPU client, its own CUDA device count says nothing about the GPU job's capacity. Reuse supplied access details; ask where to run and how to connect only when that information is missing. Never combine nodes from separate jobs.

**Discover and verify every node before choosing target placement.** Follow `harness/gateway.py::_allocation_hostfile`: `DSS_GATEWAY_HOSTFILE`, then `ARCTIC_HOSTFILE`, then `/data-fast/hostfile` or `/job/hostfile`. Confirm that the selected file describes the current allocation, has unique hosts and agrees with the GPUs visible on each host. Use allocation-local `ds_ssh -f <same-job-hostfile>` and the executing Python environment; `harness/storage.py::allocation_onboarding_prerequisites` provides the maintained all-host prerequisite check. Record each node's identity, GPU type/count, interpreter, dependency versions and imported correctness/DSS source. Two nodes with eight verified GPUs each provide sixteen target GPUs even though `torch.cuda.device_count()` on either node returns eight.

**Use the verified hostfile for both capacity detection and gateway launch.** Set `DSS_GATEWAY_HOSTFILE` or `ARCTIC_HOSTFILE` in the GPU command's environment to the verified same-job hostfile. Check both variables first: `DSS_GATEWAY_HOSTFILE` takes precedence, so a stale value must not select another file. Currently, `harness/gateway.py::available_gpus` reads only these explicit variables, while `_allocation_hostfile` also discovers the default files. Finding `/job/hostfile` alone therefore does not make every capacity check count the worker GPUs. Verify the allocation total through the executing harness before launching; do not use the CPU client's hostfile or replace an eight-GPU recipe with a sixteen-GPU recipe.

**Make setup and required files work on every executing node.** Use the job's documented setup procedure when prerequisites are absent, then verify the installed runtime and supported node-to-node transport. Do not assume `/data-fast` is shared: check fixture, adapter, model-cache and scratch access on each selected host. Stage the same frozen model/input/adapter bytes through the supported same-job distribution path and verify their complete identities; never regenerate random weights independently on a worker or treat matching filenames and sizes as identical weights. Shared source storage also does not prove that every worker imports that source.

**Keep single-node HF calibration separate from multi-node target execution.** The current reference calibration runs on one node with at most eight concurrent HF workers; do not invent distributed calibration or mistake that limit for target capacity. The target gateway can use the allocation's same-job hostfile. Start only one owned gateway through the maintained onboarding/regression lifecycle, without supplying a manually started gateway URL to bypass admission. Leave explicit external services and another agent's active command untouched; keep numerical source fixed during an attempt.

**Execute the configured placement and the selected larger placement, not just their admission probes.** For wider-placement coverage, select one additional width: 4x the configured count when it fits the verified allocation, otherwise 2x when it fits. An eight-GPU recipe on a sixteen-GPU job therefore needs eight- and sixteen-GPU outcomes, not both 2x and 4x. Preserve recipe bytes, precision, sequence length and reviewed gates; use `LoadedConfig.at_gpu_width` and `scaled_for_placement` for supported in-memory placement and batch derivation, with compatible references for the resulting arms. Inspect the executing branch's CLI and `harness/execution.py`: a larger `--gpu-pool` does not prove that reduced-fixture execution actually selected the wider width. If the maintained entry point cannot express that placement, repair that correctness-library path and its controls rather than writing a model-specific launcher or claiming wider coverage from startup.

**Treat a harness locality rejection as repair work, not missing GPUs or a defective recipe.** Trace the actual executing `harness/engine_admission.py` against the verified allocation rather than assuming a restriction from an older session still exists. Verify the actual submitted-payload builder and DeepSpeed accumulation result for every selected worker runtime; a local result or matching package versions alone cannot authenticate remote defaults. Do not delete the check, assume FP32, add an override to the catalog recipe, switch to a supplied gateway or import production/debug changes. Keep the placement `H` with the concrete next repair and rerun until verified; merely recording `H` does not complete onboarding. If the repair requires unavailable access or an out-of-scope change, explain that exact blocker and ask only for the missing prerequisite.

**Verify multi-node completion and cleanup on every selected host.** After an authorized repair, rerun the affected onboarding and standalone/combined regression against compatible references, preserving reviewed tolerances. Inspect every required arm, worker participation, exit code and actual placement before reporting `P`. Verify owned gateway and token-bound worker teardown on all hosts; a reaped head process does not prove that remote Ray workers stopped. Retain compact outcomes, exact runtimes and failure evidence, and update the existing report template. Unsafe cleanup stops further execution until resolved.

### Configuration And Reference Layout

**Preserve catalog-relative recipe paths.** For a config inside `cortex-training/model-catalog/models/`, replace that prefix with `arctic_platform/correctness/configs/` and keep every remaining directory and the filename exactly. For example, `qwen3.5-2b/standard/h200-inference-lora.json` stays that relative path. Import recipe JSON, not the catalog's `model.json` metadata; do not rewrite recipe fields or bytes.

**Derive placement only for configs outside the catalog.** Use `<model-name>/<standard|long>/<gpu>-<inference|training>-<full|lora>.json`. The model name is the lowercase model basename, without its repository owner (for HF cache snapshots, use the model component rather than the snapshot hash). `long` means an explicitly configured `max_tokens_per_mb >= 262144`, including the training `mb_spec` or native `training.ds_worker_config.mb_spec`; missing or smaller budgets are `standard`, regardless of `max_seq_len` or runtime defaults. Training takes precedence when both training and sampling jobs exist. `lora` comes from the selected job's nonempty PEFT settings; otherwise use `full`. Resolve the GPU type from explicit recipe hardware, existing accelerator path/filename, or the executing GPU; do not guess a hardware identity when none is available.

**Reference folders mirror config folders, excluding the extension.** A config at `configs/qwen3.5-2b/standard/h200-training-full.json` uses `reference_data/qwen3.5-2b/standard/h200-training-full/<check-id>/...`. An explicit reference root changes only the prefix. Moving placement does not remeasure references, relabel numerical identities, or rewrite historical evidence.

**Distinguish migrated frozen IDs from new path-derived IDs.** Existing migrated configs retain their frozen IDs through `config-layout.json`. Configs without a manifest entry derive their ID by joining the config-relative path components, without the extension, with `-`: `tiny-qwen3-129m/standard/h200-training-full.json` derives `tiny-qwen3-129m-standard-h200-training-full`, while a manifest entry for that path retains `tiny-qwen3-129m-one-h200`. Specifications and summaries remain `specs/<config-id>.json` and `specs/<config-id>.onboarding.json`; use the resolved ID printed by the command or `list`, not the source filename.

**Preserve migration aliases and explicit recipe variants.** Old correctness-config paths resolve through the manifest only within their original config root; a deleted external Cortex recipe must still be supplied from an existing file. Different existing recipes that share a derived filename retain descriptive `--<variant>` suffixes. New imports reuse identical bytes and refuse conflicting bytes; for a noncatalog variant append a lowercase descriptive suffix such as `--rl-16gpus` to the source filename stem before importing. Catalog recipes retain their exact catalog-relative filenames.

**A precision change from a frozen recipe requires a new explicit noncatalog variant.** If a runnable example adds FP32 accumulation absent from the historical recipe, append `--fp32` to the external filename stem before importing. For example, `tiny-qwen3-129m-one-h200--fp32.json` imports as `tiny-qwen3-129m/standard/h200-training-full--fp32.json` and derives `tiny-qwen3-129m-standard-h200-training-full--fp32`. Prepare fresh compatible specifications and references for that identity. Do not overwrite the frozen recipe, add a migration alias to make the new bytes reuse its ID, or relabel historical reference records. A changed ordinary basename does not distinguish recipes with the same derived placement.

**Inference-only catalog recipes are imports, not training jobs.** Preserve their sampling settings and placement. P1's two supervised correctness checks still require a training sub-job and must reject an inference-only recipe before model preparation. Import acceptance is not numerical onboarding or runtime validation.

**Report imported recipes separately from tested recipes.** Byte-preserving import and CPU layout controls establish placement, not a numerical pass. For each numerical onboarding or regression result, record the selected checks and GAS arms, actual GPU width, reduced-fixture scope, report location and cleanup evidence. Put detailed receipts in the results notes and only measured outcomes in the summary; leave untested inference or LoRA imports explicitly untested.

### Autonomous Failure Recovery

**The operator supplies only the config path and intended operation or check IDs once GPU-job access is established.** Discover the remaining context in the executing checkout and selected job, including its worker nodes; do not ask the operator to paste commands, collect logs, name report directories, choose internal backend flags, locate reference records or provide environment inventories. Missing job/access details follow Multi-Node Job Operation above. If the operation is omitted, use the matching failed attempt to determine whether onboarding or regression was intended; if no attempt exists, inspect the specification and references before choosing onboarding for a new config or regression for prepared inputs. An omitted test selection means the applicable registered checks, not always two.

**Resolve the executing checkout and configuration before reading run evidence.** Check the current Git root, active interpreter and installed `arctic_platform.correctness` location; follow the local config import in `harness/config.py`. Read the supplied config and its imported copy, deriving the config ID through that helper rather than guessing from a directory name. Inspect model source, precision, sequence length, GPU placement, attention implementation, optimizer and LoRA/RL settings. Run `python -m arctic_platform.correctness list` and the relevant command's `--help` for the actual branch's supported checks and options.

**Find reports by configuration identity, not merely by the newest directory.** Inspect `work/reports/`, `work/logs/`, and any `AP_CORRECTNESS_LOGDIR` override. Read matching `batch.json`, `report.json`, `report.md`, `full.log`, `onboarding.log` and the config's `specs/<config-id>.onboarding.json`; follow their diagnostic, gateway and work-directory paths. Match config ID/path and check IDs, then compare attempt timestamps to identify the relevant failure without borrowing another run's pass. Inspect `work/logs/onboarding-state/<config-id>/` or the override's `onboarding-state/` request/phase manifests to find reusable preparation and original artifact locations. `harness/execution.py` and `onboarding/onboard.py` define these locations if the installed version differs.

**Discover prerequisites and prepared inputs from their recorded identities.** Read `specs/<config-id>.json` and its model/cache settings, plus matching records under `reference_data/<model>/<standard|long>/<recipe-stem>/<check-id>/` or a recorded `--reference-records-dir`; follow the mirrored config path, not the frozen ID as a folder name. Inspect `AP_CORRECTNESS_TMPDIR`, allocation-local hostfile settings, visible CUDA devices and installed dependencies using the command's existing preflight; do not manufacture GPU placement or switch kernels to bypass an error. Inspect Cortex connection variables without printing credentials. Follow the owned-gateway lifecycle and ownership records in `harness/gateway.py`; never kill an unrelated or explicitly external service.

**Repair the concrete failure and verify the requested operation through completion.** Use compatible retry state, preserve reviewed gates, run focused controls for code changes and rerun the requested onboarding or regression on eligible authorized hardware. After successful onboarding, run the requested applicable regression checks against its prepared records and inspect every selected arm, exit code, report and owned cleanup. If artifacts were deleted, discover that absence and rebuild only through explicit onboarding, not regression. Missing hardware, unavailable external files or unsupported production APIs must be reported precisely; do not repeatedly request evidence the agent can read or imply access that is unavailable.

**Inspect the registered checks and supplied config before selecting work.** `python -m arctic_platform.correctness list` shows the current branch's checks. P1 registers gradients and optimizer only; the full-suite branch also registers checkpoint, inference, E2E and RL checks. Applicability comes from the config and reviewed specification, not from a successful check on another model.

**Onboarding prepares references; regression only consumes compatible prepared records.** Preserve initial weights or adapter factors, materialized inputs, declared GPU placement, parameter coverage and reviewed gates. A missing or incompatible record is a prerequisite error, never permission to generate a replacement reference during regression or widen tolerance.

**Default onboarding needs only the config path.** Use `python -m arctic_platform.correctness onboard --config <config-path>` to onboard every applicable registered test and prepare its individual and combined-selection references automatically. Do not require separate per-test commands or `--prepare-references` for this workflow. Test selectors are optional for intentionally narrower requests; preparation-only mode is optional for deliberately preparing or repairing records without target execution.

**Compact reference records and imported configs remain local until selected for publication.** Do not add `configs/` or `reference_data/` to `.gitignore`, and do not stage them without an explicit selection. Retain compatible records for subsequent regression; cleanup must not delete references still needed for testing. Demo cleanup is restricted to local checkout subdirectories; allocation scratch is left for job reset.

**The first-two supervised checks support automatic gateway ownership on the allocation head.** When no Cortex host or base URL is configured, onboarding and regression start the installed upstream DSS service, use the reduced fixture and close their owned gateway. Local ownership describes the gateway process, not a requirement that all target workers be on that node; distributed targets still require the all-node admission and placement support above. Operators use one command in one terminal, without manually starting another gateway. Explicit service settings remain external and must not be replaced or shut down. This automation does not establish support for later full-model or RL workflows.

**Verify a changed operator workflow through its final report, not just startup.** Exercise the documented command on eligible hardware when available, inspect every selected arm, exit status, retained full log and owned-resource cleanup, then verify the documented regression against prepared references. Report unavailable runtime verification explicitly. Mocked lifecycle tests alone do not establish numerical correctness or complete distributed teardown.

**Reuse only compatible completed onboarding phases after a failure.** Consume the saved retry manifest and artifact checks. A target transport repair may preserve preparation but still requires target validation; changed reference code, dependencies, weights, inputs or gates cannot be treated as equivalent preparation.

**Generate one adapter identity across calibration and regression.** Onboarding and the runner must use the same explicit harness seed, PEFT recipe and base fixture. `generate_adapter`'s standalone default seed is not the runner's seed. Compare the prepared adapter identity before target work; repairing a seed mismatch requires fresh compatible preparation, not accepting the old records.

**A config edit invalidates its frozen specifications.** `config_checksum` binds the normalized training recipe; regression rejects a changed recipe instead of comparing it against old gates. Placement-only migration must preserve that checksum, the recorded config ID and specification bytes. Do not change workload settings to make a comparison agree.

**Fixture location and fixture identity are separate checks.** Reduced models and tensor scratch live on node-local fast storage. `hash_directory` binds model asset filenames and sizes, not tensor contents: rebuilding random weights with identical shapes can satisfy that digest while changing the measured model. Reuse the original fixture on every executing node or prepare a new reference explicitly through onboarding.

**One command owns a local gateway at a time.** The ownership lock rejects a second concurrent correctness command on the host. Select several checks in one command or run commands sequentially; an external service must not be replaced or shut down.

## Numerical And Evidence Boundaries

**Gradient comparison requires every aligned trainable parameter.** Compare named gradient L2 norms after target reduction and before clipping. Missing reference gradients, unmatched target names and nonfinite values are coverage failures or prerequisites; do not silently omit tensors.

**The current optimizer norm criterion is weaker than full-tensor equality.** `optimizer-state-l2-norm-v1` compares absolute L2-norm differences for first moments, second moments and moment-independent update residuals after one AdamW step. Equal magnitudes can hide sign, permutation and directional errors. Preserve the criterion and calibrated absolute gate in records and reports.

**The three later checks have independent prerequisites, not the first-two fixture contract.** Resume requires authenticated complete checkpoint state and supported restore with the same ordered batches; inference requires validated export/schema, identical sampling-node weights, a compatible sampler and complete answer-token coverage; E2E requires an SFT replay, matching initial weights/adapters and a compatible HF trajectory record. Do not manufacture supervised references for RL configs or infer restore support from weights-only export. RL selection requires the live evidence described in the prerequisite map. Use [the actual prerequisite map](../../arctic_platform/correctness/docs/running-tests.md#check-specific-prerequisites).

**Keep preparation, CPU controls, target execution and numerical verdicts separate.** A CPU pass, source pin, accepted dispatch, calibration or successful file staging is not a GPU comparison. A reduced fixture is not full-model or maximum-sequence-length validation. A retained supplied-DSS result is not automatically local AP production validation.

**Classify results from actual evidence.** A numerical pass requires completed comparisons. A numerical failure means a measured mismatch; an execution error precedes comparison. `B` is reserved for a verified missing production API, not missing test code, references, integration or capacity. `H` denotes harness/setup work and `?` denotes pending work in progress tables.

## Changes And Verification

**Synchronize P1 selectively, not by copying the full suite.** P1 registers only `single-step-grads` and `single-step-optimizer`. **Trace synchronized behavior through the operator entry point.** A copied helper or mocked route test does not prove that the CLI invokes the helper. Check selection, per-width executor keywords, gateway and zone route installation, worker capture, decoding and cleanup together. Keep native optimizer routing limited to applicable local expert-parallel optimizer checks; dense and gradient-only runs must retain their ordinary capture path.

**Automatic final validation belongs to the regression child.** Do not start a parent gateway and pass its URL as an external endpoint to the child: that loses automatic ownership and cannot authenticate an omitted accumulation default. **Native optimizer capture needs its own receipts and node-local checkpoint inventory.** Keep ordinary participation receipts out of the native optimizer decoder; the native collector supplies the capture metadata. An AP expert-resume sidefile is not a dense model-state or optimizer shard. Select the model-state writer per node and restore the engine's writer predicate even on failure. The gateway and zone-head capture routes must bind the installed producer source, not assume that the invoking checkout is installed everywhere.

**Run CPU validation without advertising GPU correctness.** Disable visible GPUs for `make test` when matching GitHub's CPU-only CI. Run focused harness controls and the configured formatting hooks too. Attribute residual failures to main only after reproducing the relevant cases against the baseline; keep the full-suite verdict separate from focused passes and previously completed numerical runs.

Prove that the intended reduced fixture was loaded before calling a diagnosis tiny-model validation. **Keep repairs at the responsible library boundary.** Reproduce the concrete failure with focused coverage in the existing domain module, repair it without changing workload identity or numerical acceptance criteria, and verify the affected cases. Broaden testing when shared behavior changes; retain earlier failures and avoid calling focused reruns a clean full-suite result.

**Use `pytest -sv` for direct selftest invocations.** `python -m arctic_platform.correctness selftest` is the supported suite command. Keep large model, checkpoint and tensor scratch on the harness's required fast storage; durable logs and compact records have separate locations.
