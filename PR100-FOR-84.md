## First decide which of these you are doing, because the answer differs a lot

### Case A — you are running on-prem

**Do nothing. #100 is not for you.**

#84 already does client-side loss on-prem through `weighted_logprob_sum`, which
commit `d71b6c94` moved to `arctic_platform/rl/processors`. That loss is
importable on an on-prem server, so the default path works.

#100 only adds a second way to express the same gradient, for servers that
cannot import that module. It defaults to off. Leave `client_loss_encoding`
unset and your path is byte-for-byte what it is today.

If you want that verified rather than asserted:

```bash
python -m pytest tests/integrations/trl/test_client_loss_encoding.py -q
```

`test_both_encodings_hand_the_server_the_same_gradient` runs the real client
under both encodings and differentiates the real server losses on whatever each
one produced. It is CPU-only and needs no Cortex.

### Case B — you are running on Cortex

**#100 alone is not sufficient.** You need three separate things. Getting only
the first is the most likely way to waste a day.

## What Cortex needs

### 1. #100, for the encoding

Cortex's loss registry is `arctic_training.arctic_rl.processors` in
ArcticTraining-dss. It holds `causal_cross_entropy`, `grpo` and `grpo_echo_v1`.
There is no `weighted_logprob` anywhere in that repo, so #84's default loss name
cannot resolve there.

Cortex resolves loss names via `_resolve_fn`, which falls back to a dotted-path
import — and the default name *is* a dotted path. So the failure is:

```
ModuleNotFoundError: No module named 'arctic_platform.rl.processors.weighted_logprob'
  at arctic_training/arctic_rl/processors/pipeline.py:165
```

Fix: `client_loss_encoding="grpo"`, which routes the same per-token weights
through the stock `grpo` loss as signed advantages. Verified equivalent.

### 2. #95, for the transport

#100's branch has `_WIRE_OPERATION = {"forward-backward": ..., "generate": ...}`
with **no** `forward`. Client-side loss needs a no-grad forward to get logprobs,
so without #95 you get:

```
NotImplementedError: cortex has no forward
```

Merge `karthik/cortex-forward-no-grad` into your working branch.

### 3. An envelope adapter, which does not exist in any PR yet

`integrations/trl/client.py` sends the on-prem `{batch, meta, processing}`
dialect and asks for post-processors `apply_temperature` and
`compute_entropy_and_logprobs`. A Cortex zone registers only `identity` and
`compute_logprobs` — the other two names do not exist in ArcticTraining-dss at
all. The zone rejects the request before any model call, with

```
dispatch requires 2D input_ids
```

Reference implementation:
[`harness/cortex_trl_adapter.py`](https://github.com/Snowflake-AI-Research/Arctic-Platform/blob/karthik/pr100-assets/harness/cortex_trl_adapter.py)
on `karthik/pr100-assets`.

**Read these limits before you trust any number that comes out of it:**

- Sound **only at `temperature=1.0`**, where `apply_temperature` is a no-op.
  At any other temperature it is silently wrong.
- It returns **zeros for entropy**. Entropy metrics are meaningless, and an
  entropy bonus will silently do nothing.

This wants to become a real PR. It blocks Cortex regardless of which loss
encoding wins, so it is worth treating as its own piece of work.

## Wiring it up

The adapter wraps the client, and the wrapper goes to *both* the training client
and the rollout worker:

```python
from arctic_platform.client import ArcticRLClient
from arctic_platform.integrations.trl.client import ArcticTrainingClient
from arctic_platform.integrations.trl.rollout import ArcticRolloutWorker
from cortex_trl_adapter import CortexTRLAdapter

client = ArcticRLClient(cfg)
engine = CortexTRLAdapter(client, temperature=1.0)   # not `client` below

training_client = ArcticTrainingClient(
    client=engine,
    temperature=1.0,
    pad_token_id=tokenizer.pad_token_id or 0,
    rollout_n=num_generations,
    server_side_loss=False,
    client_loss_encoding="grpo",     # the one line #100 adds
    response_len=max_completion_length,
)

rollout_worker = ArcticRolloutWorker(
    engine, dataset, accuracy_reward, tokenizer,
    num_generations=num_generations,
    temperature=1.0,
    old_logprobs_source="trainer",
    pad_token_id=tokenizer.pad_token_id or 0,
)
```

A full working recipe is
[`harness/run_gsm8k_grpo_cortex.py`](https://github.com/Snowflake-AI-Research/Arctic-Platform/blob/karthik/pr100-assets/harness/run_gsm8k_grpo_cortex.py).

## Two job-config settings that will kill the job at startup

Both cost a full job launch to discover, so set them up front.

1. **`attn_implementation: "flash_attention_3"`.** The Cortex image ships FA3
   only. Asking for `flash_attention_2` dies at model load with
   `ImportError: FlashAttention2 has been toggled on, but ... doesn't seem to be
   installed`.
2. **Omit `offload_optimizer` entirely** from the DeepSpeed config. Setting it
   to `{"device": "none"}` is still enough for DeepSpeed to instantiate CPUAdam,
   which then asserts `CPUAdam param is on cuda:0 and must be 'cpu'`.

## Verify the plumbing before spending a recipe run

One operation, a couple of minutes, no training loop:

```bash
PYTHONPATH=<your-branch>:<dss-client>:. \
  python pr100/ap_client_side_loss.py --config <qa6_config.json> --job-id <running-job>
```

It drives `fwd_no_grad` through `CortexTransport`, computes TRL's GRPO loss
client-side, sends it back as the `grpo` surrogate, and compares the resulting
`grad_norm` against a direct server-side `grpo` `fwd_bwd`.

Expected: agreement to ~5e-05 relative. Measured on QA6 on 2026-09-10 against
the **default** deployed image (no debug tag): direct `99.02342224` vs surrogate
`99.02857971`, rel. diff `5.2e-05`.

If that passes, the encoding and transport are fine and any later failure is in
the recipe, not in this path.

## No debug image is needed any more

Earlier runs pinned `dev_20260828_170144_40ee0a90875`. That is obsolete. Thong's
server-side envelope decode merged Sep 1 and has since reached the default
deployment, confirmed on Sep 10 by the check above.

If you see `SafetensorError: Error while deserializing: header too large` inside
`forward_only()`, that is the *old* symptom — the server handing base64 text to
`wire.loads` instead of decoded bytes. It should not reproduce; if it does, the
deployment has regressed and that is worth reporting rather than working around.

## Possible version skew with `trl`

Depending on your `trl` commit, `AsyncGRPOTrainer` may drain
`rollout_worker.metrics_queue`, while #84's worker hangs metrics off each
`RolloutSample`. Symptom:

```
AttributeError: 'ArcticRolloutWorker' object has no attribute 'metrics_queue'
```

If you hit it, `_MetricsTee` in
[`harness/run_gsm8k_grpo_cortex.py`](https://github.com/Snowflake-AI-Research/Arctic-Platform/blob/karthik/pr100-assets/harness/run_gsm8k_grpo_cortex.py)
bridges the two by intercepting `rollout_buffer.put`. Also note that `trl`'s
`async_grpo` imports `NCCLTrainerSendWeightsArgs` at module scope, which vLLM
0.28 removed; TRL supports vLLM only through 0.27.1, so pin vLLM rather than
patching the symbol.

## Open question on #100 that you may want to weigh in on

`client_loss_encoding` is currently an opt-in flag. The alternative is for the
client to ask for its own loss, catch that specific `ModuleNotFoundError`, and
fall back once — self-correcting if Cortex ever registers the loss, with no flag
to set. Both preconditions check out: the error names the exact module, and it
is raised at loss resolution *before* `engine.backward`, so nothing is
accumulated and a retry is safe (measured on QA6: 2.0e-04 shift after a failed
attempt, against 4.4e-05 scatter between two identical requests).

The reason not to simply always use `grpo` and delete the choice: at an 8x512
shape its payload is 144 KiB against 112 KiB, because it adds `loss_mask` and
`old_log_probs_shifted`. That is a 29% larger backward request on the on-prem
path for no benefit there.

This is Tunji's call, and it is asked in
[PR #100](https://github.com/Snowflake-AI-Research/Arctic-Platform/pull/100).
