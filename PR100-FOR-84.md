## Start here: which case are you in?

The answer differs enough that getting this wrong wastes a day.

- **Running on-prem?** → Case A. You need nothing from #100.
- **Running on Cortex?** → Case B. #100 by itself is *not* enough.

---

## Case A — on-prem

**Do nothing. #100 does not apply to you.**

#84 already does client-side loss on-prem through `weighted_logprob_sum`, which
Tunji's commit `d71b6c94` moved to `arctic_platform/rl/processors` so it is
importable on an on-prem server. #100 only adds a *second* way to express the
same gradient, for servers that cannot import that module, and it defaults to
off. Leave `client_loss_encoding` unset and your path is unchanged.

To confirm that rather than take it on faith:

```bash
git checkout karthik/trl-client-loss-grpo-encoding
python -m pytest tests/integrations/trl/test_client_loss_encoding.py -q
```

Expected: `12 passed`. Run from the repo root with no `PYTHONPATH` set — checked,
it resolves `arctic_platform` from the working tree.

`test_both_encodings_hand_the_server_the_same_gradient` is the one that matters:
it runs the real client under both encodings and differentiates the real server
losses on whatever each one produced. CPU only, no Cortex, no GPU.

## Case B — Cortex

Three things are needed, and they are now three PRs: #100, #95, #109. **Only the
first is in #100.** Skipping straight to step 1 and expecting it to work is the
most common failure here.

### Step 1 — #100, for the loss encoding

Cortex resolves loss names in `arctic_training.arctic_rl.processors`
(ArcticTraining-dss), which registers `causal_cross_entropy`, `grpo` and
`grpo_echo_v1`. There is no `weighted_logprob` anywhere in that repo, so #84's
default loss name cannot resolve there. Because the default name is a *dotted
path*, `_resolve_fn` tries an import and you get:

```
ModuleNotFoundError: No module named 'arctic_platform.rl.processors.weighted_logprob'
  at arctic_training/arctic_rl/processors/pipeline.py:165
```

Fix: `client_loss_encoding="grpo"`, which sends the same per-token weights as
signed advantages through the stock `grpo` loss.

### Step 2 — the `forward` route

**Check first whether you need this.** There are two independent client stacks:

- **ArcticTraining's `ArcticRLClient`** (`arctic_training/arctic_rl/client.py`)
  builds a `dss_client.NeutrinoClient` and has `fwd_no_grad`. Thong's forward
  work merged here, so **if your pipeline uses this client you can skip step 2
  entirely.**
- **Arctic-Platform's `CortexTransport`** re-implements the Cortex protocol
  independently: its own `requests` calls and its own 410-line
  `arctic_platform/wire.py` DSSST1 codec, with zero references to
  `NeutrinoClient`. None of Thong's dss-client work reaches it.

`integrations/trl` goes through AP's client, so for the TRL path you do need
this. Without it:

```
NotImplementedError: cortex has no forward
```

Combine the two branches (verified clean, no conflicts):

```bash
git checkout -b my/trl-cortex origin/karthik/trl-client-loss-grpo-encoding
git merge origin/karthik/cortex-forward-no-grad --no-edit
grep -n '_WIRE_OPERATION = ' arctic_platform/client/transports/cortex.py
# expect: {"forward-backward": "fwd-bwd", "forward": "forward", "generate": "generate"}

python -m pytest tests/integrations/trl/ tests/client/test_cortex_forward.py -q
# expect: 78 passed
```

### Step 3 — the envelope adapter, PR #109

`integrations/trl/client.py` sends the on-prem `{batch, meta, processing}`
dialect and requests post-processors `apply_temperature` and
`compute_entropy_and_logprobs`. Neither name exists anywhere in
ArcticTraining-dss *or* dss-platform; a Cortex zone registers only `identity`
and `compute_logprobs`. The zone rejects the request before any model call:

```
ValueError: dispatch requires 2D input_ids to plan token-budget microbatches
  at dss/ray_dss/jobs/gpu/sp/data_plane.py:259
```

This is now [PR #109](https://github.com/Snowflake-AI-Research/Arctic-Platform/pull/109),
stacked on #84, landing `arctic_platform/integrations/trl/cortex.py` with 20
tests. It used to be a scratch file outside every PR, which is why no Cortex
end-to-end result was reproducible from the PRs alone — anyone starting from #84
plus #95 hit the wall above. Merge #109 and you get the adapter as a normal
import:

```bash
git merge --no-edit origin/karthik/cortex-trl-adapter
```

**Read these limits before trusting any number it produces:**

- Sound **only at `temperature=1.0`**, where `apply_temperature` is a no-op.
  Any other value is refused in the constructor rather than mis-scaled.
- Returns **zeros for entropy**. Entropy metrics are meaningless and an entropy
  bonus will silently do nothing. GRPO as configured uses neither.

It is still a translation layer. Registering those two post-processors in
ArcticTraining-dss, or teaching the integration to emit both dialects, retires
it — and either is better than a shim. It blocks Cortex regardless of which loss
encoding wins, so it is independent of #100.

### Wiring

The adapter wraps the client, and the *wrapper* goes to both the training client
and the rollout worker — passing the raw `client` to either one is a silent
mistake:

```python
from arctic_platform.client import ArcticRLClient
from arctic_platform.integrations.trl.client import ArcticTrainingClient
from arctic_platform.integrations.trl.cortex import CortexTRLAdapter
from arctic_platform.integrations.trl.rollout import ArcticRolloutWorker

client = ArcticRLClient(cfg)
engine = CortexTRLAdapter(client, temperature=1.0)

training_client = ArcticTrainingClient(
    client=engine,
    temperature=1.0,
    pad_token_id=tokenizer.pad_token_id or 0,
    rollout_n=num_generations,
    server_side_loss=False,
    client_loss_encoding="grpo",     # the one line #100 adds
    response_len=max_completion_length,
)

rollout_worker = ArcticRolloutWorker(
    engine, dataset, accuracy_reward, tokenizer,
    num_generations=num_generations,
    temperature=1.0,
    old_logprobs_source="trainer",
    pad_token_id=tokenizer.pad_token_id or 0,
)
```

A complete working recipe, including `install_stub_model_loader()` and the
`_MetricsTee` bridge, is
[`harness/run_gsm8k_grpo_cortex.py`](https://github.com/Snowflake-AI-Research/Arctic-Platform/blob/karthik/pr100-assets/harness/run_gsm8k_grpo_cortex.py).

### Two job-config settings that kill the job at startup

Both cost a full job launch to discover. Set them up front.

1. **`attn_implementation: "flash_attention_3"`.** The Cortex image ships FA3
   only; FA2 dies at model load.
2. **Omit `offload_optimizer` entirely.** Setting it to `{"device": "none"}` is
   still enough for DeepSpeed to instantiate CPUAdam, which then asserts
   `CPUAdam param is on cuda:0 and must be 'cpu'`.

## Verify the plumbing before spending a recipe run

Two minutes and one operation, versus an hour to find the same thing mid-run.

The adapter is in #109 now, but the probe scripts are not in any PR's diff —
they live on the `karthik/pr100-assets` branch. Get them into a directory of
their own:

```bash
git fetch origin karthik/pr100-assets
git worktree add /tmp/pr100-assets origin/karthik/pr100-assets --detach
cd /tmp/pr100-assets/pr100    # the probe and its helpers live here
```

`cortex_client_side_loss.py` (which supplies `build_client`) is in `pr100/`, so
run the commands below from that directory.

You also need a Cortex config JSON of this shape (supply your own PAT):

```json
{"host": "<account>.snowflakecomputing.com", "pat": "<token>",
 "database": "NEUTRINO_DB", "schema": "PUBLIC", "endpoint": "cortex-training"}
```

Then create a job and run the transport check against it:

`PYTHONPATH` decides which checkouts get exercised, and the scripts derive their
defaults from it — the job body from the imported `dss_client`, the TRL loss from
the imported `arctic_platform`. So put the combined branch first and there is
nothing else to point at:

```bash
export PYTHONPATH=<combined-branch>:<dss-client-checkout>:.

# Create a job on the default image and wait for RUNNING (a few minutes).
python -c "
import json; from pathlib import Path
from cortex_client_side_loss import build_client, default_job_body
c = build_client(json.loads(Path('<config.json>').read_text()))
jid = str(c.create_job_from_body(json.loads(Path(default_job_body()).read_text()))['job_id'])
print(jid, flush=True); c.wait_for_job(jid)
"

python ap_client_side_loss.py --config <config.json> --job-id <job-id>
```

Sanity-check the wiring before you spend a job, since a wrong `PYTHONPATH` is
the easiest way to test the wrong code:

```bash
python -c "
import arctic_platform, dss_client, os
print('arctic_platform ->', os.path.dirname(arctic_platform.__file__))
print('dss_client      ->', os.path.dirname(dss_client.__file__))"
```

Both should point at your checkouts, not at `site-packages` or someone else's
clone.

It drives `fwd_no_grad` through `CortexTransport`, computes TRL's GRPO loss
client-side, returns it as the `grpo` surrogate, and compares the resulting
`grad_norm` against a direct server-side `grpo` `fwd_bwd`.

Expected: agreement to ~5e-05. Measured on QA6 against the **default** deployed
image, no debug tag: direct `99.02342224` vs surrogate `99.02857971`, relative
difference `5.2e-05`.

**Cancel the job when you are done** — it holds GPUs on a shared account:

```bash
python -c "
import json; from pathlib import Path
from cortex_client_side_loss import build_client
build_client(json.loads(Path('<config.json>').read_text())).cancel_job('<job-id>')"
```

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `NotImplementedError: cortex has no forward` | AP transport has no `forward` route | Step 2 |
| `ModuleNotFoundError: ...rl.processors.weighted_logprob` | Cortex cannot import AP's loss | Step 1, `client_loss_encoding="grpo"` |
| `ValueError: dispatch requires 2D input_ids ...` | on-prem envelope sent to a Cortex zone | Step 3, merge #109 |
| `SafetensorError: ... header too large` in `forward_only()` | server handed base64 text to `wire.loads` | Should not reproduce; deployment regression, report it |
| `ImportError: FlashAttention2 ... doesn't seem to be installed` | image ships FA3 only | `attn_implementation: "flash_attention_3"` |
| `AssertionError: CPUAdam param is on cuda:0` | `offload_optimizer` present at all | remove the key |
| `AttributeError: 'ArcticRolloutWorker' object has no attribute 'metrics_queue'` | `trl` version skew | `_MetricsTee` in the harness recipe |
| `ImportError: cannot import name 'NCCLTrainerSendWeightsArgs'` | vLLM 0.28 removed it; TRL supports ≤0.27.1 | pin vLLM ≤0.27.1 (do **not** stub the symbol) |

## What was verified here, and what was not

Verified on 2026-09-10:

- #100 applies to #84's head with no rebase; #100 + #95 merge with no conflicts.
- `12 passed` on #100 alone; `78 passed` on the combination, from a clean
  checkout with no `PYTHONPATH`.
- The equivalence test can fail: rolling `advantages` by one position breaks it
  plus five existing tests.
- Client-side loss through AP's `CortexTransport` on the **default** QA6 image,
  matching a direct server-side `grpo` to `5.2e-05` on `grad_norm`.
- A forward forced into 33 chunks returns **bitwise-identical** logprobs to the
  single-envelope forward on the default image.
- Every error string above, located at the file and line cited.
- The adapter's translation, by 20 unit tests in #109. The two failures that
  would be quiet — an off-by-one label frame, and a `loss_mask` one position
  wider than the labels — were confirmed discriminative by mutation: reverting
  either fix turns exactly its test red.
- vLLM pinned to 0.27.1, after which TRL imports with no stub. `trl` itself
  declares `vllm<=0.27.1`, so 0.28 was out of contract to begin with.
- **A recipe-scale run on the default image, no pinned tag**: 100 steps of GSM8K
  GRPO over Cortex through #109's adapter, reward `0.401 -> 0.634` on seed 7,
  against the same seed with advantages negated going `0.217 -> 0.000`. The two
  configs differ in exactly one meaningful key, `negate_advantages`. This
  retires the debug-image caveat that used to sit here.
- The log-prob **frame**, indirectly but for real: importance ratio inside
  `[0.99937, 1.00244]` across both runs. On policy an off-by-one frame blows the
  ratio up, so this is the check that `compute_logprobs` and
  `compute_entropy_and_logprobs` agree — the one thing no client-side unit test
  can settle.

Also fixed as part of this review, because the scripts were not runnable off my
machine: two of them called `sys.path.insert` on a hardcoded clone, which
silently overrode `PYTHONPATH`, and several flags defaulted to absolute paths in
my home directory. Defaults are now derived from the imported packages. If you
do want to force a dss-client checkout, set `DSS_CLIENT_REPO`.

**Not** verified:

- The adapter at any temperature other than 1.0 — it refuses those rather than
  guessing, so this is a limit, not a risk. Entropy is likewise zeros by
  construction on this path, which rules out entropy-regularised recipes.
- Any model other than Qwen3-1.7B, and any recipe other than GSM8K GRPO.
- LoRA, which is a separate gap and not addressed anywhere in this stack.

## Open question on #100

`client_loss_encoding` is an opt-in flag. The alternative: the client asks for
its own loss, catches that specific `ModuleNotFoundError` once, and falls back —
self-correcting if Cortex ever registers the loss, with no flag to set. Both
preconditions hold: the error names the exact module, and it is raised at loss
resolution *before* `engine.backward`, so nothing is accumulated and a retry is
safe (measured: 2.0e-04 shift after a failed attempt, against 4.4e-05 scatter
between two identical requests).

The reason not to simply always use `grpo` and delete the choice: at an 8x512
shape its payload is 144 KiB against 112 KiB, since it adds `loss_mask` and
`old_log_probs_shifted` — a 29% larger backward request on the on-prem path for
no benefit there.

Tunji's call, asked in
[PR #100](https://github.com/Snowflake-AI-Research/Arctic-Platform/pull/100).
