## Case A — on-prem

**Do nothing. #100 does not apply to you.**

## Case B — Cortex

Three things are needed, and they are now three PRs: #100, #95, #109. **Only the
first is in #100.** Skipping straight to step 1 and expecting it to work is the
most common failure here.

### How the encoding works, in six lines

Useful when debugging, because the failure modes only make sense against it.

The client gets log-probs back from a no-grad forward, detaches them into a leaf,
runs TRL's real GRPO loss on that leaf, and differentiates:

```python
leaf = log_probs.detach().requires_grad_(True)
loss = loss_fn(leaf)
(grad_log_probs,) = torch.autograd.grad(loss, leaf)   # w = dL/dlogprobs
```

That autograd graph holds the loss function only — a few elementwise ops on a
`[1, T]` tensor, no model, no activations. It runs on CPU. The server then
evaluates a surrogate whose gradient is `w`, and backprops *that* through the
model. So the chain rule is split across the wire: the client owns
`dL/dlogprobs`, the server owns `dlogprobs/dtheta`, and their composition is the
true `dL/dtheta`. The server never needs to know what `L` was, which is why any
client-side loss — PPO, importance sampling, a custom objective — needs no new
server code. The cost is one extra forward pass per step (~1 s against a ~6 s
`fwd_bwd` at this shape).

`_surrogate_payload` in `integrations/trl/loss.py` does the encoding. Under
`"grpo"` it pins `old_log_probs_shifted` to the log-probs the forward just
returned, which makes the ratio exactly 1 and leaves GRPO's gradient at
`-advantages`; passing `advantages = -w` therefore delivers `w`. Setting
`batch_num_tokens` and `dp_size` to 1 collapses token-mean into a plain masked
sum so the scale matches too. Clipping cannot engage: at ratio 1,
`min(r*A, clip(r)*A) == A` for any epsilon.

The ratio is 1 only to within bf16 forward nondeterminism, which predicts a
gradient perturbation of ~1e-5 relative. The measured `5.2e-05` is that
prediction landing where it should.

### Step 1 — #100, for the loss encoding

Cortex resolves loss names in `arctic_training.arctic_rl.processors`
(ArcticTraining-dss), which registers `causal_cross_entropy`, `grpo` and
`grpo_echo_v1`. There is no `weighted_logprob` anywhere in that repo, so #84's
default loss name cannot resolve there. Because the default name is a *dotted
path*, `_resolve_fn` tries an import and you get:

```
ModuleNotFoundError: No module named 'arctic_platform.rl.processors.weighted_logprob'
  at arctic_training/arctic_rl/processors/pipeline.py:165
```

Fix: `client_loss_encoding="grpo"`, which sends the same per-token weights as
signed advantages through the stock `grpo` loss.

### Step 2 — the `forward` route

### Step 3 — the envelope adapter, PR #109

`integrations/trl/client.py` sends the on-prem `{batch, meta, processing}`
dialect and requests post-processors `apply_temperature` and
`compute_entropy_and_logprobs`. Neither name exists anywhere in
ArcticTraining-dss *or* dss-platform; a Cortex zone registers only `identity`
and `compute_logprobs`. The zone rejects the request before any model call:

```
ValueError: dispatch requires 2D input_ids to plan token-budget microbatches
  at dss/ray_dss/jobs/gpu/sp/data_plane.py:259
```

This is now [PR #109](https://github.com/Snowflake-AI-Research/Arctic-Platform/pull/109),
stacked on #84, landing `arctic_platform/integrations/trl/cortex.py` with 20
tests. It used to be a scratch file outside every PR, which is why no Cortex
end-to-end result was reproducible from the PRs alone — anyone starting from #84
plus #95 hit the wall above. Merge #109 and you get the adapter as a normal
import:

```bash
git merge --no-edit origin/karthik/cortex-trl-adapter
```

**Read these limits before trusting any number it produces:**

- Sound **only at `temperature=1.0`**, where `apply_temperature` is a no-op.
  Any other value is refused in the constructor rather than mis-scaled.
- Returns **zeros for entropy**. Entropy metrics are meaningless and an entropy
  bonus will silently do nothing. GRPO as configured uses neither.

It is still a translation layer. Registering those two post-processors in
ArcticTraining-dss, or teaching the integration to emit both dialects, retires
it — and either is better than a shim. It blocks Cortex regardless of which loss
encoding wins, so it is independent of #100.

### Wiring

The adapter wraps the client, and the *wrapper* goes to both the training client
and the rollout worker — passing the raw `client` to either one is a silent
mistake:

```python
from arctic_platform.client import ArcticRLClient
from arctic_platform.integrations.trl.client import ArcticTrainingClient
from arctic_platform.integrations.trl.cortex import CortexTRLAdapter
from arctic_platform.integrations.trl.rollout import ArcticRolloutWorker

client = ArcticRLClient(cfg)
engine = CortexTRLAdapter(client, temperature=1.0)

training_client = ArcticTrainingClient(
    client=engine,
    temperature=1.0,
    pad_token_id=tokenizer.pad_token_id or 0,
    rollout_n=num_generations,
    server_side_loss=False,
    client_loss_encoding="grpo",     # the one line #100 adds
    response_len=max_completion_length,
)

rollout_worker = ArcticRolloutWorker(
    engine, dataset, accuracy_reward, tokenizer,
    num_generations=num_generations,
    temperature=1.0,
    old_logprobs_source="trainer",
    pad_token_id=tokenizer.pad_token_id or 0,
)
```

A complete working recipe, including `install_stub_model_loader()` and the
`_MetricsTee` bridge, is
[`harness/run_gsm8k_grpo_cortex.py`](https://github.com/Snowflake-AI-Research/Arctic-Platform/blob/karthik/pr100-assets/harness/run_gsm8k_grpo_cortex.py).

### Two job-config settings that kill the job at startup

Both cost a full job launch to discover. Set them up front.

1. **`attn_implementation: "flash_attention_3"`.** The Cortex image ships FA3
   only; FA2 dies at model load.
2. **Omit `offload_optimizer` entirely.** Setting it to `{"device": "none"}` is
   still enough for DeepSpeed to instantiate CPUAdam, which then asserts
   `CPUAdam param is on cuda:0 and must be 'cpu'`.

### What a healthy run looks like, early

Don't wait 2.5 hours to find out. By step ~20:

- **`ratio` pinned near 1.000.** Mine stayed inside `[0.99937, 1.00244]` for all
  200 logged steps across both arms. This is the single most informative number
  on the path: on policy it must be ~1, and an off-by-one log-prob frame blows it
  up immediately. If it is not ~1, stop and fix that before reading anything else.
- **Reward moving in the normal arm**, noisily. Per-step sd is ~0.24, so single
  steps swing wildly; look at a 10-step mean.
- **Reward declining in the control arm.** Mine went `0.275` (steps 1–10) →
  `0.158` → `0.048` → `0.002` → identically 0 from step 32 on.

### Expected result

| arm | reward, first 20 steps | last 20 | delta |
|---|---|---|---|
| normal | 0.4007 | 0.6340 | **+0.2333** |
| `--negate-advantages` | 0.2166 | 0.0000 | **−0.2166** |

Permutation test on the normal arm's first-20 vs last-20: p = 0.0052. Normal vs
control over the last 20: p < 0.0001. Each reward point is a mean over 32
completions across 8 prompts.

**Why the control is the real result.** The two arms share seed 7 and every
hyperparameter — I diffed the arg dicts and they differ in exactly two keys, the
output path and `negate_advantages`. So the only thing separating a run that
climbs to 0.63 from one that collapses is the *sign* of the weights the client
sends. A converging run on its own would not establish that; plenty of bugs
still let a model improve.

The control's floor at exactly zero is expected, not a crash: once every
completion in a group scores 0, GRPO's within-group advantages are all 0, the
loss is 0, and gradients vanish. Its decline is also gradual over 32 steps,
which is what learning backwards looks like — a broken pipeline fails at step 1.

### Three metrics that will mislead you

Worth reading before you conclude something is broken.

1. **`grad_norm` is `0.0` at every step, in both arms.** A logging artifact, not
   a finding: the optimizer step happens on Cortex, so the local TRL trainer has
   no gradient to report. `learning_rate` does log correctly (nonzero at all 100
   steps). Don't use `grad_norm` as a health signal here at all.
2. **The server's reported loss is not the loss.** Under the `grpo` encoding the
   server computes a surrogate whose *gradient* is right and whose *value* is
   meaningless — at ratio 1 the per-token term is `-advantages`, so it reports
   `sum(w)` rather than `sum(w * logprobs)`. The client reports its own loss to
   TRL and discards the server's. Server-side loss metrics on this path are
   meaningless by construction.
3. **`entropy` is `0.0` throughout.** The zone's `compute_logprobs` doesn't
   compute it; #109 substitutes zeros to keep the shape contract. Harmless for
   GRPO as configured, disqualifying for anything entropy-regularised.

under `assets/default-image/`, if you want something to diff against.

## Open question on #100

`client_loss_encoding` is an opt-in flag. The alternative: the client asks for
its own loss, catches that specific `ModuleNotFoundError` once, and falls back —
self-correcting if Cortex ever registers the loss, with no flag to set. Both
preconditions hold: the error names the exact module, and it is raised at loss
resolution *before* `engine.backward`, so nothing is accumulated and a retry is
safe (measured: 2.0e-04 shift after a failed attempt, against 4.4e-05 scatter
between two identical requests).

The reason not to simply always use `grpo` and delete the choice: at an 8x512
shape its payload is 144 KiB against 112 KiB, since it adds `loss_mask` and
`old_log_probs_shifted` — a 29% larger backward request on the on-prem path for
no benefit there.
